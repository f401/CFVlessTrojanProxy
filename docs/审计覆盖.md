# 审计覆盖清单（自举 7.124–7.238）

这份文件只回答一个问题：**哪些地方已经系统性看过、结论是什么、哪些不必再看**。
它不描述代码行为（去 `docs/ARCHITECTURE.md` 与 `docs/v8.md`），只记录审计的边界 —— 免得每一轮都把同一批函数重读一遍，也免得"没查出问题"被误读成"这里没问题"。

结论分三档：

- **已清（机械判据）**：能写成脚本、已挂成门禁或已跑过全仓，零发现就到零发现为止。
- **已清（人工判定）**：读过全文，判过"有疑点无缺陷"，理由写在这里，**不要重开**。
- **未验（只能真机）**：本地无法证明，必须真实 CF 流量，见 `docs/本地验证.md`。

## 3. 未验（只能真机）

- **子请求 / `connect()` 名额耗尽**：免费计划一轮 50 个子请求、全局 6 个并发 `connect()`。本地只能验"代码里每个循环都有界"，真实耗尽要靠线上 `?plan=1` 与 `/health` 的 `cnt`。
- **DO 单实例排队**：`cronOnce` 里多个 `env.METER.fetch` 在真实 DO 上会串行排队；本地 mock 立即返回，测不出等待长度。
- **CF 出口族**：同一个 Worker 的不同连接可能拿到 v4/v6 不同出口，这是 `eg`/`dns` 两类事实存在的理由，本地无从复现。
- **`facts` 绑定开关的真实对照**：`facts=eg` vs `none` 的收益只能在线上交替配对（7.123 之前那一轮因为 `HOOK.facts` 从未注册，全部对比作废）。


### 3.1 2026-11-17 部署 7.269 之后的真实观测

线上已发 7.269（`/health`：`version=7.269`、`facts=["eg"]`、`uuids=1`、`colo=WAW`）。两个只能在真 CF 上成立的探针回答了上面四条里的两条：

- **CF 出口族（第 3 条）**：`/<uuid>/debug?tfb=x.com&n=2` → `probed=3 / okN=3 / badN=0 / verdict=ok`，三条腿都是 `status=200`、`bytes≈45255`（整页 45 KB，不是 4 字节的 `IPv6`）：直连 189 ms、`185.253.117.147` 143 ms、`45.136.117.194` 143 ms。说明该 colo 此刻三条腿的出口族都能过 x.com —— 这正是 7.49 之前必然 403 的那条路径，所以「出口族」是时变的，只能按批次记录，不能写成常量结论。
- **DO 单实例排队（第 2 条）**：同一次 `?tfb=` 里 DO 侧并发探两条中继，单条 143–189 ms 完成、无超时、响应体完整；`/health` 的 `errors=0`、`errsByKind=[]`。另跑 `?tfb=example.com&n=1` → `probed=2 / okN=2`，直连 7 ms、`185.253.117.147` 4 ms、577 B。
- **子请求 / `connect()` 名额（第 1 条）**：部署后立刻读 `/health`，12 项失败计数（`pendFail`/`snapWriteFail`/`snapReadFail`/`snapFlush*`/`seedWriteFail`/`statsSeedFail`…）全为 0、`doCalls=0`、`src.bad=0`；`?plan=1` 给出 `adm=48`（与 `SC.SCAN_MAX` 一致）。尚无高流量轮次，这一条仍需一次真实 cron 轮次后复查 `cnt` 与 `errsByKind`。
- **`facts` 绑定配对（第 4 条）**：绑定仍是 `eg`（部署时按线上真实 settings 回写，18 条绑定齐全）；`eg` vs `none` 的配对收益仍只能靠交替改绑定 + 客户端实测，本轮未做。

结论：四条里两条已用真实流量确认（出口族、DO 排队），两条（子请求名额的极端情形、`facts` 配对收益）仍需高流量轮次与绑定交替。
