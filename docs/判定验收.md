# 判定层验收记录（v7.13）

本文件记录「压缩判定 / 业务 403 绝不拦截 / IP 级封禁 1–3 次请求感知 / OOP 重构」四项验收口径的
实现事实与线上证据。所有数字均来自本机探针（`.tmp-sim/pin.mjs`，经真实 Worker 建 VLESS/TLS 隧道）
或仓库内的 Gate 命令，可复现。

## 一、判定模型（唯一一张表）

| 项 | 实现 | 位置 |
| --- | --- | --- |
| 键 | `目标 \| 通道`，通道 = `d`（直连）/ `r:<ip>`（中继）/ `e:<ip>`（入口） | `src/route/channel.ts` |
| 状态 | `0 unknown / 1 ok / 2 blocked / 3 dead` | `src/route/verdict.ts` |
| 证据源 | `0 流量（弱）/ 1 探测或差分 / 2 端到端` | 同上 |
| 覆盖规则 | `old.src > new.src` 时拒绝覆盖；同级可互相翻案 | `VerdictTable.setState()` |
| 寿命 | 30 分钟（`fresh()`），上限 600 条，超限按最旧淘汰 | `src/route/verdict.ts` |
| 消费者 | `Policy.decide()`（选路）、`Prefs`（诊断视图）、`RelayHealth`（中继存活度） | `src/route/*` |

**为什么只有一张表**：v7 之前有 9 个重叠机制（`needPx`、`cfHost`、`pxHosts`、`cfHttp`、`cfBlock`、
`relayOff`、`relaySite`、`viaRelay|viaDirect`、`edge`），共同病症是「粒度=域名、证据=有没有字节、
结论=布尔」。现在粒度是 `目标 IP × 通道`，证据分级，结论带寿命。

## 二、判据：什么才算「被封」

| 证据 | 判据 | 能推出 |
| --- | --- | --- |
| 差分（强） | 小响应（`0 < down < 12000`、`life ≤ 8s`、`up ≤ 16KB`）**且**同站点 6 小时内另一条通道出过整页（`down ≥ 20000`） | 该通道对该目标 blocked |
| 本出口状态码（强） | `cfHttpCode(host) === 403` | 绕中继；`=== 200` 直接直连 |
| 中继假 200 | `ok && via=node && down < 6000`，累计 3 次 | 该中继对该站点不可用 |
| 流量 | 只能把 `unknown` 提成弱 ok；失败**不改结论** | —— |
| 端到端（客户端） | 订阅侧 `expected-status: 200` 的 url-test | 客户端自己挑入口 |

**误伤防护**：业务 403（`api.x.com` 无凭证、风控页）没有「同站点另一条通道刚出过整页」这个旁证，
所以差分不成立；尺寸分桶实测也证明按字节阈值分不开（`sz4` 命中 27 次、`sz1..sz3 = 0`：
封锁页与业务 403 都落在 3–12KB，其中 3–5KB 是握手证书）。

## 三、自我纠错

| 机制 | 规则 | 目的 |
| --- | --- | --- |
| 复检 | 被判死的通道按 5% 概率重试（`why="explore"`），成功的大响应立刻改回 ok | 判死只是当时的证据 |
| 比例兜底 | 被判死比例 > 75% 且可用 < 2 时，只保留最近 2 条，其余解除 | 一次机房级风控不该封死整池 |
| 自愈 | `usable` 为空时 `vClearHost(host)` 重来 | 绝不出现「没路可走」 |
| 证据时效 | 1 小时内的探测/端到端 ok 免于被流量证据推翻 | 避免「成功一次就再也学不到」 |

## 七、真实 403 证据：能做到哪一步（v7.15 实测）

目标要求「不依赖流量判定，拿到真实的 IP 级封禁证据」。结论分三层：

### 7.1 服务端做 TLS 客户端：免费计划不可行（有硬证据）

| 位置 | 结果 |
| --- | --- |
| Worker 请求路径（`SC.PROBE_REQ`） | `error code: 1102`（CPU 超 10ms） |
| Durable Object（`?tls=` → `/meter/probe`） | `Durable Object exceeded its CPU time limit and was reset.` |
| 去掉证书链校验后（`src/vendor/subtls.js` 里跳过 `Validated certificate chain…`） | 仍然超限 —— 说明开销主要在握手本身（P-256 ECDH + HKDF + AES-GCM + ASN.1 解析证书），不是验签 |

所以 `?tls=` 端点保留为诊断（能直接给出上面的报错），但**不能作为运行时证据源**。

### 7.2 替代：把「真实证据」放到能付得起 CPU 的地方

| 证据源 | 真实性 | 成本 | 落点 |
| --- | --- | --- | --- |
| 本出口 `fetch` 的 HTTP 状态码（`cfHttpCode`） | 真实（本出口到目标的 HTTP 响应） | 1 子请求、零 CPU | `decide()` 的 `http403` / `http200` |
| 客户端 `url-test`（订阅 `?tu=<url>` → `📡 通道实测` 组） | **真实端到端**：客户端逐条中继对目标做 HTTPS，`expected-status: 200` 才算健康 | 零服务端成本 | 客户端自动切到真能打通的中继 |
| 明文 `:80` 诊断（`?http=`） | 弱：状态码语义因站而异（x.com 直连回 500、经中继回中继自己的 404） | 零 CPU | 只诊断，不写判定 |
| 流量差分（`Judge`） | 推断（旁证） | 零成本 | 兜底，只在有旁证时判 |

`?tu=` 的用法：`/<uuid>/cl?tu=https%3A%2F%2Fx.com%2F` —— 生成 `📡 通道实测` 组，成员是「按中继走」的节点条目，
`type: url-test`、`url: <tu>`、`expected-status: 200`、`interval: 180`、`tolerance: 0`。哪个中继真能打开目标，
由客户端实测决定（已上线核对：订阅里该组存在、`expected-status: 200` 生效）。

### 7.3 npm 上的相关项目（本轮检索结论）

| 包 | 结论 |
| --- | --- |
| `subtls` 0.5.0 | 已在用：纯 JS + SubtleCrypto、TLS 1.3 only、P-256 + AES-128-GCM、无链构建。CPU 仍超免费额度 |
| `@reclaimprotocol/tls` 0.1.5 | TLS 1.2/1.3、纯 JS（noble/peculiar）+ 可选 `webcrypto` 加速、支持 `verifyServerCertificate: false`。**已实测**（见 7.3.1）：能打通（`HTTP/1.1 200 OK`，TLS1.3 CHACHA20 / TLS1.2 AES-128-GCM 都成功），但握手 CPU 落在 15–47 ms 量级，仍超限 |
| `node-forge` 1.4.3 | TLS 1.2 only、800KB 级、RSA 纯 JS —— 更慢，排除 |
| `pg-cloudflare` / `worker-mailer` | 用 `cloudflare:sockets` 的协议适配层，不做 TLS，排除 |
| `@peculiar/x509`、`@noble/*` | 只是证书解析 / 密码学原语，可作依赖但本身不是 TLS 客户端 |

### 7.3.1 reclaim 实测方法（可复跑）

`.tmp-sim/meas-reclaim4.mjs`：`makeTLSClient({ host, verifyServerCertificate: false, write(pkt){写 pkt.header + pkt.content}, ... })`
配合 `setCryptoImplementation(webcryptoCrypto)`，`sock.on("data", tls.handleReceivedBytes)`，只 `await startHandshake()`（不收 body、不发 GET）。

结果（本机 Node 24，`process.cpuUsage()`，Windows 计时粒度约 15 ms）：

| 目标 | 握手 CPU | 协议 |
| --- | --- | --- |
| www.apple.com | 15–47 ms | TLS1.3 / CHACHA20 |
| api.github.com | 0–32 ms | TLS1.3 |
| www.baidu.com | 0–15 ms | TLS1.2 / AES-128-GCM |

即使把证书校验关掉仍然这个量级 —— 说明成本在握手（ECDH + HKDF + AEAD + ASN.1 解析证书链），
和「验不验证书」关系不大。**结论：免费计划的 10 ms/请求（Worker）与 DO 的 CPU 上限都装不下它。**

### 7.4 subtls 轻量化实测（7.16 试验，结论：仍然装不下）

为了回答「能不能把 subtls 优化到不超时」，用上游 TS 源码（`.tmp-sim/subtls-src/`，从 `jawj/subtls@master` 拉 33 个文件）
自建了一个「只干活、不验身份」的变体（`.tmp-sim/make-lite.mjs` 生成 `.tmp-sim/subtls-lite/`）：

| 优化项 | 做法 | 省掉的东西 |
| --- | --- | --- |
| 证书链 | 按窗口 `certRemaining()` 直接跳过 DER | ASN.1 解析 3–5 KB 证书 ×2–3 张 |
| CertificateVerify | 不读摘要、跳过签名 | 1 次 SHA-256 + 1 次 ECDSA/RSA 验签 + 1 次 `importKey` |
| 链验证 | `verifiedToTrustedRoot = true` | 逐张验签、根库比对 |
| 根库 | `databaseFromPEM` 完全跳过 | 7 KB PEM 解析（5 张根） |
| 服务端 Finished | 不校验 | 1 次 HKDF + 1 次 HMAC |
| HMAC / SHA-256 | 换成纯 JS（`src/util/jshash.ts`，手写 SHA-256 + HMAC） | **十几次 `crypto.subtle` 异步调用** |

本地（Node 24，`process.cpuUsage()`）实测：

| 版本 | 握手 CPU | 说明 |
| --- | --- | --- |
| 原版 subtls | 15–63 ms | 含证书解析与链验证 |
| lite（跳过证书类工作） | 15–77 ms | 噪声内，说明证书解析不是主因 |
| lite + 纯 JS HMAC/SHA-256 | **0–16 ms**（多轮 0） | 主要成本是 `crypto.subtle` 的调用开销，不是算法本身 |

代价：lite 变体**不验证服务器身份**（不做链校验、不验 CertificateVerify、不验 Finished），只能用于「探测通不通」，
不能用于承载真实数据 —— 所以它没法取代现有的数据面。

上线实测（7.16，把 lite 换进 `src/vendor/subtls.js`）：

```
?tls=github.com                              → {"ok":false,"error":"Durable Object exceeded its CPU time limit and was reset."}
?tls=x.com&r=185.253.117.147:443             → 同上
?tls=github.com&now=1   （Worker 请求路径内联） → HTTP 503
```

结论：**即使把可控成本全部榨干，免费计划的 DO / Worker CPU 上限仍然装不下一次握手**。
本轮的处置是：把 vendor 回滚到签名的原版（不让「不验身份」的实现留在生产里），
把优化实验的产物与数据留在 `.tmp-sim/`（已 gitignore）与本节，等有非 CF 出口或付费计划时再复用。

### 7.4.1 但「不要超时」做到了（7.18）

既然握手本身装不下，就保证**探测端点永远快速返回、不再把请求拖死**：

| 端点 | 7.17 行为 | 7.18 行为 |
| --- | --- | --- |
| `?tls=github.com` | 45 s 后 1101 / 503 | **4.8 s** → `{"ok":false,"error":"timeout"}` |
| `?tls=x.com&r=185.253.117.147:443` | 同上 | **4.7 s** → 同上 |
| `?http=github.com` | **24.5 s** → `Durable Object exceeded its CPU time limit` | **0.78 s** → `{"ok":true,"code":301,"ms":29}` |

做法：
- `src/core/tlsprobe.ts` 加硬截止 `const hardEnd = t0 + 3000;`，`nextChunk` 循环顶部超时即 `sock.close()` 并结束（不再无限等待），读循环 `Math.min(now + 8000, hardEnd)`。
- `src/routes/debug.ts` 的 `?tls=` 转发 DO 时 `withTimeout(stub.fetch(...), 4000)` + `withTimeout(resp.json(), 3000)`。
- `?http=` 不再绕 DO（那条会等 20 s+ 才被重置），改为在请求路径内联 `probeHttp80()` + `withTimeout(…, 6000)` —— 明文探测只是 `connect` + 读 ≤2 KB，几毫秒的成本。

### 7.4.2 免费额度到底卡在哪（7.19/7.20 分段实测）

为了把「超时」拆成「I/O 慢」还是「算力超」，加了两条诊断路径：

| 端点 | 做什么 | 结果 |
| --- | --- | --- |
| `?raw=<host>&stage=hello` | 只 `connect` + 写一个手搓 ClientHello | **670 ms（含冷启动），bytes 177，无报错** |
| `?raw=<host>` | 再加「读回首个记录」 | `github.com` **17 ms** 就收到 `ServerHello`（head `02 6d`，即消息类型 2、长度 0x006d） |
| `?tlsnow=<host>` | 在**请求路径**跑完整握手（不绕 DO） | `github.com` / `www.apple.com` / `x.com` / 经中继 → **全部 HTTP 503（1102 CPU 超限）** |
| `?tls=<host>` | 在 DO 里跑完整握手 | 4.5–4.7 s → `{"ok":false,"error":"timeout"}` |

结论有三条：

1. **网络与读泵没问题**：手搓 ClientHello 到 `github.com` 拿到 ServerHello 只要 17 ms，全部在 10 ms CPU 预算之外（I/O 等待不计 CPU）。
2. **算力是硬墙**：同一个 Worker 里换成完整握手就 503（CPU 超限）。即使换成「跳过证书解析/证书链验证/CertificateVerify/Finished + 纯 JS HMAC/SHA-256」的 lite 变体，**请求路径仍然 503，DO 仍然 4 s+ timeout**。
3. 顺带修掉一个真 bug：`tlsprobe.ts` 的读等待原来是**单槽回调**（`notify`），当 pump 在「检查队列为空」与「登记等待者」之间插入一次 push 时会丢唤醒 → 读函数永远挂着，表现为 `timeout` 或被算力墙撞死。现在改成**等待者队列**（push 后 drain 所有等待者），并把 `?raw=` 作为回归探针留着。

所以「在免费计划内让它可用」这条做不到：一次 TLS 1.3 握手（P-256 ECDH + HKDF + AES-GCM，即便不验签）在 Node 里最省是 0–16 ms，已经顶到甚至超过 Workers 免费版 10 ms/请求的 CPU 上限，冷启动时更差。要真正可用只有三条路：付费计划、非 CF 出口（VPS/中转机）、或把「真实状态码」交给客户端实测（现有的 `?tu=<url>` + `expected-status: 200`）。

### 7.4.3 X25519 与 DO 的 CPU 预算（7.21 实测，结论：平台上限）

**试了 X25519**：把 vendored subtls 的密钥协商从 P-256 改成 X25519（`startTls.ts` 的 `generateKey({name:'X25519'})`、
`makeClientHello.ts` 的 group/key_share 改 `0x001d`、`parseServerHello.ts` 的 key share 长度 65→32、
`keys.ts` 的 `importKey`/`deriveBits` 改 `X25519`），握手能跑通，但 Node 里 CPU 仍是 **15 ms / 0 / 0 / 0**（首轮含 JIT），
与 P-256 版本没有量级差异 —— 说明成本摊在「整条 WebCrypto 调用链 + 记录加解密」上，不在单次 ECDH 的曲线上。

**量了 DO 自己的 CPU 预算**（`/meter/burn?ms=` + `?burn=` 诊断，用 `crypto.subtle.digest` 循环烧 CPU）：

| 请求 | 结果 |
| --- | --- |
| `?burn=20` | 15.7 s 后仍 `timeout`（DO 未返回） |
| `?burn=50` | 15.7 s 后 `timeout` |
| `?burn=200` | 3.7 s → `Durable Object exceeded its CPU time limit and was reset.` |
| `?burn=800` / `2000` | `timeout` |

即**免费计划 DO 的 CPU 预算是几十毫秒级**（20 ms 的纯 digest 循环就已经过不去）。
一次 TLS 1.3 握手在 Node 里最省也要 15 ms 量级，加上冷启动、读泵与记录解析，必然越界。

结论：**只要还在免费计划，服务端 TLS 探测就不可能可用** —— 这不是实现优劣问题，是额度问题。
三条出路：付费计划、非 CF 出口（VPS/中转机）执行探测、或把「真实 200/403」交给客户端实测（现有 `?tu=`）。

### 7.5 额度实测（7.15 线上）

```
before : {"doCalls":0,"kvWrites":0,"pend":0}
（连打 3 次 ?tls= + 3 次 ?http=）
after  : {"doCalls":0,"kvWrites":0,"pend":1}
```

探测**不触发 `/add`、不写 KV、不落 DO 存储**；`pend` 的那 1 条来自连接记账，与探测无关。
所以「新的计划不会超出免费版的 DO 和 KV 写」这一条有实测支撑：探测的写入成本是 0，
既有写入仍只有三处闸门（`edge:pref` / `px:seed` / `snap`）与 `/add` 批次。

## 八、已知限制（不阻塞验收）

1. 判定表是 **per-isolate** 内存表；只有 blocked/dead 会经 `/add` 批次同步到 DO，ok 不同步。
2. 免费计划下一次 subtls 握手即 `1102`（CPU > 10ms），所以**主动探测默认关闭**
   （`SC.PROBE_REQ = 0`、`SC.PROBE_RND = 0`），学习依赖流量差分与本出口状态码。
3. `?prefs=1` 看到的是本 isolate 合并 DO 后的视图，不同请求可能落到不同 isolate，多次读到的
   条数会波动（`n = 0/2/8`）。
4. x.com 的最终成功率仍由落地机房决定；判定层只保证「不把整池判死、不让业务 403 被当成封禁、 一旦识别就改道」。
