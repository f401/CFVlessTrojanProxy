# 判定层验收记录（v7.13）

本文件记录「压缩判定 / 业务 403 绝不拦截 / IP 级封禁 1–3 次请求感知 / OOP 重构」四项验收口径的
实现事实与线上证据。所有数字均来自本机探针（`.tmp-sim/pin.mjs`，经真实 Worker 建 VLESS/TLS 隧道）
或仓库内的 Gate 命令，可复现。

## 一、判定模型（唯一一张表）

| 项 | 实现 | 位置 |
| --- | --- | --- |
| 键 | `目标 \| 通道`，通道 = `d`（直连）/ `r:<ip>`（中继）/ `e:<ip>`（入口） | `src/route/channel.ts` |
| 状态 | `0 unknown / 1 ok / 2 blocked / 3 dead` | `src/route/verdict.ts` |
| 证据源 | `0 流量（弱）/ 1 探测或差分 / 2 端到端` | 同上 |
| 覆盖规则 | `old.src > new.src` 时拒绝覆盖；同级可互相翻案 | `VerdictTable.setState()` |
| 寿命 | 30 分钟（`fresh()`），上限 600 条，超限按最旧淘汰 | `src/route/verdict.ts` |
| 消费者 | `Policy.decide()`（选路）、`Prefs`（诊断视图）、`RelayHealth`（中继存活度） | `src/route/*` |

**为什么只有一张表**：v7 之前有 9 个重叠机制（`needPx`、`cfHost`、`pxHosts`、`cfHttp`、`cfBlock`、
`relayOff`、`relaySite`、`viaRelay|viaDirect`、`edge`），共同病症是「粒度=域名、证据=有没有字节、
结论=布尔」。现在粒度是 `目标 IP × 通道`，证据分级，结论带寿命。

## 二、判据：什么才算「被封」

| 证据 | 判据 | 能推出 |
| --- | --- | --- |
| 差分（强） | 小响应（`0 < down < 12000`、`life ≤ 8s`、`up ≤ 16KB`）**且**同站点 6 小时内另一条通道出过整页（`down ≥ 20000`） | 该通道对该目标 blocked |
| 本出口状态码（强） | `cfHttpCode(host) === 403` | 绕中继；`=== 200` 直接直连 |
| 中继假 200 | `ok && via=node && down < 6000`，累计 3 次 | 该中继对该站点不可用 |
| 流量 | 只能把 `unknown` 提成弱 ok；失败**不改结论** | —— |
| 端到端（客户端） | 订阅侧 `expected-status: 200` 的 url-test | 客户端自己挑入口 |

**误伤防护**：业务 403（`api.x.com` 无凭证、风控页）没有「同站点另一条通道刚出过整页」这个旁证，
所以差分不成立；尺寸分桶实测也证明按字节阈值分不开（`sz4` 命中 27 次、`sz1..sz3 = 0`：
封锁页与业务 403 都落在 3–12KB，其中 3–5KB 是握手证书）。

## 三、自我纠错

| 机制 | 规则 | 目的 |
| --- | --- | --- |
| 复检 | 被判死的通道按 5% 概率重试（`why="explore"`），成功的大响应立刻改回 ok | 判死只是当时的证据 |
| 比例兜底 | 被判死比例 > 75% 且可用 < 2 时，只保留最近 2 条，其余解除 | 一次机房级风控不该封死整池 |
| 自愈 | `usable` 为空时 `vClearHost(host)` 重来 | 绝不出现「没路可走」 |
| 证据时效 | 1 小时内的探测/端到端 ok 免于被流量证据推翻 | 避免「成功一次就再也学不到」 |

## 四、线上证据（v7.13）

### 4.1 业务 403 不被拦截（`api.x.com`，无凭证 → 必然 403）

```
node .tmp-sim/pin.mjs api.x.com 4241b903-... / -
dns	403	MRS	cloudflare      ← 客户端原样收到 403
dns	403	MRS	cloudflare
dns	403	MRS	cloudflare
```

判定表里没有 `api.x.com` 的任何 blocked 行；连接、TLS、HTTP 全部走通，403 只是上游的合法响应。

### 4.2 IP 级封禁 1–3 次请求感知（钉在已知必封边缘 `104.18.32.1`）

```
PINIP=104.18.32.1 node .tmp-sim/pin.mjs x.com 4241b903-... / -
104.18.32.1	200	MXP	cloudflare envoy
104.18.32.1	200	MXP	cloudflare envoy
104.18.32.1	200	MXP	cloudflare envoy
104.18.32.1	200	MXP	cloudflare envoy
104.18.32.1	200	MXP	cloudflare envoy
```

学习前（6.79 首测）同一入口是 `403 CPH → 200(nginx 假页) → 200 MXP`，即**第 2 次请求即改道**；
判定表建立后为 0 次失败。判定表可见：

```
curl '/<uuid>/debug?prefs=1'   → bad: r:91.215.154.80 / r:193.181.211.185 / r:185.253.117.147 ...
curl '/<uuid>/debug?vt=x.com&do=1' → { t:"x.com", c:"r:185.253.117.147", state: 2 }
```

### 4.3 CF 出口按机房封（这是成功率波动的根因，不是判定错误）

| 机房 | 结果 |
| --- | --- |
| VIE / MXP / ARN / TLL | 200（真 X 首页，`server: cloudflare envoy`） |
| SOF / MRS / CPH | 403，响应体恒为 4 字节纯文本 `IPv6` |

同一份代码一小时内成功率可在 2/6–5/6 之间漂移；`Worker` 无法选择落地机房，这一层只能靠
「非 CF 中继」或客户端多入口解决。

## 七、已知限制（不阻塞验收）

1. 判定表是 **per-isolate** 内存表；只有 blocked/dead 会经 `/add` 批次同步到 DO，ok 不同步。
2. 免费计划下一次 subtls 握手即 `1102`（CPU > 10ms），所以**主动探测默认关闭**
   （`SC.PROBE_REQ = 0`、`SC.PROBE_RND = 0`），学习依赖流量差分与本出口状态码。
3. `?prefs=1` 看到的是本 isolate 合并 DO 后的视图，不同请求可能落到不同 isolate，多次读到的
   条数会波动（`n = 0/2/8`）。
4. x.com 的最终成功率仍由落地机房决定；判定层只保证「不把整池判死、不让业务 403 被当成封禁、 一旦识别就改道」。
