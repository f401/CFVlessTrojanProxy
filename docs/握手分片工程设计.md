# 握手分片工程设计（新工程，7.22 立项）

目标：让**服务端**能看见隧道里的 HTTP 状态码（例如 `x.com` 的 403），并且**在免费计划内可用**。
单次执行的方案已经被实测否掉（见 `docs/判定验收.md` §7.4），本工程改成**把一次握手拆成多个 DO 请求**。

## 1. 实测前提（7.22 当天全部在线上量过）

| 能力 | 结论 | 证据 |
| --- | --- | --- |
| DO 能否对外 `connect()` | **能** | `?draw=github.com` → ServerHello 19–26 ms |
| socket 能否跨请求存活 | **能**（至少 ~1 s） | `?hold=github.com` 发 ClientHello 后返回；800 ms 后 `?cont` 读到 `15 03 03 00 02 02` |
| DO 里 `setTimeout` | **会触发** | `?tim=200` → wall 200；`?tim=1000` → wall 1000 |
| DO 里 WebCrypto | **单次都是 ~0 ms** | `?crypto`：random/digest/importKey/sign/P-256 keygen×2 全部 0 |
| DO 的 CPU 预算 | **几十毫秒量级** | 固定迭代 `?iter=10000000` 通过、`4×10⁷` 超时 |
| 单次跑完 subtls 握手 | **不可行** | 原版与 lite 版（跳过证书解析/验签/Finished + 纯 JS SHA-256）都让 DO `exceeded its CPU time limit` |
| Worker 请求路径跑握手 | **不可行** | `?tlsnow=` → HTTP 503（1102） |
| `Date.now()` | **同步段内冻结** | 早期 `while (Date.now()-t0 < ms)` 的 burn 循环永不退出（结论：所有截止时间必须用计时器） |

另有两个踩过的坑，已修进代码：
- `db()`（`TrustedCert.databaseFromPEM`）在 DO 里可能挂住（`?dbt` 10 s 无响应）→ 已加 1.2 s 计时器兜底，退回原始 PEM。
- 读泵的等待者队列丢唤醒（单槽回调）→ 已改成队列 + 计时器兜底。

## 2. 分片状态机

```
        ┌──────── 每次 DO 请求只推进一个阶段（含步数预算）────────┐
  start →  A hello   : 生成密钥 + 发 ClientHello
           B sh      : 读 ServerHello，派生 handshake keys
           C flight  : 解密服务端 flight（按记录拆分，可跨多次请求）
           D fin     : 发 client Finished + GET 请求
           E resp    : 读并解密应用数据，解析状态行
  done ←──┘
```

- **状态**（存 DO storage，键 `ts:<id>`）：`{ phase, privKey(JWK), rand, transcript, secrets{hs,s/c ap}, seq{in,out}, buf, host, relay, startedAt }`。
- **单次预算**：`MAX_OPS = 3`（3 次 WebCrypto 调用）或 `MAX_BYTES = 8192`（一次 AES-GCM 处理量），先到者停；返回 `{ phase, done:false }`。
- **驱动**：`/<uuid>/debug?tch=<host>&r=<ip:port>` 在请求路径里循环调用 `/ts` `/tc`（每次 `stub.fetch`），最多 N 次（`N ≤ 8`），把结果汇总成一条 JSON；客户端只发一次请求。
- **失败**：任一阶段 `stopped`/`ended` → 清 storage，返回 `{ ok:false, err, phase }`。

## 3. 为什么不是「在 Worker 里连续调用 DO」

Worker 请求有 10 ms CPU 预算，驱动循环本身只是 `await stub.fetch`，不烧 CPU；真正的算力都在 DO 的每次分片里。所以驱动放在 Worker 是正确的：8 次 `stub.fetch` 的墙钟约 1–3 s，CPU 几乎为 0。

## 4. 安全边界（必须写进实现）

- 免费额度下**做不了证书链校验**（省 CPU 的必要条件），所以分片探测的结论只能当**旁证**：
  - 探测说「200」→ 记 `state=1`，但**不能**覆盖 `src>=1` 的强结论；
  - 探测说「403」→ 只有在**两条不同通道**都返回 403 时才升级为 `blocked`（consensus），单条只记 `suspect`。
- 路由决策仍以「客户端 `?tu=` 实测 + 本出口 `cfHttpCode` + 流量差分」为主；分片探测只补上「经中继」这一维度的证据。

## 5. 里程碑

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| M1 | `src/core/tlschunk.ts` 纯函数状态机（可在 Node 里跑）+ 单测（用本地自签服务器） | Node 里对 `github.com` 拿到 `HTTP/1.1 200` |
| M2 | DO 端点 `/ts` `/tc` + storage 持久化 + Worker 侧驱动 `?tch=` | 线上 `?tch=github.com` 返回 200；`?tch=x.com&r=<中继>` 返回 200/403 |
| M3 | 结论接入 `recordProbe`（consensus 规则）+ 文档 + 门禁 | 判定表出现 `x.com` 的 `r:<ip>` 行，且单条 403 不升级 |
| M4 | 若 M2 显示单次分片仍超预算 → 把 `flight` 按记录再细分（每片 ≤4 KB） | 每片 ≤ 2 ms（以 `?iter` 等价量标定） |

## 6. 风险

1. **socket 在请求边界被回收**：只在 ~1 s 内验证过；若 2 s 以上被回收，则整个方案不成立（M2 的第一件事就是在 3 s / 5 s 后各测一次 `?cont`）。
2. **DO storage 写入额度**：每次分片写 1 行（`ts:<id>`），一次探测 ≈ 4–6 行；按每天 500 次探测算 ≈ 3000 行，远低于 10 万/天。
3. **不验证书**：见 §4，只当旁证。

## 7. 7.23 实测：socket 能活过 5 秒（M2 前提成立）

新端点 /meter/chopen|chread|chclose + 驱动 ?ch=<host>&gap=<ms>（adminOnly）：

| gap | 结果 |
| --- | --- |
| 0 ms | open ok，read ok（31 ms，7 字节） |
| 3000 ms | open ok，read ok（age 3015 ms，7 字节） |
| 5000 ms | open ok，read ok（age 5008 ms，7 字节） |

读到的 7 字节是 15 03 03 00 02 02 32 = TLS alert(fatal, decode_error)：因为存活测试用的 x25519
公钥是随机字节（不是合法公钥），github 直接拒绝——**这恰好证明连接还活着、且字节能跨请求读到**。

结论：分片方案的前提（socket 跨请求存活 + 后续请求能读到之前没读的数据）**成立**，可以进入 M1。
## 8. 8.0 转折：tunnelfetch 在 DO 里一次跑通（分片工程可以不做）


pm i tunnelfetch@1.13.1（零依赖 ESM，userland TLS 1.2/1.3 + 证书校验），挂在
/meter/tf?h=<host>&r=<relay>，实测（真 DO，7.24）：

| 目标 | 中继 | 结果 |
| --- | --- | --- |
| github.com | 无 | **200**、526 KB、81 ms、server: github.com |
| www.apple.com | 无 | **200**、260 KB、84 ms、server: Apple |
| x.com | 无 | ProxyError（CF 自环，直连必失败） |
| x.com | 185.253.117.147:443 | **403**、4 字节 body `IPv6`、157 ms |
| x.com | 45.136.117.194:443 | **200**、46 KB 真 X 首页、393 ms |

结论：
- **单次握手在 DO 里装得下**（无 CPU 超限、无 1102），subtls 之所以超限是实现问题不是平台问题；
- 经中继能直接看见 200/403，且 403 的 body 就是 4 字节 `IPv6` —— 判定层要的「真实证据」到手；
- 代价：bundle 从 362.9 → 884.9 KB（tunnelfetch 约 +520 KB），后续可改用子路径导入瘦身。

因此 M1–M4 的分片状态机**不再需要**；下一步把 probeTf 接进判定层（consensus 规则不变）。
