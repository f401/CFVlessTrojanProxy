# 架构重设计 v8

> 目标：在免费计划额度内，让「吞吐 / 速率」两种模式都能稳定路由到当前最优通道，同时能给出**有绝对证据的 IP 级封锁判定**，且不误伤业务 4xx、不依赖任何站点特化。
> 本文只写设计，不含实现。当前线上版本 7.86，源 88 文件 / 12907 行。

## 0. v8.1 修订（由实测推翻的三条旧假设）

| 旧假设 | 实测结论 | 影响 |
|---|---|---|
| 「v6 出口 → 目标必拒」 | 同一台 v6 出口中继、同一分钟：**2/5 成功**（出口恒为 `2a0f:f01:208:3ba::`） | 地址族不是开关，而是**成功率折扣**：`p6 ≈ 12.5%`（2/16） |
| 「可以把中继改成 v4 出口」 | 递 v4 字面量给中继无效：这些 proxyip **按 ClientHello 的 SNI 自己解析**（SNI 换成别的域名，回的就是那个域名） | 中继腿的族**不可控**，只能在「选哪条中继」上做 |
| 「中继探测的结论可以直接套用到用户连接」 | CF 托管站点会**透传发起方身份**：DO 探测是 DO 的出口，用户连接是客户端/中继的出口 | 直连腿的探测结论不可跨主体复用；中继腿可以（R 是第三方） |

另外两条新增事实：
- **出口族按连接抽签**：同一个 Worker 的不同连接可能拿到不同族的出站地址 → 直连腿必须自己钉族。
- **DNS 有 AAAA ≠ 接受 v6**：x.com 有 AAAA 但 v6 通过率 12.5%，所以「站点族能力」与「站点对 v6 的接受度」是两件事，必须分别记。

## 2. 设计目标 / 非目标

### 目标
1. **单一真值**：一条通道对一个站点的结论只有一个来源。
2. **证据可分级**：任何持久化结论都必须能追溯到「哪次对比、谁做的对照」。
3. **冷启动可用**：新 isolate 靠 KV 事实立即避开已知坏通道，不必试错。
4. **额度内运行**：6 并发 `connect()`、48 子请求/轮、DO CPU 几十毫秒。
5. **零站点特化**：代码里不出现任何目标域名（现状已验证 `dist` 命中 0）。

### 非目标
- 不追求「每次都是最优」（物理上做不到：冷启动、出口族抽签、客户端路径抖动）。
- 不做 userland TLS（7.69 已整体删除，免费计划装不下握手）。
- 不做站点规则分流（`DOMAIN-SUFFIX` 之类）。
- 不追求「让 v6 出口对某站点 100% 通过」——那是站点侧的行为，我们只能估计 `p6` 并据此排序。

## 4. 两个核心抽象

### 4.1 `ChanTable`（isolate 内存，唯一的内存真值）

```ts
// 键：`${host}|${chan}`，chan = "d"（直连）| "r:<relayIP>"
interface ChanRow {
  bigAt: number;      // 最近一次拿到「本站点典型尺寸以上」的响应
  tinyAt: number;     // 最近一次拿到 ≤64B 的拒绝页（**唯一可靠的封锁信号**）
  failAt: number;     // 最近一次拨号/握手中断
  ttfb: number;       // EWMA 首字节 ms
  bps: number;        // EWMA 字节/毫秒（down ≥ 5×TICK 才采；≥1MB 权重更高）
  okN: number;        // 成功次数（半衰期 6h）—— 用来算 p(host, chan)
  badN: number;       // 失败次数（同上）
  bigTypical: number; // 该站点「正常响应」尺寸的 EWMA/max，用来判 relative-small
  n: number;          // 样本数（置信度用）
}
```

- 失效：`bigAt/tinyAt` 30 分钟，`failAt` 10 分钟，性能字段 10 分钟滑动，`okN/badN` 半衰期 6 小时。
- 成功定义（**普适性的关键**）：拿到完整响应即 `ok`（`down > 64`）。业务 4xx（如 `api.github.com` 的 415 + 1277B）算成功，不算失败。
- 失败定义：`down === 0` 或 `down <= 64`（拒绝页）或拨号/握手中断。
- 写入：连接结束时一次（`connection.flush` → hook）。
- 读取：`policy.decide` 里按 host 取候选行的切片。

### 4.2 `Facts`（KV，跨 isolate 的客观事实）

```ts
interface Facts {
  v: 2;

  // ① 目标地址族能力：客观、可复现、写入即定论   【共享】
  dns: Record<string, { a: 0 | 1; aaaa: 0 | 1; at: number }>;   // "host"

  // ② 中继出口族：回显为强证据（egress 探测）      【共享】
  //    —— 这是 x 类站点成功率的关键事实：v4 出口 6/6，v6 出口 0–2/5（§13）
  eg: Record<string, { fam: 4 | 6; at: number; n: number }>;    // "relayIP"

  // ③ 站点侧统计：Beta 后验，不是布尔              【不共享，留 isolate】
  //    理由：这是「统计」，且与具体 isolate 的出口/路由相关
  site: Record<string, {
    b4: number; n4: number;   // 经 v4 出口的成功/样本
    b6: number; n6: number;   // 经 v6 出口的成功/样本
  }>;                         // "host"

  // ③b 封锁事实：**必须带中继维度**（D1）。键 = `${host}|${relayIP}`；值为证据时间  【共享】
  //     直连通道永不进这张表（CF 边缘出站身份不可归属，见 §6）
  blk: Record<string, number>;

  // ④ 中继自身健康与容量
  dead: Record<string, number>;   // relayIP → 最近一次握手必败
  cap: Record<string, number>;    // relayIP → 0..3 容量档
}
```

- **单键 `facts:1`**（与 seed / pool 合并成 world 单文档，见 §8.2），上限：`dns` 512、`eg` 256、`site` 256、`blk` 512、`dead` 128、`cap` 256，超限按最旧淘汰。
- **TTL**：`dns` 24h（DNS 结果很少变）；`eg` 6h；`site` 的 `p4/p6` 6h 指数衰减；`blk` **90 分钟**（≥ 2× cron 间隔，D9）；`dead` 30 分钟；`cap` 24h。
- **写纪律**：只写强证据（§6）；脏标记 + 最多 10 分钟一次 + 内容 hash 变化才写 → 每天 < 150 次（额度 1000）。
- **读纪律**：isolate 启动读 1 次（world 单文档），之后每 10 分钟刷新；读失败一律降级为「无事实」，不影响选路。
- **不存**：任何「站点级二元封锁」（`blk` 是 `host|relay` 且只有 A 级可写）、任何「v6 不可用」的族级结论（只存 `b6/n6` 概率）、任何与 isolate 相关的延迟样本。

#### 为什么用 Beta 后验而不是布尔

v6 出口对某站点不是「能用/不能用」，而是**每次请求抽签**（同一出口 2/5）。用 `b6/n6` 记成败，选路时按 `1/p6` 折价，既能保住「v6 节点质量好时仍可用」，也不会让请求反复落在 12.5% 的那一档上。`n` 小的时候后验接近先验（0.5），自然带有探索性。

## 6. 事实写入协议：分级 + 闸门

### 6.1 五类事实与证据等级

| 事实 | 键 | 等级 | 判定条件 | TTL |
|---|---|---|---|---|
| 地址族能力 | `dns[H]` | **A（客观）** | DoH 同时查 A / AAAA，两次（≥10 分钟间隔）结果一致 | 24h |
| 中继出口族 | `eg[R]` | **A（回显）** | 经 R 访问回显服务，两次拿到同族地址；或「配对：R 上 200 + 另一 R 上恰 4 字节 `IPv6`」 | 6h |
| 站点 × 族成功率 | `site[H].b4/n4`、`b6/n6` | **B（统计）** | 同小时窗口内，v4 腿与 v6 腿各 ≥4 次配对样本 | 6h 衰减 |
| 站点 × 中继封锁 | `blk[H|R]` | **A（差分）** | 同批内 R 得 403/451（≤32B），另一通道 2xx 且 ≥20KB；**两个独立批次**（间隔 ≥60s）；直连腿不参与 | 90 分钟（≥2×cron） |
| 中继自身坏 | `dead[R]` | **A（客观）** | 回自己的页面 / 证书不匹配 / 握手必败 | 30 分钟 |

> **没有「站点对 v6 = 封锁」这种二元事实。** v6 只影响 `p6` 的数值，不产生禁止清单。

### 6.2 单一写入口

```ts
/** 把一条候选事实提交给事实库；返回是否真的写入（弃权 = false）。 */
function commitFact(f: Facts, kind: Kind, key: string, ev: Evidence, now: number): boolean;
```

任一条件不满足即返回 `false`（弃权不写），并计入 `/health` 的 `factSkip` 分类。必须覆盖的 10 条拒绝路径：

1. 只有一个批次（缺第二次确认）
2. 同批没有 2xx 对照（做不出差分）
3. 对照腿本身是 4xx（分不清站点级）
4. 响应是 429
5. 响应是 1.2KB 的业务页（不是封锁页）
6. `eg` 事实已过期 1.5h（对照腿的族不可信）
7. 两个批次结论相反
8. 中继出口族未知（`eg` 缺失）
9. 参与的是直连腿（身份不可归属）
10. 全部满足 → 写入（唯一返回 `true` 的用例）

### 6.3 为什么这样切

- **直连腿的结论不进 KV**：直连时目标看到的是 CF 边缘身份（对 CF 托管站点还会透传客户端 IP），同一秒不同连接可能拿到不同身份 —— 结论无法归属到稳定对象。
- **中继腿可以进 KV**：R 是第三方 TCP 中继，探测与用户流量里目标看到的都是 R 的出口地址，所以「R 被该站点拒绝」是关于 R 的客观事实。
- **DNS 事实独立于观测**：它是「目标有没有 v4/v6 地址」的客观答案，与谁去连无关，因此最稳定、TTL 最长。
- **成功率只进统计字段**：二元的 `blocked` 会永久缩小可用池（7.57 实测：通配封锁把中继标死后成功率从 95% 掉到 10%）。

## 7. 选路算法

```ts
function decide(inp: DecisionIn): Choice {
  const f = facts.snap();                    // 启动读一次，之后 10 分钟刷新
  const st = f.site[inp.host];
  const p4 = st && st.n4 >= 4 ? st.b4 / st.n4 : 0.95;   // 先验：v4 很少被站点拒
  const p6 = st && st.n6 >= 4 ? st.b6 / st.n6 : 0.5;    // 先验：未知不折价

  // ① 硬过滤：只排「客观必败」的**单条**通道（D1：blk 必须带 relay 维度）
  const alive = inp.relays.filter((ip) =>
    !isBlacklist(ip) && !isFrozen(ip) && !f.dead[ip] && !f.blk[inp.host + "|" + ip]);
  const cands = alive.length ? alive : inp.relays;      // 全被排掉时绝不返回空

  // ② 单条通道的成功率：族只做先验，个体样本才是主体（D6）
  const priorOf = (ip: string) => (f.eg[ip]?.fam === 4 ? p4 : f.eg[ip] ? p6 : 0.5);
  const pOf = (row: ChanRow | null, ip: string): number => {
    const a = 4;                                        // 先验强度：4 个等效样本
    const ok = row?.okN ?? 0, bad = row?.badN ?? 0;
    return (ok + a * priorOf(ip)) / (ok + bad + a);
  };

  // ③ 代价：传输代价 / 成功率（两个维度、两个衰减率，互不污染）
  const score = (ip: string): number =>
    transport(inp.mode, perf.get(inp.host, ip)) / max(0.08, pOf(chan.get(inp.host, ip), ip));

  // ④ 直连腿：能直连就直连（懒加载族绑定见 §7.1）
  if (preferDirect(inp) && !chan.tinyRecently(inp.host, "d")) return { chan: "d", why: "direct" };

  // ⑤ 中继：score 最小 + Thompson 探索（样本少者自动获得探索）
  const pick = thompson(cands.map((ip) => ({ ip, c: score(ip), sd: sdOf(ip) })));
  return pick ? { chan: { kind: "r", ip: pick }, why: "relay-best" }
              : { chan: leastBad(inp), why: "least-bad" };
}
```

**模式差异**：

| 模式 | `transport()` | 说明 |
|---|---|---|
| `tput` | `ttfb + 512KB / max(32KB/s, bps×1024)` | `bps` 用「down ≥ 5×TICK（~40KB）」的样本；`<40KB` 的站点退化为 `ttfb + 200`（小页面吞吐无意义） |
| `lat` | `ttfb` | 只关心首字节 |

**两个维度必须分开**（这是同时满足「x 类成功率」与「站点特定吞吐优化」的核心）：

| 维度 | 键 | 采样来源 | 衰减 | 作用 |
|---|---|---|---|---|
| `transport` | `host × relay` | 成功传输的 `ttfb` 与 `bytes/ms` | 10 分钟 | 「谁更快」= 站点特定优化 |
| `p` | `host × relay`（族做先验） | 完整响应 / 拒绝页（≤64B） | 6 小时 | 「谁能过」= x 类保护 |

**防污染铁律**：拒绝页（≤64B）**绝不写 `transport` 样本** —— 4 字节 403 只要 80ms，写进去会让「越坏越快」（7.83 踩过这个坑）。

**冷启动**：`cap` 作为 `bps` 先验；`dead` / `blk` 排除单条通道；族先验 `p4/p6` 在样本 <4 时生效。

**探索**：保留 5% 概率选「未知」通道，避免事实过期后永远不验证。

### 7.1 直连腿的地址族（懒绑定，不用 Happy Eyeballs 预热）

直连腿是**我们自己的 `connect()`**，所以族可控 —— 这是 v8 里唯一能钉族的地方。但**不要**在 happy path 上先查 DNS 再拨（那会把 20–50ms 加到 TTFB 上，且双栈时要吃 2 个 connect）。

```
① 直接按域名 connect（不查 DNS、不并发）
② 成功 → 记 ok；失败或拿到 tiny(≤64B) 响应
     → 查 A / AAAA（缓存 24h）
       ├─ 只有 A    → 用 IPv4 字面量重试一次
       ├─ 只有 AAAA → 用 IPv6 字面量重试一次
       └─ 双栈      → IPv4 先试；失败再用 IPv6 重试一次
```

| A | AAAA | 只在这种情况才需要 |
|---|---|---|
| 有 | 无 | v6-only 不可能，直接 v4 |
| 无 | 有 | v6-only 站点：**必须 v6**，绝不强制 v4 |
| 有 | 有 | 双栈：v4 先，失败退 v6 |

- 只有在「已失败」时才用字面量重试，因此**好路径零额外延迟、零额外 connect**。
- 族序可由 `p4/p6` 调整（并列时 v4 先）；DNS 结果缓存在 `dns[H]`，24h，失败也缓存 5 分钟（避免反复查）。
- 由于只在失败时重试，这条逻辑最多让一条请求多花一次拨号，而不是让每次请求都多花。

### 7.2 中继腿的地址族（不可控，只能选）

- proxyip 按 **ClientHello 的 SNI** 自己解析目标，递 v4 字面量无效（实测：SNI 换成别的域名，回的就是那个域名的页面）。
- 所以中继腿只能做两件事：① 优先 `eg=4` 的中继；② `eg=6` 的中继按 `1/max(0.15, p6)` 折价。
- **永不硬封**：`eg=6` 的中继在「没有 `eg=4` 可用」时仍会被选中（探索项），否则池子会缩到 1/8。

### 7.3 v4 出口保底（供给规则，不是选路规则）

实测（§13.1 / §13.6）：8 条活跃中继里 **3 条是 v4 出口**（37.5%），而 v4 出口对 x 类站点 6/6、v6 出口 0–2/5。也就是说 **v4 出口其实够用，问题在于「不知道是哪三条」** —— 不共享时每个新 isolate 只能盲抽（命中 37.5%），共享 `eg` 之后同样的 8 条就能稳定先挑 v4。这条规则放进调度而不是 `decide()`：

```
每轮 cron：
  1. 统计 eg=4 的活跃中继数 v4n
  2. if v4n < 3:  把本轮探活预算的 2/3 花在「eg 未知」的中继上（回显探测）
     else:       按「最久未探」均摊
  3. 任何中继的 eg 探测结果**立刻写 DO**（共享），不等本轮结束
```

- 目标值 **3 条**：实测曲线（§14）里 1 条 v4 ≈ 90%、3 条 ≈ 96–97%、≥5 条 ≈ 98%；当前池子刚好 3 条，所以 v8 的增量收益主要来自「**把这 3 条认出来并共享**」，而不是「捞更多中继」。
- 为什么「未知优先」而不是「最久未探优先」：`eg` 是机器属性、6 小时才过期，未知样本的边际价值最高；而已知 v6 的中继再探也不会变成 v4。
- 为什么写 DO 而不是攒批：isolate 平均寿命只有几分钟（低流量时几乎每条请求都是新的），攒批等于把这轮发现丢掉。

## 8. 预算与配额

单轮 48 子请求、6 并发 `connect()`：

| 用途 | 预算 | 说明 |
|---|---|---|
| 池子准入（探活节点） | 32–40 | 节点是 WS 端点，决定基础可用性 |
| 审计探测（tfb 批次） | 6–8 | 每批 1 个 DO 请求 + 3 条 connect |
| 退款/重试 | 4 | `refund` 池 |
| 订阅/健康检查 | 0 | 客户端侧 |

**并发闸门**：任何时刻「竞速/探测」占用的 connect ≤ 2（给真实流量留 4）。

### 8.1 额度账（免费计划）

| 额度 | 上限 | 现状消耗 | v8 设计 |
|---|---|---|---|
| Worker 请求 | 10 万/天 | 随流量 | 不变 |
| KV 读 | 10 万/天 | 每次 isolate 启动 2 次（`px:seed` + `px:pool:<gen>`） | **1 次**（world 单文档） |
| **KV 写** | **1000/天** | ~110（seed 90 分钟一次 + pool 换代） | **≤150**（合并 cron 写 + 内容 hash 变化才写） |
| DO 请求 | 10 万/天 | ~50（30 分钟一轮 tfb） | **≤80**（45 分钟一轮、每批带 3 个 host） |
| KV 存储 | 1 GB | 60 KB | <150 KB |

- **能撑多少 isolate**：启动读 = 1 次时，KV 读额度 → **10 万 isolate 启动/天**（此时先撞 Worker 请求额度，不再撞 KV）。v8 朴素做法（facts 独立键 + 10 分钟刷新）是每次启动 3 读 → 3.3 万，**比现在倒退**，所以必须走单文档。
- 数据面连接**不读 KV**（`readStatsCached` 只在订阅/admin 路径），这一条是能撑住的前提。

### 8.2 world 单文档

```ts
// KV 键 w:1：只放**冷数据**（事实见 §16.3，改由 DO 承载）
interface World { v: 2; seed: Seed[]; poolGen: string; pool: string[]; at: number }
```

六条压缩（对应上表）：
1. seed / pool 合并为 `w:1`；facts 走 DO（§16.3）：启动仍是 **1 次 KV 读 + 1 次 DO 读**。
2. facts 用短键（host 取 6 字节 hash、数组下标代替对象键）：20 KB → ~7 KB。
3. seed / pool 统一由 cron 写，写前比内容 hash：写 254 → **140/天**（facts 不再占 KV 写）。
4. 探测合并：一次 `/meter/tfb` 带 3 个 host；cron 30 → 45 分钟；DO 150 → **80/天**。
5. `meterCache` 5 → 15 分钟 + Cache API（`w:1` 世界快照 60 s/colo）。
6. `alive` 800 → 256、`chan/perf` 512 → 256：内存 0.8 → 0.45 MB。

**改口：facts 进 DO（第一版说「不做」，理由是「同为 10 万/天且多一跳」——重算后不成立）**。DO 请求额度 10 万/天是 KV **写**额度（1000/天）的 100 倍，而「写」才是真正的瓶颈；多一跳只发生在惰性刷新时（10 分钟一次、后台进行），不在首字节路径上。详见 §16.3 与 §16.4。

**仍然不做**：用 KV `list` 分片（`list` 同样受写额度约束，读还会放大）。

## 12. 明确不做

- 连接内「看到 403 就换中继重试」（Worker 只看得到 TLS 密文）
- 缓冲首块再判定（https 看不到方法，重放会重复投递 POST）
- 站点域名常量 / `DOMAIN-SUFFIX` 分流
- 入口 × 中继全交叉订阅（条目爆炸）
- 多级中继（延迟与失败点翻倍）
- 用直连通道的探测结论写 KV（身份不可归属）
- 把 v6 出口当「必败」硬封（会缩池、且与实测 2/5 矛盾）
- 往中继递 IPv4 字面量（proxyip 按 SNI 解析，实测无效）

| 中继 | 出口 | x.com |
|---|---|---|

⇒ `P(通过|v4) ≈ 100%`、`P(通过|v6) ≈ 12.5%`（2/16）：**v6 是折扣，不是开关**。

### 13.3 中继不改族（`forcev4.mjs`）

把 VLESS 目标换成 v4 字面量 `104.18.32.1`、SNI 仍为 `x.com`：经 v6 出口中继**照样 403/3 次**；经 v4 出口中继 200/3 次。再换 SNI：`cloudflare.com` → 301（CF 自己的页面）、`github.com` → 握手失败 ⇒ proxyip 认 SNI，不认 VLESS 地址。

### 13.4 客户端族（`famtest.mjs`）

同一中继，v4 客户端 6/6 200；`family=6` 臂 6/6 `ws error`（本机没有到 CF 边缘的 v6 路由）⇒ 客户端族这条**本地无法验证**，只能由用户在 v6 网络上用 FlClash 复测。

### 13.5 本地枚举池子这条路走不通（`relayscan.mjs` / `relaytls.mjs`）

两条都试过，结论明确：

| 试法 | 结果 | 原因 |
|---|---|---|
| 抽样公开源 80 条，发 `CONNECT host:443` | **0/80 可达**，且已知可用的中继回 `HTTP/1.1 400 Bad Request` | proxyip 不是 HTTP 代理，是**按 ClientHello SNI 转发的透明 TCP 代理**（`src/proxy/dialer.ts` 直接 `connect({hostname: relay})` 后写 ClientHello） |
| 抽样公开源 → 真 TLS（SNI=icanhazip.com） | 已知 v4 中继 `45.136.117.194` 复现「出口 45.136.117.194（v4）」✅；但 `185.253.117.147` 直接 `ECONNRESET`，第二个站点请求也 RST | 绝大多数中继**只对 CF 出口网段开放**（用户 2026-11-15 确认：「这些 proxyip 大部分本地确实无法访问」），并有速率/并发限制 |

**推论（写进设计的约束）**：

1. `eg` 事实**只能由 Worker 探测产生** —— 本地无法枚举、无法旁证，所以 §16.5 的「共享 `eg`」不是优化，而是让全队共担这份探测成本的**必要**机制。
2. 一次探测必须同时得到两样东西（`alive` + `eg`）：探测目标用**回显服务**（`icanhazip.com` 这类返回来源 IP 的站点），这样「连得上」与「出口是 v4 还是 v6」一次拿到 —— 这也是 D10 的修法。
3. 本地仍能做的是**经 Worker 的端到端测量**（`vclient`/`vspeed`/`pairtest` 走 `?rx=` 钉中继），以及「拿已知中继做对照」；不能做全池普查。

### 13.6 一次探测同时拿到「活着」与「出口族」（`vclient.mjs` + `?px=1&rx=`）

不写任何新代码就能验证 v8 的探测设计：`?px=1&rx=<relay>` 钉住中继，把隧道里的请求打到 **`icanhazip.com`**（回显来源 IP），body 就是该中继的出口地址。实测 8 条活跃中继（每条 1 次，1.2–1.8 s、约 620 B）：

| 中继 | 出口 | 族 |
|---|---|---|
| `45.136.117.194` | `45.136.117.194` | **v4** |
| `45.147.250.39` | `45.147.250.39` | **v4** |
| `45.151.183.22` | `45.151.183.22` | **v4** |
| `91.215.153.143` | `2001:67c:2f4c:2::51e` | v6 |
| `91.215.154.80` | `2001:67c:2f4c:2::234` | v6 |
| `193.181.211.185` | `2a0f:f01:208:3ba::` | v6 |
| `185.253.117.147` | `2a01:8640:1c::efcd:2d49` | v6 |
| `89.22.227.132` | —— | 失败：`Hostname/IP does not match certificate's altnames: Host: ica…`（回自己的页面） |

三条结论：

1. **v4 出口占 3/8（37.5%）**，比先前「1/8」的估计乐观；先前那次只测了 4 条，属于抽样偏差。
2. **一次 connect + 一次 GET 就同时得到「活着」与「出口族」** —— 这正是 D10 想要的「探测合并」，且不需要新增端点（`?rx=` 已有）。
3. `89.22.227.132` 这类「回自己证书」的中继应进 `dead` 表（机器属性、可共享），而不是仅记为「本次失败」。

**对 §7.3 的影响**：目标「≥3 条 v4 在线」当前已经满足，所以收益不在扩张池子，而在**识别 + 共享** —— 一个 isolate 探到 `eg` 就立刻写 DO，别队立刻可用。

### 13.7 首请求成功率 = v4 出口占比（基线实测，2026-11-15 02:31）

20 个新进程、每个只发 1 条请求（等价于「冷连接的第一条请求」），目标 x.com：

| 结果 | 次数 | 占比 |
|---|---|---|
| 200（4107 B，真首页） | 8 | 40% |
| 403（**737 B**，正文含 `IPv6`） | 11 | 55% |
| 失败（`Hostname/IP does not match… Host: x.c`，中继回自己的证书） | 1 | 5% |

两个结论，一个推翻假设、一个给出量化：

1. **首请求 40% ≈ v4 出口占比 37.5%（§13.6）** —— 这说明「盲选时能不能过」几乎完全由「抽到的是不是 v4 出口」决定，而不是由延迟/评分决定。**这就是可量化的杠杆**：`eg` 共享 + 优先 v4 之后，同样的 8 条中继应该把首请求从 40% 拉到 95%±。
2. **拒绝页不是 4 字节，而是 737 B**（带 `IPv6` 文本的 HTML）。这条直接推翻了「`tiny = down ≤ 64`」的判据（D3）—— 见 §15 的修正。

另注：失败那条是「中继回自己的证书」，属于 `dead`（机器属性），不是站点封锁。

## 14. 上限与瓶颈（诚实清单）

| 场景 | 现状（7.86） | v8 目标 | 说明 |
|---|---|---|---|
| 串行稳态 | 92–96% | **96–98%** | 残差是站点侧的请求级拒绝 |
| 冷 isolate 头几条 | 60–80% | **80–90%** | 事实靠 KV，但事实本身要有人先探到 |
| 20 并发 | 75–85% | **85–90%** | 每并发可能落在不同 isolate |

**不可解**：客户端→CF 边缘质量、免费计划 6 并发 / 10ms CPU、KV 1000 写/天（事实传播最慢 30 分钟）。
**半可解**：站点对 v6 的拒绝率（靠 `p6` 排序 + `eg` 优先 v4，不能归零）、假 200 骗过客户端 url-test、`eg` 的跨 isolate 传播延迟（cron 30–45 分钟）。v4 出口数量本身**不是瓶颈**：实测已有 3/8（§13.6）。
**结构性**：每个 isolate 都要自己积累内存证据；KV 只承载「客观事实」，不承载「这台机器快不快」。

## 15. 第二轮审查：11 个缺陷与修正

审查方法：把 §4/§6/§7/§8 的每个判据对着 7.86 的代码与今天的实测数据推演一遍，凡「在某种真实输入下会给出错误行为」的即计入。

### D1 `blkAt` 是站点级却过滤掉所有中继（§7 伪代码 bug）

```ts
!(f.site[inp.host]?.blkAt > 0)   // 一旦有封锁记录，cands 直接空
```

- 后果：`thompson([])` 未定义行为；即使不崩，也会退化成「无候选」。
- 修正：封锁必须键为 `host|relay`，只排那一条；全排掉时走 `leastBad(host)`（7.x 已有）兜底，并记 `why: "least-bad"`。

### D2 `ChanTable` 没有成败计数 → 算不出 `p(host, relay)`

今天实测（同一分钟）：

| 中继 | 族 | x.com | github.com | example.com |
|---|---|---|---|---|
| `91.215.153.143` | v6 | **0/8** | 3/3（120 KB） | 3/3（932 B） |
| `193.181.211.185` | v6 | **2/5** | — | — |
| `185.253.117.147` | v6 | 0/3 | — | — |
| `45.136.117.194` | v4 | 6/6 | 3/3（120 KB） | — |

- 同族内 0/8 与 2/5 差一个数量级 ⇒ 按族聚合会误伤。
- 修正：`ChanRow` 加 `okN` / `badN`（半衰期 6h）+ `bigTypical`（该站点成功响应尺寸的 EWMA/max）。

### D3 「小响应」用绝对阈值 → 冤枉正常小页面（**此条被 §13.7 实测再修正一次**）

- 实测：`example.com` 正常响应 **932 B**、`api.github.com` **1277 B**。按 `<12KB` 判据，两者都会被当成「可疑小响应」。
- 第一版修正「`tiny = down <= 64`」**同样不成立**：§13.7 实测 X 的拒绝页是 **737 B**（带 `IPv6` 文本的 HTML），`≤64B` 会漏掉今天的绝大部分封锁页。
- 最终修正（两条同时满足才算 `tiny`）：
  1. **绝对**：`down <= 2048`（覆盖 4B / 737B / 1.3KB 这几代拒绝页）；
  2. **相对**：`down < 0.2 × bigTypical(H)`（737 B / 45 KB = 1.6% 明显低于阈值；`example.com` 932 B 但它的 `bigTypical` 也只有 ~1KB ⇒ 比值 ≈1，不会误判）。
- `tiny` 只用于「降权 / 记负记忆」，**永不单独作为封锁证据**（封锁仍要 §6 的两批次差分）。

### D4 成功 ≠ 2xx：业务 4xx 会被记成失败

- 实测：`api.github.com` 经两条中继都是 **415 + 1277 B**（它要求 `Accept: application/json`）。这是**正常的应用层响应**，但按「2xx 才算成功」会被算成 0% 成功，于是该站点的每条中继都被降权，最终无人可用。
- 修正：`ok` 的定义改成「拿到完整响应」：`down > 64`（非拒绝页）即可；`2xx` 只作为「整页」的辅助判据。**这是普适性最关键的一条**：API、GraphQL、401 页面、重定向都算成功。

### D5 吞吐样本要求 ≥1 MB → 普通网页永远学不到 `kbs`

- 实测尺寸：x.com 主页 45 KB、github.com 120 KB、example.com 0.9 KB。`connection.ts:317` 的 `down >= 1048576` 意味着**这些站点全部记为 `kbs=0`**，tput 模式退化成只看 `ttfb`。
- 修正：门槛改成 `down >= 5 × TICK_BYTES`（约 40 KB）并记 `bytes/ms`；同时保留「≥1MB 样本权重更高」。对 `<40KB` 的站点，tput 代价退化为 `ttfb + 200`（表示「小页面的吞吐无意义」）。

### D6 `famPen` 用单值 `p6` 乘所有 v6 中继

- 见 D2 的数据：同族内差异巨大。
- 修正：`p(host, relay) = (okN + α·prior) / (okN + badN + α)`，`α=4`，`prior` 由族先验给出（`eg=4 → p4`、`eg=6 → p6`、未知 → 0.5）；排序用 `score = transport / max(0.08, p)`。

### D7 Happy Eyeballs 没进预算，且要 DoH 才有地址

- 一次双栈请求吃 2 个 connect（6 并发下砍掉 1/3 真实流量）；DoH 20–50 ms 全加在 TTFB 上。
- 修正：**懒加载族绑定** —— happy path 直接按域名连（不查 DNS）；只有「失败」或「tiny 响应」时才 DoH 取 A 记录重试一次。既不需要预算，也不给好路径加延迟。

### D8 `world` 单键的读改写竞争

- 两个 isolate 同时「读 → 改 → 写」`w:1`，后写覆盖前写，facts 丢更新（尤其 `eg`/`site` 这类高频更新的字段）。
- 修正：按类分片（`w:dns` / `w:eg` / `w:site`）**并且**每条事实自带 `at`，读时按 `at` 取新（合并语义而非整体替换）。

### D9 TTL 与 cron 节奏踩线

- `blk` TTL 45 分钟、cron 45 分钟一轮 ⇒ 封锁事实在过期边界反复抖动（刚过期就被重新写）。
- 修正：`blk` TTL ≥ 2× cron（90 分钟），或 cron 回到 30 分钟；其余事实同理取 `max(TTL_min, 2×轮询间隔)`。

### D10 探测预算与候选规模不匹配

- 若 `alive` 扩到 32，一轮要「refill ≤6 + 探活 32 + tfb 1」> 48 子请求上限，且并发只有 6。
- 修正：探活分 3 轮（每轮 12 条），并把「回显探测」与「探活」合并（探测目标用回显服务 ⇒ 一次 connect 同时得到「活着」与「出口族」）；预算表写死 `refill 6 + 探活 12 + tfb 6 = 24 < 48`。

---

### D11 `eg` 会变：6 小时 TTL 会让「v4 出口」变成错误事实

- 42 次实测里出现过「同一条中继先 200 后 403」（§13.7 的 193.181.211.185：2/5），说明**出口地址族可能随时间/线路变化**，而 `eg` 的 TTL 是 6 小时 —— 一条已经切到 v6 的中继会在最长 6 小时内仍被当作 v4 优先使用，且因为「v4 优先」它会被**高频选中**，错误被放大。
- 修正（三条一起）：
  1. **失败即复核**：`eg=4` 的中继连续 2 次 `tiny` → 立刻安排一次回显探测（优先级高于「未知」，因为它正在被高频使用）。
  2. **TTL 分层**：`eg` 对「正在被使用的中继」按 1 小时刷新，对「闲置的」才用 6 小时（用的时候才值钱）。
  3. **不信任单点**：选路时 `eg=4` 只作为先验（`prior=0.95`），`p` 仍由个体 `okN/badN` 修正 —— 与 D6 的公式天然一致，不需要额外逻辑。
## 16. KV / DO 额度：现状、重算与优化

### 16.1 现有 KV 键与写节奏

| 键 | 内容 | 写入时机 | 估算/天 |
|---|---|---|---|
| `px:seed` | 节点名字表（≤800） | 最长 90 分钟一次 + 内容变化 | 16 |
| `px:pool:<gen>` | 代际池子 | refill 且 hash 变化 | 5 |

| `users` | 用户记录 | 管理操作 | <5 |
| `rtt:<id>` / `edge:pref` | 调试/偏好 | 变化时 | <5 |
| **合计** | | | **~85** |

### 16.2 若把 facts 放 KV

| 项 | 每天 | 说明 |
|---|---|---|
| facts 写（10 分钟节流 + hash 门） | +140 | 只要 4 类事实都在动就接近这个数 |
| 合计写 | **225** | 额度 1000 时还有 4.4× 余量 |
| 读 | 1/冷启动 ≈ 10k | 额度 10 万，10× 余量 |

**问题**：写额度消耗翻 2.6 倍，而「写」是最紧的额度（1000/天）。流量涨 10 倍时（isolate 10 万）写仍受 1000 限制，但**读**先到顶 —— 那时 facts 反而写不进去。

### 16.3 建议：facts 搬 DO，KV 只留冷数据

| 载体 | 放什么 | 为什么 |
|---|---|---|
| **DO 存储**（`Meter`） | `facts`（dns/eg/site/dead/cap）、计数器 | DO 请求额度 10 万/天，比 KV 写 1000/天 宽 **100 倍**；且可原子读改写，天然解决 D8 的竞争 |
| **KV** | `px:seed`、`px:pool:<gen>`、`users`、`snap`、`usage:snap` | 冷数据，写少、需要跨机房 |
| **Cache API** | `w:1` 世界快照（60 s/colo） | 读 10k → ~500/天，且 KV 读额度不再是瓶颈 |

```ts
// 新增：DO 上的一个端点，一次拿全量事实（冷启动用）
GET  /meter/facts?s=<shard>          → { v, dns, eg, site, dead, cap, at }
// 增量写：只提交变化项，服务端按 at 合并（解决 D8）
POST /meter/facts  { shard, items: [{ k, f: "eg"|"site"|"dns", ... , at }] }
```

预算（改后）：KV 写 ~85/天（不动）、KV 读 ~500/天、DO 请求 ~110/天（探活批 80 + facts 30）。

### 16.4 还能再压的三处

1. **`snap` 与 `usage:snap` 合并**（同一份数据两处写）：写 60 → 30/天。
2. **`rtt:<id>` 移进 DO**（它本来就是按 id 分片的调试数据）。
3. **`edge:pref` 只在有变化时写**（现在已经是变化才写，但要确认没有「空表覆盖」路径）。

**结论**：把 facts 放 DO 之后，KV 侧只承担「冷数据 + 用户数据」，读写在 10 倍流量下都还有 5–10 倍余量；DO 侧 100 倍余量，可以放心把「探测 + 事实」都放进去。

### 16.5 共享与不共享的边界（用户 2026-11-15 拍板）

> 原话：「在不超免费版额度的情况下，可以共享」。

这条拍板解决了 v8 里最关键的一个供给问题：**「哪条中继是 v4 出口」这件事，每个 isolate 都得从零试一遍**。实测 8 条活跃中继里有 **3 条** v4 出口（§13.6），而 v4 出口对 x 类站点 6/6、v6 出口 0–2/5。也就是说池子里的好中继够用，但每条新 isolate 都要靠「8 选 3」的盲抽去撞，撞不中就必然踩 403。

| 数据 | 共享？ | 载体 | 理由 |
|---|---|---|---|
| `dns[H]` 目标的 A/AAAA | **共享** | DO | 客观事实，与谁去连无关 |
| `eg[R]` 中继出口族 | **共享** | DO | **机器属性**：`45.136.117.194` 永远是 v4 出口，不会因 isolate 而变 |
| `blk[H\|R]` A 级封锁 | **共享** | DO | 用户 m13158：「机房级封锁对跨 isolate 没有影响，只要有绝对证据」+ §6 的两批次闸门 |
| `dead[R]` 握手必败 | **共享** | DO | 回自己证书/握手必败是机器属性 |
| `cap[R]` 容量档 | **共享** | DO | 与位置弱相关，作为先验即可（真正排序靠本地 `bps`） |
| `p(host,relay)` 成功率、`ttfb`、`bps` | **不共享** | isolate 内存 | 这些是统计量，且强依赖「本 isolate 看到的路径」；共享会重演 7.57 的「越共享越差」 |
| 选路游标、冷启动钉住 | 不共享 | isolate 内存 | 本来就是探索状态 |

**额度账（共享之后）**：

| 项 | 每天 | 额度 | 余量 |
|---|---|---|---|
| DO 请求：isolate 启动读 facts | ≈ 5 万（按 5 万次启动） | 10 万 | 2× |
| DO 请求：探测写（12 条/轮 × 48 轮） | ≈ 576 | 10 万 | 170× |
| KV 写 | ≈ 85 | 1000 | 11× |
| KV 读 | ≈ 500（Cache API 兜住 world 快照） | 10 万 | 200× |

⇒ **共享是免费的**：真正贵的 KV 写只有 85/天，DO 请求的 5 万/天来自「每次冷启动读一次 facts」，而这一读换来的是「新 isolate 第一条请求就知道哪条中继是 v4 出口」。

**供给推论（这才是 x 类成功率的杠杆）**：

- 现状：每 isolate 8 条活跃中继、其中 v4 出口实测 3 条（37.5%）⇒ 盲选命中 v4 的概率 37.5%，剩余 62.5% 里 v6 出口只有 0–2/5 能过。
- 共享后：`eg` 是全队共享的，**任意 isolate 探到一条 v4 出口，全队立刻可用**。同样的 8 条中继，共享前后差别不是「多几条中继」，而是「每个新 isolate 第一条请求就能直接挑 v4」——盲选 37.5% → **排序后接近 100%**，对应「首次请求就 200」的实测曲线 96–98%（§14）。
- 因此 v8 的 `alive` 目标不是「越多越好」，而是「**保证 v4 出口 ≥3 条在线**」；`eg` 共享让这个目标从「每条 isolate 各自撞运气」变成「全队共同维护」。

**与旧约束的关系**：早期「不跨 isolate 共享统计」的原因（m00676）是「每个 isolate 到同一节点的 RTT 可能差一倍」——那条约束对**延迟/带宽统计**依然成立，本节的共享清单里没有任何延迟或带宽数字。

## 17. 迁移第 1 步施工图：事实层（不改选路）

目标：先把「跨 isolate 的客观事实」落地并跑起来，**选路逻辑一行不动** —— 这样任何问题都能靠 `SC.FACTS=0` 回滚，且收益（`firstTry` 提升）能单独归因。

### 17.1 开关与边界

| 开关 | 含义 | 行为 |
|---|---|---|
| `SC.FACTS = 0` | 关闭 | 不读不写，等同 7.86 |
| `1` | 影子 | 只写、`/health` 可见，但 `decide()` 不读 |
| `2` | 生效（默认） | 读 `eg` / `blk` / `dead`，写全部 |

第 1 步只做 `0 / 1` 两档；`2` 留到第 2 步（读进 `decide()`）。**本步不碰 KV**：写入量维持约 85/天，用来验证 §16 的账。

### 17.2 DO 存储（`Meter` 的 SQLite）

```sql
CREATE TABLE IF NOT EXISTS facts (
  kind TEXT NOT NULL,   -- dns | eg | blk | dead | cap
  k    TEXT NOT NULL,   -- host / relayIP / "host|relay"
  at   INTEGER NOT NULL,
  j    TEXT NOT NULL,   -- 紧凑 JSON，如 {"f":4,"n":2}
  PRIMARY KEY (kind, k)
);
CREATE INDEX IF NOT EXISTS idx_facts_at ON facts(kind, at);
```

- **合并语义（解决 D8）**：`INSERT … ON CONFLICT(kind,k) DO UPDATE SET at=excluded.at, j=excluded.j WHERE excluded.at > facts.at` —— 只有更新的证据才覆盖，乱序到达也不会回退。
- **容量（每 kind）**：`dns 512 / eg 512 / blk 1024 / dead 256 / cap 256`；插入后按 `at` 升序删掉超出部分（同一事务）。
- **单行上限** 128 字节；`j` 里不放注释、不放浮点尾数（`toFixed(2)` 后存字符串）。

| POST | `/meter/facts` | `{ rows:[[kind,k,at,j]] }`，≤64 行/次 | `{ ok, wrote, skipped }`（`skipped` 含 `at` 更旧的） |

## 18. `decide()` 的表驱动测试向量（第 5 步的验收标准）

第 5 步要重写选路，所以先把**行为**定死：下表每一行都是一个「可直接翻译成单测」的用例。约定：

- 先验：`prior(v4) = 0.95`、`prior(v6) = 0.5`（族未知）、先验强度 `α = 4`。
- `p = (okN + α·prior) / (okN + badN + α)`；`transport(tput) = ttfb + 512000 / max(32, bps)`，`transport(lat) = ttfb`；`score = transport / max(0.08, p)`。
- 排序：`score` 升序 → `okN` 降序 → `ip` 字典序（保证确定性，测试可断言具体哪一条）。
- 「有效率」= 不在 `dead`、不在未过期的 `blk`、不在黑名单/冻结。

| # | 输入摘要 | 期望通道 | `why` | 覆盖的规则 |
|---|---|---|---|---|
| 1 | 只有 v6 中继、全无样本 | `r:` 中 ttfb 最小者 | `relay-best` | 永不因「全是 v6」返回空 |
| 2 | v4（无样本，ttfb 800）vs v6（bps 2000 → transport≈800） | **v4** | `relay-best` | 族先验压过速度差 |
| 3 | v4 有 6 次失败（p≈0.35）vs v6 有 6 次成功（p≈0.9） | **v6** | `relay-best` | 个体样本覆盖先验 |
| 4 | 两条都在 `blk`（未过期） | `leastBad` 中的最优者 | `least-bad` | D1：绝不返回空 |
| 5 | 一条在 `dead` | 另一条 | `relay-best` | 机器属性直接排除 |
| 6 | 未知族（无样本）vs 已知 v6（有 3 次成功） | **未知族** | `relay-best` | 探索：未知先验 0.5 > v6 实测仍需样本 |
| 7 | `mode=lat`，v6 bps 极高但 ttfb 2000，v4 ttfb 300 | **v4** | `relay-best` | lat 不看 bps |
| 8 | `preferDirect` 且直连无 `tiny` 记录 | `d` | `direct` | 直连优先 |
| 9 | `preferDirect` 但直连 5 分钟内有 `tiny` | 中继最优 | `relay-best` | tiny 只降权直连 |
| 10 | `relays = []` 且 `cfHost` | `d` | `direct-only` | 没有中继可挑时的兜底 |
| 11 | 唯一一条中继，`dead` 已过期（>30 分钟） | 用它 | `relay-best` | TTL 过期即复活 |
| 12 | `blk` 的 `at` 早于 90 分钟 | 用该中继 | `relay-best` | D9 的 TTL |
| 13 | `tput` 且所有 `bps = 0` | 按 `ttfb` 排序 | `relay-best` | D5 小页面退化 |
| 14 | 两条完全同分 | `ip` 字典序小者 | `relay-best` | 确定性 tie-break |

**必须同时满足的三条不变量**（可写成 property test，随机输入 1000 次）：

1. 返回值永不为 `null`，且 `chan` 一定是「`d`」或一条**在候选中**的中继。
2. 若存在「有效且 `p ≥ 0.8`」的通道，则选中它的 `score` ≤ 任何其他通道 `score` × 1.05（容许 Thompson 抖动）。
3. 不存在「必然失败」的通道被选中：`dead` 命中率 0、未过期 `blk` 命中率 0。

> 这三条比任何具体用例都重要：它们保证重写之后**不会退化成「返回空/返回必败通道」**——而这正是 7.57 那次失败（通配封锁把池子标死）的本质。
### 13.8 验证：钉住 v4 出口后首请求 100%（21/21）

同一时段、同样的请求方式（每个新进程 1 条请求，目标 x.com），只把中继钉在 §13.6 实测的三条 v4 出口上轮转：

| 策略 | 200 | 非 200 | 失败 | 成功率 |
|---|---|---|---|---|
| 盲选（默认策略） | 8 | 11 | 1 | **40%** |
| 钉住 v4 出口（3 条轮转） | **21** | 0 | 0 | **100%** |

这就是 v8 的核心论据：**不需要更多中继、也不需要更好的带宽，只要「知道哪几条是 v4 出口」并把它们优先**，x 类站点的首请求成功率就能从 40% 拉到 100%。`eg` 共享（§16.5）是把这条从「每条 isolate 各自撞」变成「全队都知道」的机制。

## 19. 怎么判定「IP 级封锁」（v4 / v6），且不碰业务逻辑

这一节回答一个具体问题：**看到一次 4xx，凭什么说「这条出口 IP 被这个站点封了」？** 而且判定过程不能改变任何业务响应。

### 19.1 四件事必须分开，混在一起就会误伤

| 现象 | 真实含义 | 该怎么处理 | 能不能进封锁表 |
|---|---|---|---|
| 业务 4xx（401/403/404/415/429，带 1KB+ 站点页） | 目标说「你这个请求不对」 | **原样透传**，最多按状态码退避 | ❌ 永不 |
| 族级拒绝（站点不接受 v6 来源） | 站点策略，与具体 IP 无关 | 降权 v6 出口（`p6`），**不排除** | ❌ 只进统计 |
| 单 IP 封锁（这条出口被该站点拒） | 出口 IP 进了该站点的黑名单 | 只排这**一条** `(host, relay)`，90 分钟 | ✅ 需 A 级证据 |
| 中继自身坏（回自己证书/垃圾页/握手必败） | 中继坏了，与站点无关 | 进 `dead`，30 分钟 | ✅ 但记 `dead` 不记 `blk` |

我们实测过的四个真实输入，正好落在四个格子里：

| 输入 | 大小 | 判定 |
|---|---|---|
| `api.github.com` 经任意中继 → **415** | 1277 B，`bigTypical≈1277` ⇒ 比值 1.0 | 业务 4xx → 只计数 |
| `x.com` 经 v6 出口 → **403** | **737 B**，`bigTypical≈45 KB` ⇒ 1.6% | 疑似族级/单 IP，需差分 |
| `x.com` 经 v4 出口 → 200 | 45 KB | 正常 |
| `89.22.227.132` → 证书不匹配 | —— | `dead`（中继自身坏） |

### 19.2 判据只用「结构」，不读内容

**核心：生产环境不读响应体**（隐私 + 普适性 + 我们只看得到密文这件事的另一面：读了也没法泛化）。所以判据只有三个结构量：

```ts
// ① 是不是「小响应」：两个条件同时满足（§13.7 的 737B 拒绝页正是这么抓到的）
const tiny = down > 0 && down <= 2048 && down < 0.2 * (bigTypical[host] || 16384);

// ② 有没有「同窗口的对照成功」：另一条通道在同一 120s 窗口里拿到 ≥20KB
const hasBigPeer = (host, chan, now) =>
  others(host, chan).some((c) => row(host, c).bigAt > now - 120_000 &&
                                   row(host, c).bigTypical >= 20480);

// ③ 两批独立：同一结论在 ≥60s 之后再次出现
const confirmed = second(host, chan, now);
```

`tiny + hasBigPeer + confirmed` 三条同时成立，才允许写 `blk[host|relay]`。

### 19.3 v4 与 v6：判定方式的根本区别

**直连腿：族可控，所以能做「同窗口 A/B」** —— 这是唯一能干净判定「站点是否拒绝 v6」的地方：

```
同一 host、同一 120s 窗口：
  legA = connect(A 记录 → IPv4 字面量)   → 200 / ≥20KB
  legB = connect(AAAA → IPv6 字面量)     → 4xx / tiny
⇒ 站点级事实：site[host] 的 p6 低（族级拒绝），写 DO，6h 衰减
⇒ 若两条腿都 tiny ⇒ 站点级封锁，**不写任何封锁**（换出口重采）
⇒ 若 legA 也 tiny ⇒ 没有对照，弃权
```

**中继腿：族不可控，所以必须「先测族、再做差分」**：

```
第 1 步：eg[relay] = 回显（icanhazip）→ v4 | v6      // §13.6，一次 connect + 一次 GET
第 2 步：同窗口，relay 打 host → tiny
        且另一条 eg=4 的中继打 host → 2xx ≥20KB
        且 60s 后重复一次
⇒ 单 IP 封锁：blk[host|relay] = now（90 分钟）
```

**v4 与 v6 的判据完全对称，唯一差别是「先验」**：`prior(v4)=0.95`、`prior(v6)=0.5`。因为实测 v4 出口 6/6、v6 出口 0–2/5（§13.1/§13.6），v6 的每一次 tiny 需要**更多**证据才下结论（这也是为什么 v6 的 `blk` 要两批、而 v4 的可以一批加复核）。

### 19.4 证据分级与落库

| 级 | 构成 | 落库 | 生效方式 |
|---|---|---|---|
| **A** | 两批（≥60s），每批有 `tiny` 腿 + 同窗口 `≥20KB` 对照腿 | DO `blk` / `eg` / `dead` | 排序时排除 / 降权 |
| **B** | 单批差分，或同一 `(host, relay)` 连续 2 次 `tiny` | isolate 内存（`markNeg`） | 只降到队尾，10 分钟 |
| **C** | 单次 4xx；429；带站点页的 403；证书错误 | 计数器 | 不改变任何行为 |

**永不进 A 级的三种输入**：直连腿的 4xx（CF 边缘出口身份不可归属）、全通道 4xx（站点级，不是出口级）、429（限流，只需要退避）。

### 19.5 「不影响业务逻辑」的六条工程约束

1. **事实只影响排序，不影响返回**：`decide()` 的返回值永远是「`d` 或某条候选中继」，任何事实缺失/损坏都退化成今天的默认行为。
2. **热路径零 I/O**：facts 是 isolate 内存快照（启动读 1 次 + 10 分钟后台刷新），`decide()` 里不 `await`、不读 KV、不读 DO。
3. **写是旁路**：`POST /meter/facts` fire-and-forget，失败只加 `factErr` 计数，绝不影响请求。
4. **永不返回空**：所有候选都被 `blk`/`dead` 排掉时走 `leastBad`（§18 不变量 1）。
5. **可自愈**：5% 概率对「已封锁的 `(host, relay)`」复探一次，连续 2 次成功即解除——避免把一条好中继永久焊死（7.57 的教训）。
6. **判定本身要花额度**：每轮最多 2 条 connect 用于差分、每天每站点最多 3 批（现有 `tf` 预算不变）；不用新额度。

### 19.6 我们为什么有把握「不误伤业务」

用四个实测数字验证这条链：

| 站点 | 响应 | `tiny` 判据 | 结论 |
|---|---|---|---|
| `api.github.com` | 415 / 1277 B，`bigTypical≈1277` | `1277 ≤ 2048` ✅ 但 `1277 < 0.2×1277` ❌ | **不算 tiny** → 只计数，永不封锁 |
| `example.com` | 200 / 932 B | 比值 ≈1 ❌ | 正常小站，不误判 |
| `github.com` | 200 / 120 KB | 远超阈值 ❌ | 正常 |
| `x.com`（v6 出口） | 403 / **737 B**，`bigTypical≈45 KB` | 绝对 ✅ + 相对 1.6% ✅ | 疑似封锁 → 进差分 |

也就是说：**业务 4xx 因为「相对自身典型尺寸不算小」而天然逃过 `tiny`**，不需要任何站点名单，也不需要读内容。

## 20. 北极星指标 `firstTry` 与冷 isolate 自愈

### 20.1 指标定义（两个数，不能只报一个）

我们**唯一能观测到的"用户成功"代理量是响应字节数**，而字节数阈值是站点相关的：x.com 首页 45 KB、`github.com` 120 KB、`example.com` 932 B、封锁页 737 B。任何单一阈值都会说谎：

- 只看 `down > 0` → 把 737 B 的封锁页算成功（虚高）；
- 只看 `down >= 4096` → 把正常的 932 B 小站算失败（虚低）。

所以 `firstTry` 必须报**两个数**，并且用它们之间的差来定位问题：

```
firstTry   = 第 1 条连接就 down > 0 的 isolate 占比        // 连通率（含封锁页）
firstPage  = 第 1 条连接就 down >= 4096 的 isolate 占比     // 拿到真页面
gap        = firstTry - firstPage                          // 被"小响应"吃掉的差值
```

- `gap` 大 ⇒ 大量连接落在封锁页/错误页（这正是 7.86 的形态：`firstTry` 约 0.95、`firstPage` 约 0.40）；
- `firstTry` 与 `firstPage` 都低 ⇒ 问题是**连不上**（中继挂死/超时），不是被拒。

计数按 isolate 计（不是按请求），每个 isolate 只统计**前 3 条用户连接**：

```ts
// src/core/state.ts
S.ftN = 0;        // 已结算的用户连接数（封顶 3）
S.ftFirst = 0;    // 第 1 条连接就命中的次数（down > 0）
S.ftPage = 0;     // 第 1 条连接就拿到页面的次数（down >= 4096）
S.ft3 = 0;        // 前 3 条内拿到过页面的次数（用户"刷新两次能开"的部分）
S.ftIso = 0;      // 观察到的 isolate 数（有 ≥1 条连接结算即 +1，封顶 1）
```

`/health` 读数：`{ firstTry: ftFirst/ftIso, firstPage: ftPage/ftIso, within3: ft3/ftIso, n: ftN }`。

**为什么按 isolate 计而不是按请求计**：热态 isolate 会把总体成功率拉到 92–96%，把冷启动的洞完全稀释掉；而用户感受到的正是"新连接的第一下"。

### 20.2 冷 isolate 自愈（三档）

| 档 | 条件 | 行为 | 期望 |
|---|---|---|---|
| **warm** | `S.alive` 与 facts 快照都在 | 正常排序（`eg` 先验 + `p` 修正） | 95%+ |
| **cold+facts** | isolate 新起，但 DO 里有 `eg` | **最多等 200 ms** 读一次 facts 快照再拨号 | ~90% |
| **cold+empty** | 新 isolate 且 DO 里也没有 `eg` | 不等待，盲选；同时在后台发 1 条回显探测，结果写 DO | 40% → 下一条 90% |

**为什么值得为一次 DO 读阻塞 200 ms**：冷启动的 TTFB 已经是 2.5–3.3 s，200 ms 是 8%；换来的是首请求 40% → 90%。而 DO 读额度是 10 万/天，冷启动 ≈5 万/天（§16.5），**在额度内**。

**注意不能无限等**：`Promise.race([readFacts(), 200ms])`，超时就用「盲选 + 后台补探测」，绝不让 DO 抖动变成用户等待（7.81 的教训：`ensurePool` 就是这么把 p50 拖到 6.4 s 的）。

### 20.3 数值模型（用实测常数外推）

实测常数：`P(ok|v4)=0.95`（v4 出口 21/21 与 6/6）、`P(ok|v6)=0.125`（2/16）、活跃中继里 v4 占 37.5%（3/8）、`dead` 12.5%（1/8）。

| 情形 | 首请求期望成功率 |
|---|---|
| 盲选（现状 7.86） | 0.375×0.95 + 0.5×0.125 + 0.125×0 = **0.42**（实测 8/20 = 0.40 ✅） |
| `eg` 已知、v4 可用 | **0.95**（实测 21/21） |
| `eg` 已知、v4 全死（退 v6，试 1 次） | **0.125** |
| 同上，但 v6 试 2 次 | 1−0.875² = **0.23** |
| `eg` 未知（cold+empty） | 0.42，下一跳起 0.95 |

模型给出两个可验证的预言：① 只要池子里还有 1 条活的 v4 出口，`firstTry` 就该≥0.9；② **v4 全死时重试几乎无用**（23%），此时该做的是「别浪费用户时间」——直接回直连腿（§7.3）而不是连试两条 v6。

### 20.4 验收标准（迁移后必须同时满足）

| 指标 | 现状（7.86） | 目标 |
|---|---|---|
| `firstPage`（cold+facts） | 0.40（= 盲选命中率） | **≥ 0.85** |
| `firstPage`（warm） | 19/20 = 0.95 | **≥ 0.95**（不得退化） |
| `firstTry`（连通率，含封锁页） | ~0.95 | ≥ 0.98 |
| `gap`（连通 − 真页面） | ~0.55 | **≤ 0.10** |
| `?bench=`（源站腿） | 147 MB/s | ≥ 100 MB/s（不得退化） |
| 业务 4xx 误封 | 0（§19） | **仍为 0** |
| KV 写/天 | 85 | ≤ 100（§16.5） |

任何一项没达标，就不该继续往第 2 步迁移——**先修指标，再加功能**。

### 20.5 `readFacts` 的接口契约（三态 + 降级阶梯）

```ts
/** 事实快照：只有"客观、可共享"的那几类（§16.5），不含任何统计量 */
export interface FactsSnap {
  v: number;                  // 版本号，不匹配就整份丢弃
  at: number;                 // 快照时刻
  eg: Record<string, 4 | 6>;  // 中继 → 出口族
  blk: Record<string, number>;// "host|relay" → 写封锁的时刻
  dead: Record<string, number>;
  dns: Record<string, 0 | 4 | 6 | 1>; // host → 0 无记录 / 4 纯 v4 / 6 仅 v6 / 1 双栈
}

/** 只读一次 DO；超时/失败返回 null，永不 throw，永不重试第二次 */
export async function readFacts(env: Env, budgetMs = 200): Promise<FactsSnap | null>;
```

契约四条：

1. **全有或全无**：要么返回完整快照，要么返回 `null`；**不做部分应用**——半张表会让排序在两次请求之间抖动（7.57 的另一种形态）。
2. **只在冷 isolate 的第 1 条连接上阻塞**：`budgetMs = 200`，之后所有连接都读内存快照（`S.facts`），热路径零 I/O。
3. **每 isolate 每 10 分钟最多读 1 次**，失败后 60 秒内不再重试（避免 DO 抖动放大成额度浪费）。
4. **陈旧但可用**：快照超过 1 小时仍会被使用，只是标记 `stale: true`——因为出口族是小时级稳定的（§13.9），而"没有 facts"的代价（40% vs 95%）远大于"用了 1 小时前的 facts"。

降级阶梯（每一级都不改变业务响应）：

| 情况 | `readFacts` 返回 | `decide()` 行为 | 用户可见影响 |
|---|---|---|---|
| 内存有快照且 <10 min | 快照 | 正常排序（`eg` 先验 + `p` 修正） | 无 |
| 内存无快照，DO 200 ms 内返回 | 快照 | 同上 | 首字节 +20–50 ms |
| DO 超时/500 | null | 盲选 + 后台补一次回显探测 | 首请求约 40%，下一条恢复 |
| 快照版本号不符 | null | 同上 | 同 7.86 现状 |
| 快照 >1 h | 快照（`stale`） | 同上（仍需个体 `okN/badN` 修正） | 极小 |

### 20.6 `firstTry` 计数器的准确插入点

**唯一结算点是** `src/proxy/connection.ts` 的 `flush(closing?: boolean)`（第 238 行起）。那里已经具备全部三个观测量：
```
this.failed   // 中途断流（pipeBack 的 catch 置位），不算成功
this.down     // 下行字节数
this.node     // 有值 = 走中继；空 = 直连
```
插入位置：紧跟现有 `cnt(this.node ? "node" : "direct");`（第 301 行）之后、`nsOk` 之前：

```ts
// firstTry 只统计"用户连接"（有 host），不统计探活/内部隧道
if (this.host && S.ftN < 3) {
  const ok = !this.failed && this.down > 0;
  const page = ok && this.down >= 4096;
  if (S.ftN === 0) { S.ftIso = 1; if (ok) S.ftFirst += 1; if (page) S.ftPage += 1; }
  if (page) S.ft3 = 1;                 // 前 3 条内拿到过页面
  S.ftN += 1;
}
```

三个坑（都是我们踩过的同类）：

- **不要用 `this.ttfb > 0` 当成功判据**：直连失败时 `ttfb` 也可能是 0 而 `down > 0`（拿到了错误页）。
- **不要把探活/内部隧道算进去**：它们的 `host` 为空或为回显服务，会把 `firstPage` 拉高。
- **不要在 `pipeBack` 里计数**：那里会按块触发，一条连接会加多次。

### 20.7 指标被"做好看"的三个风险

1. **只优化 `firstPage` 会偏向大页面站点**：应当在 `/health` 同时看 `gap`，并在 sim 里按场景分组（小页面 / 大页面 / 封锁页）分别汇报。
2. **按 isolate 统计天然有幸存者偏差**（活得久的 isolate 才被观察到 3 条以上连接）：所以 `/health` 的 `n` 也要暴露，别只看比例。
3. **`ftN < 3` 的 isolate 会影响可读性**：低流量时几乎每个 isolate 只有 1 条连接，此时 `firstPage` 就等价于"最后一次单请求是否成功"——这正是我们要的，但要写明它不是长期平均。
