# 架构重设计 v8

> 目标：在免费计划额度内，让「吞吐 / 速率」两种模式都能稳定路由到当前最优通道，同时能给出**有绝对证据的 IP 级封锁判定**，且不误伤业务 4xx、不依赖任何站点特化。
> 本文只写设计，不含实现。当前线上版本 7.86，源 88 文件 / 12907 行。

## 0. v8.1 修订（由实测推翻的三条旧假设）

| 旧假设 | 实测结论 | 影响 |
|---|---|---|
| 「v6 出口 → 目标必拒」 | 同一台 v6 出口中继、同一分钟：**2/5 成功**（出口恒为 `2a0f:f01:208:3ba::`） | 地址族不是开关，而是**成功率折扣**：`p6 ≈ 12.5%`（2/16） |
| 「可以把中继改成 v4 出口」 | 递 v4 字面量给中继无效：这些 proxyip **按 ClientHello 的 SNI 自己解析**（SNI 换成别的域名，回的就是那个域名） | 中继腿的族**不可控**，只能在「选哪条中继」上做 |
| 「中继探测的结论可以直接套用到用户连接」 | CF 托管站点会**透传发起方身份**：DO 探测是 DO 的出口，用户连接是客户端/中继的出口 | 直连腿的探测结论不可跨主体复用；中继腿可以（R 是第三方） |

另外两条新增事实：
- **出口族按连接抽签**：同一个 Worker 的不同连接可能拿到不同族的出站地址 → 直连腿必须自己钉族。
- **DNS 有 AAAA ≠ 接受 v6**：x.com 有 AAAA 但 v6 通过率 12.5%，所以「站点族能力」与「站点对 v6 的接受度」是两件事，必须分别记。

## 2. 设计目标 / 非目标

### 目标
1. **单一真值**：一条通道对一个站点的结论只有一个来源。
2. **证据可分级**：任何持久化结论都必须能追溯到「哪次对比、谁做的对照」。
3. **冷启动可用**：新 isolate 靠 KV 事实立即避开已知坏通道，不必试错。
4. **额度内运行**：6 并发 `connect()`、48 子请求/轮、DO CPU 几十毫秒。
5. **零站点特化**：代码里不出现任何目标域名（现状已验证 `dist` 命中 0）。

### 非目标
- 不追求「每次都是最优」（物理上做不到：冷启动、出口族抽签、客户端路径抖动）。
- 不做 userland TLS（7.69 已整体删除，免费计划装不下握手）。
- 不做站点规则分流（`DOMAIN-SUFFIX` 之类）。
- 不追求「让 v6 出口对某站点 100% 通过」——那是站点侧的行为，我们只能估计 `p6` 并据此排序。

## 4. 两个核心抽象

### 4.1 `ChanTable`（isolate 内存，唯一的内存真值）

```ts
// 键：`${host}|${chan}`，chan = "d"（直连）| "r:<relayIP>"
interface ChanRow {
  bigAt: number;      // 最近一次拿到「本站点典型尺寸以上」的响应
  tinyAt: number;     // 最近一次拿到 tiny 响应（§19.2：down ≤ 2048 且 < 0.2×bigTypical）
  failAt: number;     // 最近一次拨号/握手中断
  ttfb: number;       // EWMA 首字节 ms
  bps: number;        // EWMA 字节/毫秒（down ≥ 5×TICK 才采；≥1MB 权重更高）
  okN: number;        // 成功次数（半衰期 6h）—— 用来算 p(host, chan)
  badN: number;       // 失败次数（同上）
  bigTypical: number; // 该站点「正常响应」尺寸的 EWMA/max，用来判 relative-small
  n: number;          // 样本数（置信度用）
}
```

- 失效：`bigAt/tinyAt` 30 分钟，`failAt` 10 分钟，性能字段 10 分钟滑动，`okN/badN` 半衰期 6 小时。
- 成功定义（**普适性的关键**）：拿到完整响应即 `ok`（`down > 64`）。业务 4xx（如 `api.github.com` 的 415 + 1277B）算成功，不算失败。
- 失败定义：`down === 0` 或 `down <= 64`（拒绝页）或拨号/握手中断。
- 写入：连接结束时一次（`connection.flush` → hook）。
- 读取：`policy.decide` 里按 host 取候选行的切片。

### 4.2 `Facts`（DO / SQLite，跨 isolate 的客观事实；施工图见 §17.2）

```ts
interface Facts {
  v: 2;

  // ① 目标地址族能力：客观、可复现、写入即定论   【共享】
  dns: Record<string, { a: 0 | 1; aaaa: 0 | 1; at: number }>;   // "host"

  // ② 中继出口族：回显为强证据（egress 探测）      【共享】
  //    —— 这是 x 类站点成功率的关键事实：v4 出口 6/6，v6 出口 0–2/5（§13）
  eg: Record<string, { fam: 4 | 6; at: number; n: number }>;    // "relayIP"

  // ③ 站点 × 中继通过率：EWMA 软后验（255 制），不是布尔   【共享（§22）】
  //    键 = "host|relayIP"；q/n 见 §22.4。族（eg）只做先验，个体样本才是主体（D6）
  ps: Record<string, { q: number; n: number; at: number }>;

  // ③b 封锁事实：**必须带中继维度**（D1）。键 = `${host}|${relayIP}`；值为证据时间  【共享】
  //     直连通道永不进这张表（CF 边缘出站身份不可归属，见 §6）
  blk: Record<string, number>;

  // ④ 中继自身健康与容量
  dead: Record<string, number>;   // relayIP → 最近一次握手必败
  cap: Record<string, number>;    // relayIP → 0.5..2.0 相对容量（§24 R2：比值，不是 KB/s）
}
```

- **存储**：DO `Meter` 的 SQLite 表 `facts(kind,k,at,j)`（§17.2），**不进 KV**。早期草案把 facts 与 seed/pool 合并成 `world` 单键，已被 §16.3 的额度账推翻——真正紧的是 **KV 写 1000/天**，而 DO 请求有 10 万/天。
- **上限（每 kind）**：`dns 512`、`eg 512`、`blk 1024`、`dead 256`、`cap 256`、`ps 512`，超限按 `at` 升序淘汰。
- **TTL**：`dns` 24h（DNS 结果很少变）；`eg` 6h（在用的缩到 1h，D11）；`ps` 45 分钟（软折价，每次连接都会更新）；`blk` **90 分钟**（≥ 2× cron 间隔，D9；硬排除，需 A 级双批证据）；`dead` 30 分钟；`cap` 24h。**`blk` 与 `ps` 是两种不同寿命的事实**：前者「别再用这条通道」，后者「这条通道现在大概多能成」。
- **写纪律**：只写强证据（§6）；脏标记 + 最多 10 分钟一次 + 内容 hash 变化才写 → 每天 < 150 次（额度 1000）。
- **读纪律**：只在**冷 isolate 的第 1 条连接**读 1 次（`GET /meter/facts?since=`，四条契约见 §20.5），之后每 10 分钟刷新；读失败一律降级为「无事实」，不影响选路。
- **不存**：任何「站点级二元封锁」（`blk` 是 `host|relay` 且只有 A 级可写）、任何「v6 不可用」的族级结论（只存 `b6/n6` 概率）、任何与 isolate 相关的延迟样本。

#### 为什么用 Beta 后验而不是布尔

v6 出口对某站点不是「能用/不能用」，而是**每次请求抽签**（同一出口 2/5）。用 `b6/n6` 记成败，选路时按 `1/p6` 折价，既能保住「v6 节点质量好时仍可用」，也不会让请求反复落在 12.5% 的那一档上。`n` 小的时候后验接近先验（0.5），自然带有探索性。

## 6. 事实写入协议：分级 + 闸门

### 6.1 五类事实与证据等级

| 事实 | 键 | 等级 | 判定条件 | TTL |
|---|---|---|---|---|
| 地址族能力 | `dns[H]` | **A（客观）** | DoH 同时查 A / AAAA，两次（≥10 分钟间隔）结果一致 | 24h |
| 中继出口族 | `eg[R]` | **A（回显）** | 经 R 访问回显服务，两次拿到同族地址；或「配对：R 上 200 + 另一 R 上恰 4 字节 `IPv6`」 | 6h |
| 站点 × 族成功率 | `site[H].b4/n4`、`b6/n6` | **B（统计）** | 同小时窗口内，v4 腿与 v6 腿各 ≥4 次配对样本 | 6h 衰减 |
| 站点 × 中继封锁 | `blk[H|R]` | **A（差分）** | 同批内 R 得 403/451（≤32B），另一通道 2xx 且 ≥20KB；**两个独立批次**（间隔 ≥60s）；直连腿不参与 | 90 分钟（≥2×cron） |
| 中继自身坏 | `dead[R]` | **A（客观）** | 回自己的页面 / 证书不匹配 / 握手必败 | 30 分钟 |

> **没有「站点对 v6 = 封锁」这种二元事实。** v6 只影响 `p6` 的数值，不产生禁止清单。

### 6.2 单一写入口

```ts
/** 把一条候选事实提交给事实库；返回是否真的写入（弃权 = false）。 */
function commitFact(f: Facts, kind: Kind, key: string, ev: Evidence, now: number): boolean;
```

任一条件不满足即返回 `false`（弃权不写），并计入 `/health` 的 `factSkip` 分类。必须覆盖的 10 条拒绝路径：

1. 只有一个批次（缺第二次确认）
2. 同批没有 2xx 对照（做不出差分）
3. 对照腿本身是 4xx（分不清站点级）
4. 响应是 429
5. 响应是 1.2KB 的业务页（不是封锁页）
6. `eg` 事实已过期 1.5h（对照腿的族不可信）
7. 两个批次结论相反
8. 中继出口族未知（`eg` 缺失）
9. 参与的是直连腿（身份不可归属）
10. 全部满足 → 写入（唯一返回 `true` 的用例）

### 6.3 为什么这样切

- **直连腿的结论不进 KV**：直连时目标看到的是 CF 边缘身份（对 CF 托管站点还会透传客户端 IP），同一秒不同连接可能拿到不同身份 —— 结论无法归属到稳定对象。
- **中继腿可以进 KV**：R 是第三方 TCP 中继，探测与用户流量里目标看到的都是 R 的出口地址，所以「R 被该站点拒绝」是关于 R 的客观事实。
- **DNS 事实独立于观测**：它是「目标有没有 v4/v6 地址」的客观答案，与谁去连无关，因此最稳定、TTL 最长。
- **成功率只进统计字段**：二元的 `blocked` 会永久缩小可用池（7.57 实测：通配封锁把中继标死后成功率从 95% 掉到 10%）。

## 7. 选路算法

```ts
function decide(inp: DecisionIn): Choice {
  const f = facts.snap();                    // 启动读一次，之后 10 分钟刷新
  const st = f.site[inp.host];
  const p4 = st && st.n4 >= 4 ? st.b4 / st.n4 : 0.95;   // 先验：v4 很少被站点拒
  const p6 = st && st.n6 >= 4 ? st.b6 / st.n6 : 0.5;    // 先验：未知不折价

  // ① 硬过滤：只排「客观必败」的**单条**通道（D1：blk 必须带 relay 维度）
  const alive = inp.relays.filter((ip) =>
    !isBlacklist(ip) && !isFrozen(ip) && !f.dead[ip] && !f.blk[inp.host + "|" + ip]);
  const cands = alive.length ? alive : inp.relays;      // 全被排掉时绝不返回空

  // ② 单条通道的成功率：共享的 ps 做先验，本地样本（若有）叠在上面
  //    §22 的仿真：短命 isolate 里本地 p 只有 1–3 个样本，效果等于先验（C≈B），
  //    所以先验必须来自共享表，本地样本只是补充。
  const pOf = (ip: string): number => {
    const sh = f.ps[inp.host + "|" + ip];
    const row = chan.get(inp.host, ip);
    const ok = row?.okN ?? 0, bad = row?.badN ?? 0;
    const a = 4;                                        // 先验强度：4 个等效样本
    const prior = sh && sh.n >= 2 ? sh.q / 255
                : f.eg[ip]?.fam === 4 ? p4 : f.eg[ip] ? p6 : 0.5;
    return (ok + a * prior) / (ok + bad + a);
  };

  // ③ 代价：传输代价 / 成功率（两个维度、两个衰减率，互不污染）
  const score = (ip: string): number =>
    transport(inp.mode, perf.get(inp.host, ip)) / max(0.08, pOf(ip));

  // ④ 直连腿：能直连就直连（懒加载族绑定见 §7.1）
  if (preferDirect(inp) && !chan.tinyRecently(inp.host, "d")) return { chan: "d", why: "direct" };

  // ⑤ 中继：score 最小 + Thompson 探索（样本少者自动获得探索）
  const pick = thompson(cands.map((ip) => ({ ip, c: score(ip), sd: sdOf(ip) })));
  return pick ? { chan: { kind: "r", ip: pick }, why: "relay-best" }
              : { chan: leastBad(inp), why: "least-bad" };
}
```

**模式差异**：

| 模式 | `transport()` | 说明 |
|---|---|---|
| `tput` | `ttfb + 512KB / max(32KB/s, cap×64KB/s)` | 容量用**共享的相对值** `cap`（§24 R1 噪声门通过才写）；无 `cap` 或站点页 <40KB 时退化为 `ttfb + 200`（小页面上吞吐无意义） |
| `lat` | `ttfb` | 只关心首字节 |

**两个维度必须分开**（这是同时满足「x 类成功率」与「站点特定吞吐优化」的核心）：

| 维度 | 键 | 采样来源 | 衰减 | 作用 |
|---|---|---|---|---|
| `transport` | `host × relay` | 成功传输的 `ttfb` 与 `bytes/ms` | 10 分钟 | 「谁更快」= 站点特定优化 |
| `ps` | `host × relay`（族做先验） | 完整响应 vs tiny 响应（§19.2） | 45 分钟 | 「谁能过」= x 类保护 |

**防污染铁律**：`tiny` 响应**绝不写 `transport` 样本** —— 403 只要 80ms，写进去会让「越坏越快」（7.83 踩过这个坑）。`tiny` 的判据是 §19.2 的 `down ≤ 2048 且 < 0.2×bigTypical`，**不是**早期的「≤64B」：x 的封锁页已经变成 737B HTML。

**冷启动**：共享的 `cap` 做容量先验、`ps` 做成功率先验（§22/§24）；`dead` / `blk` 排除单条通道；族先验 `p4/p6` 只在 `ps` 样本不足（`n < 2`）时生效。

**探索**：保留 5% 概率选「未知」通道，避免事实过期后永远不验证。

### 7.1 直连腿的地址族（懒绑定，不用 Happy Eyeballs 预热）

直连腿是**我们自己的 `connect()`**，所以族可控 —— 这是 v8 里唯一能钉族的地方。但**不要**在 happy path 上先查 DNS 再拨（那会把 20–50ms 加到 TTFB 上，且双栈时要吃 2 个 connect）。

```
① 直接按域名 connect（不查 DNS、不并发）
② 成功 → 记 ok；失败或拿到 tiny 响应（§19.2）
     → 查 A / AAAA（缓存 24h）
       ├─ 只有 A    → 用 IPv4 字面量重试一次
       ├─ 只有 AAAA → 用 IPv6 字面量重试一次
       └─ 双栈      → IPv4 先试；失败再用 IPv6 重试一次
```

| A | AAAA | 只在这种情况才需要 |
|---|---|---|
| 有 | 无 | v6-only 不可能，直接 v4 |
| 无 | 有 | v6-only 站点：**必须 v6**，绝不强制 v4 |
| 有 | 有 | 双栈：v4 先，失败退 v6 |

- 只有在「已失败」时才用字面量重试，因此**好路径零额外延迟、零额外 connect**。
- 族序可由 `p4/p6` 调整（并列时 v4 先）；DNS 结果缓存在 `dns[H]`，24h，失败也缓存 5 分钟（避免反复查）。
- 由于只在失败时重试，这条逻辑最多让一条请求多花一次拨号，而不是让每次请求都多花。

### 7.2 中继腿的地址族（不可控，只能选）

- proxyip 按 **ClientHello 的 SNI** 自己解析目标，递 v4 字面量无效（实测：SNI 换成别的域名，回的就是那个域名的页面）。
- 所以中继腿只能做两件事：① 优先 `eg=4` 的中继；② `eg=6` 的中继按 `1/max(0.15, p6)` 折价。
- **永不硬封**：`eg=6` 的中继在「没有 `eg=4` 可用」时仍会被选中（探索项），否则池子会缩到 1/8。

### 7.3 v4 出口保底（供给规则，不是选路规则）

实测（§13.1 / §13.6）：8 条活跃中继里 **3 条是 v4 出口**（37.5%），而 v4 出口对 x 类站点 6/6、v6 出口 0–2/5。也就是说 **v4 出口其实够用，问题在于「不知道是哪三条」** —— 不共享时每个新 isolate 只能盲抽（命中 37.5%），共享 `eg` 之后同样的 8 条就能稳定先挑 v4。这条规则放进调度而不是 `decide()`：

```
每轮 cron：
  1. 统计 eg=4 的活跃中继数 v4n
  2. if v4n < 3:  把本轮探活预算的 2/3 花在「eg 未知」的中继上（回显探测）
     else:       按「最久未探」均摊
  3. 任何中继的 eg 探测结果**立刻写 DO**（共享），不等本轮结束
```

- 目标值 **3 条**：实测曲线（§14）里 1 条 v4 ≈ 90%、3 条 ≈ 96–97%、≥5 条 ≈ 98%；当前池子刚好 3 条，所以 v8 的增量收益主要来自「**把这 3 条认出来并共享**」，而不是「捞更多中继」。
- 为什么「未知优先」而不是「最久未探优先」：`eg` 是机器属性、6 小时才过期，未知样本的边际价值最高；而已知 v6 的中继再探也不会变成 v4。
- 为什么写 DO 而不是攒批：isolate 平均寿命只有几分钟（低流量时几乎每条请求都是新的），攒批等于把这轮发现丢掉。

## 8. 预算与配额

单轮 48 子请求、6 并发 `connect()`：

| 用途 | 预算 | 说明 |
|---|---|---|
| 池子准入（探活节点） | 32–40 | 节点是 WS 端点，决定基础可用性 |
| 审计探测（tfb 批次） | 6–8 | 每批 1 个 DO 请求 + 3 条 connect |
| 退款/重试 | 4 | `refund` 池 |
| 订阅/健康检查 | 0 | 客户端侧 |

**并发闸门**：任何时刻「竞速/探测」占用的 connect ≤ 2（给真实流量留 4）。**按波次计，不是按连接计**：一波用户连接最多 2 次探测，超出的连接直接用事实里最稳的那条，不再 probe（§32 实测：40 并发下把 p95 从 675 ms 压到 250 ms；名额才是并发第一资源，不是 DO 读）。

### 8.1 额度账（免费计划）

| 额度 | 上限 | 现状消耗 | v8 设计 |
|---|---|---|---|
| Worker 请求 | 10 万/天 | 随流量 | 不变 |
| KV 读 | 10 万/天 | 每次 isolate 启动 2 次（`px:seed` + `px:pool:<gen>`） | **1 次**（`w:1` 只含 seed + poolGen + pool；facts 另走 DO） |
| **KV 写** | **1000/天** | ~110（seed 90 分钟一次 + pool 换代） | **≤150**（合并 cron 写 + 内容 hash 变化才写） |
| DO 请求 | 10 万/天 | ~50（30 分钟一轮 tfb） | **≤80**（45 分钟一轮、每批带 3 个 host） |
| KV 存储 | 1 GB | 60 KB | <150 KB |

- **能撑多少 isolate**：启动读 = 1 次时，KV 读额度 → **10 万 isolate 启动/天**（此时先撞 Worker 请求额度，不再撞 KV）。v8 朴素做法（facts 独立键 + 10 分钟刷新）是每次启动 3 读 → 3.3 万，**比现在倒退**，所以必须走单文档。
- 数据面连接**不读 KV**（`readStatsCached` 只在订阅/admin 路径），这一条是能撑住的前提。

### 8.2 world 单文档

```ts
// KV 键 w:1：只放**冷数据**（事实见 §16.3，改由 DO 承载）
interface World { v: 2; seed: Seed[]; poolGen: string; pool: string[]; at: number }
```

六条压缩（对应上表）：
1. seed / pool 合并为 `w:1`；facts 走 DO（§16.3）：启动仍是 **1 次 KV 读 + 1 次 DO 读**。
2. facts 用短键（host 取 6 字节 hash、数组下标代替对象键）：20 KB → ~7 KB。
3. seed / pool 统一由 cron 写，写前比内容 hash：写 254 → **140/天**（facts 不再占 KV 写）。
4. 探测合并：一次 `/meter/tfb` 带 3 个 host；cron 30 → 45 分钟；DO 150 → **80/天**。
5. `meterCache` 5 → 15 分钟 + Cache API（`w:1` 世界快照 60 s/colo）。
6. `alive` 800 → 256、`chan/perf` 512 → 256：内存 0.8 → 0.45 MB。

**改口：facts 进 DO（第一版说「不做」，理由是「同为 10 万/天且多一跳」——重算后不成立）**。DO 请求额度 10 万/天是 KV **写**额度（1000/天）的 100 倍，而「写」才是真正的瓶颈；多一跳只发生在惰性刷新时（10 分钟一次、后台进行），不在首字节路径上。详见 §16.3 与 §16.4。

**仍然不做**：用 KV `list` 分片（`list` 同样受写额度约束，读还会放大）。

## 9. 可观测性

| 指标 | 位置 | 用途 |
|---|---|---|
| `v6c` | `/health` 计数器 | v6 客户端比例，用来分离「客户端族」与「出口抽签」两类 403 |
| `smN` / `smD` | 同上 | 小响应来自中继/直连的比例 |
| `errsByKind` / `errsDup` | 同上 | 错误分类与限流丢弃量 |
| `?rt=<host>` | `/debug` | 本站点 × 中继的 ttfb/kbs |
| `?plan=1` | `/debug` | 本轮预算分配与消耗 |
| `?facts=1` | `/debug` | KV 事实快照（`dns`/`eg`/`site`/`dead`/`cap` + `factSkip` 分类） |
| `?fam=<host>` | `/debug` | 该站点的 A/AAAA 能力、`p4`/`p6`、最近一次族决策 |

**延迟指标必须拆三个**（§33.3 的教训：成功率变化会让「平均延迟」失去意义）：

| 指标 | 定义 | 为什么必须单列 |
|---|---|---|
| `p95all` | 全部响应的 p95 | 混进被封锁页（60 ms），成功率高时反而变大 |
| `p95ok` | **只算成功请求**的 p95 | 唯一能回答「是不是变慢了」的数字 |
| `good3s` | 成功 **且** ≤3 s 的占比 | 唯一能对用户承诺的端到端体感指标 |

只报一个「平均延迟」或「p95」的方案，在成功率从 45% 涨到 95% 时会被误读成性能退化（实测 +74 ms，其中 +7 ms 是真差异）。

## 11. 风险与开关

| 风险 | 缓解 | 开关 |

## 12. 明确不做

- 连接内「看到 403 就换中继重试」（Worker 只看得到 TLS 密文）
- 缓冲首块再判定（https 看不到方法，重放会重复投递 POST）
- 站点域名常量 / `DOMAIN-SUFFIX` 分流
- 入口 × 中继全交叉订阅（条目爆炸）
- 多级中继（延迟与失败点翻倍）
- 用直连通道的探测结论写 KV（身份不可归属）
- 把 v6 出口当「必败」硬封（会缩池、且与实测 2/5 矛盾）
- 往中继递 IPv4 字面量（proxyip 按 SNI 解析，实测无效）

## 13. 实验依据（本次修订的数据来源）

脚本都在 `.tmp-sim/`，都是真 VLESS+TLS 隧道或真 DoH/TCP 探测。

### 13.1 出口族（`egress.mjs`，经中继访问回显服务）

| 中继 | 出口 | 族 |
|---|---|---|
| `45.136.117.194` | `45.136.117.194` | **v4** |
| `91.215.153.143` | `2001:67c:2f4c:2::51e` | v6 |
| `193.181.211.185` | `2a0f:f01:208:3ba::` | v6 |
| `185.253.117.147` | `2a01:8640:1c::efcd:2d49` | v6 |

8 条活中继里只有 1 条 v4 出口 —— 这是「扩池 + 标族」最直接的动机。

### 13.2 逐次配对（`pairtest.mjs`：先问出口，再打 x.com）

| 中继 | 出口 | x.com |
|---|---|---|
| `91.215.153.143` | 恒定 v6 | **0/8** |
| `193.181.211.185` | 恒定 v6 | **2/5**（同出口 200/403 交替） |
| `185.253.117.147` | 恒定 v6 | 0/3 |
| `45.136.117.194` | 恒定 v4 | **6/6** |

⇒ `P(通过|v4) ≈ 100%`、`P(通过|v6) ≈ 12.5%`（2/16）：**v6 是折扣，不是开关**。

### 13.3 中继不改族（`forcev4.mjs`）

把 VLESS 目标换成 v4 字面量 `104.18.32.1`、SNI 仍为 `x.com`：经 v6 出口中继**照样 403/3 次**；经 v4 出口中继 200/3 次。再换 SNI：`cloudflare.com` → 301（CF 自己的页面）、`github.com` → 握手失败 ⇒ proxyip 认 SNI，不认 VLESS 地址。

### 13.4 客户端族（`famtest.mjs`）

同一中继，v4 客户端 6/6 200；`family=6` 臂 6/6 `ws error`（本机没有到 CF 边缘的 v6 路由）⇒ 客户端族这条**本地无法验证**，只能由用户在 v6 网络上用 FlClash 复测。

### 13.5 本地枚举池子这条路走不通（`relayscan.mjs` / `relaytls.mjs`）

两条都试过，结论明确：

| 试法 | 结果 | 原因 |
|---|---|---|
| 抽样公开源 80 条，发 `CONNECT host:443` | **0/80 可达**，且已知可用的中继回 `HTTP/1.1 400 Bad Request` | proxyip 不是 HTTP 代理，是**按 ClientHello SNI 转发的透明 TCP 代理**（`src/proxy/dialer.ts` 直接 `connect({hostname: relay})` 后写 ClientHello） |
| 抽样公开源 → 真 TLS（SNI=icanhazip.com） | 已知 v4 中继 `45.136.117.194` 复现「出口 45.136.117.194（v4）」✅；但 `185.253.117.147` 直接 `ECONNRESET`，第二个站点请求也 RST | 绝大多数中继**只对 CF 出口网段开放**（用户 2026-11-15 确认：「这些 proxyip 大部分本地确实无法访问」），并有速率/并发限制 |

**推论（写进设计的约束）**：

1. `eg` 事实**只能由 Worker 探测产生** —— 本地无法枚举、无法旁证，所以 §16.5 的「共享 `eg`」不是优化，而是让全队共担这份探测成本的**必要**机制。
2. 一次探测必须同时得到两样东西（`alive` + `eg`）：探测目标用**回显服务**（`icanhazip.com` 这类返回来源 IP 的站点），这样「连得上」与「出口是 v4 还是 v6」一次拿到 —— 这也是 D10 的修法。
3. 本地仍能做的是**经 Worker 的端到端测量**（`vclient`/`vspeed`/`pairtest` 走 `?rx=` 钉中继），以及「拿已知中继做对照」；不能做全池普查。

### 13.6 一次探测同时拿到「活着」与「出口族」（`vclient.mjs` + `?px=1&rx=`）

不写任何新代码就能验证 v8 的探测设计：`?px=1&rx=<relay>` 钉住中继，把隧道里的请求打到 **`icanhazip.com`**（回显来源 IP），body 就是该中继的出口地址。实测 8 条活跃中继（每条 1 次，1.2–1.8 s、约 620 B）：

| 中继 | 出口 | 族 |
|---|---|---|
| `45.136.117.194` | `45.136.117.194` | **v4** |
| `45.147.250.39` | `45.147.250.39` | **v4** |
| `45.151.183.22` | `45.151.183.22` | **v4** |
| `91.215.153.143` | `2001:67c:2f4c:2::51e` | v6 |
| `91.215.154.80` | `2001:67c:2f4c:2::234` | v6 |
| `193.181.211.185` | `2a0f:f01:208:3ba::` | v6 |
| `185.253.117.147` | `2a01:8640:1c::efcd:2d49` | v6 |
| `89.22.227.132` | —— | 失败：`Hostname/IP does not match certificate's altnames: Host: ica…`（回自己的页面） |

三条结论：

1. **v4 出口占 3/8（37.5%）**，比先前「1/8」的估计乐观；先前那次只测了 4 条，属于抽样偏差。
2. **一次 connect + 一次 GET 就同时得到「活着」与「出口族」** —— 这正是 D10 想要的「探测合并」，且不需要新增端点（`?rx=` 已有）。
3. `89.22.227.132` 这类「回自己证书」的中继应进 `dead` 表（机器属性、可共享），而不是仅记为「本次失败」。

**对 §7.3 的影响**：目标「≥3 条 v4 在线」当前已经满足，所以收益不在扩张池子，而在**识别 + 共享** —— 一个 isolate 探到 `eg` 就立刻写 DO，别队立刻可用。

### 13.7 首请求成功率 = v4 出口占比（基线实测，2026-11-15 02:31）

20 个新进程、每个只发 1 条请求（等价于「冷连接的第一条请求」），目标 x.com：

| 结果 | 次数 | 占比 |
|---|---|---|
| 200（4107 B，真首页） | 8 | 40% |
| 403（**737 B**，正文含 `IPv6`） | 11 | 55% |
| 失败（`Hostname/IP does not match… Host: x.c`，中继回自己的证书） | 1 | 5% |

两个结论，一个推翻假设、一个给出量化：

1. **首请求 40% ≈ v4 出口占比 37.5%（§13.6）** —— 这说明「盲选时能不能过」几乎完全由「抽到的是不是 v4 出口」决定，而不是由延迟/评分决定。**这就是可量化的杠杆**：`eg` 共享 + 优先 v4 之后，同样的 8 条中继应该把首请求从 40% 拉到 95%±。
2. **拒绝页不是 4 字节，而是 737 B**（带 `IPv6` 文本的 HTML）。这条直接推翻了「`tiny = down ≤ 64`」的判据（D3）—— 见 §15 的修正。

另注：失败那条是「中继回自己的证书」，属于 `dead`（机器属性），不是站点封锁。

|---|---|---|---|
| 串行稳态 | 92–96% | **96–98%** | 残差是站点侧的请求级拒绝 |
| 冷 isolate 头几条 | 60–80% | **80–90%** | 事实在 DO（§16.5），但事实本身要有人先探到 |
| 20 并发 | 75–85% | **85–90%** | 每并发可能落在不同 isolate |
| 下载吞吐 | 0.3–2.3 MB/s | 不变 | 瓶颈在客户端→边缘，不在源站（`?bench=` 147 MB/s） |

**不可解**：客户端→CF 边缘质量、免费计划 6 并发 / 10ms CPU、事实传播延迟（cron 30–45 分钟；KV 写 1000/天已不再是瓶颈，因为事实不走 KV）。
**半可解**：站点对 v6 的拒绝率（靠 `p6` 排序 + `eg` 优先 v4，不能归零）、假 200 骗过客户端 url-test、`eg` 的跨 isolate 传播延迟（cron 30–45 分钟）。v4 出口数量本身**不是瓶颈**：实测已有 3/8（§13.6）。
**结构性**：路径性证据（`ttfb`）只能每个 isolate 自己积累；DO 只承载「与 isolate 无关的客观事实」——出口族 `eg`、相对容量 `cap`、站点通过率 `ps`、封锁 `blk`（§16.5 的最终边界）。

## 15. 第二轮审查：11 个缺陷与修正

审查方法：把 §4/§6/§7/§8 的每个判据对着 7.86 的代码与今天的实测数据推演一遍，凡「在某种真实输入下会给出错误行为」的即计入。

### D1 `blkAt` 是站点级却过滤掉所有中继（§7 伪代码 bug）

```ts
!(f.site[inp.host]?.blkAt > 0)   // 一旦有封锁记录，cands 直接空
```

- 后果：`thompson([])` 未定义行为；即使不崩，也会退化成「无候选」。
- 修正：封锁必须键为 `host|relay`，只排那一条；全排掉时走 `leastBad(host)`（7.x 已有）兜底，并记 `why: "least-bad"`。

### D2 `ChanTable` 没有成败计数 → 算不出 `p(host, relay)`

今天实测（同一分钟）：

| 中继 | 族 | x.com | github.com | example.com |
|---|---|---|---|---|
| `91.215.153.143` | v6 | **0/8** | 3/3（120 KB） | 3/3（932 B） |
| `193.181.211.185` | v6 | **2/5** | — | — |
| `185.253.117.147` | v6 | 0/3 | — | — |
| `45.136.117.194` | v4 | 6/6 | 3/3（120 KB） | — |

- 同族内 0/8 与 2/5 差一个数量级 ⇒ 按族聚合会误伤。
- 修正：`ChanRow` 加 `okN` / `badN`（半衰期 6h）+ `bigTypical`（该站点成功响应尺寸的 EWMA/max）。

### D3 「小响应」用绝对阈值 → 冤枉正常小页面（**此条被 §13.7 实测再修正一次**）

- 实测：`example.com` 正常响应 **932 B**、`api.github.com` **1277 B**。按 `<12KB` 判据，两者都会被当成「可疑小响应」。
- 第一版修正「`tiny = down <= 64`」**同样不成立**：§13.7 实测 X 的拒绝页是 **737 B**（带 `IPv6` 文本的 HTML），`≤64B` 会漏掉今天的绝大部分封锁页。
- 最终修正（两条同时满足才算 `tiny`）：
  1. **绝对**：`down <= 2048`（覆盖 4B / 737B / 1.3KB 这几代拒绝页）；
  2. **相对**：`down < 0.2 × bigTypical(H)`（737 B / 45 KB = 1.6% 明显低于阈值；`example.com` 932 B 但它的 `bigTypical` 也只有 ~1KB ⇒ 比值 ≈1，不会误判）。
- `tiny` 只用于「降权 / 记负记忆」，**永不单独作为封锁证据**（封锁仍要 §6 的两批次差分）。

### D4 成功 ≠ 2xx：业务 4xx 会被记成失败

- 实测：`api.github.com` 经两条中继都是 **415 + 1277 B**（它要求 `Accept: application/json`）。这是**正常的应用层响应**，但按「2xx 才算成功」会被算成 0% 成功，于是该站点的每条中继都被降权，最终无人可用。
- 修正：`ok` 的定义改成「拿到完整响应」：`down > 64`（非拒绝页）即可；`2xx` 只作为「整页」的辅助判据。**这是普适性最关键的一条**：API、GraphQL、401 页面、重定向都算成功。

### D5 吞吐样本要求 ≥1 MB → 普通网页永远学不到 `kbs`

- 实测尺寸：x.com 主页 45 KB、github.com 120 KB、example.com 0.9 KB。`connection.ts:317` 的 `down >= 1048576` 意味着**这些站点全部记为 `kbs=0`**，tput 模式退化成只看 `ttfb`。
- 修正：门槛改成 `down >= 5 × TICK_BYTES`（约 40 KB）并记 `bytes/ms`；同时保留「≥1MB 样本权重更高」。对 `<40KB` 的站点，tput 代价退化为 `ttfb + 200`（表示「小页面的吞吐无意义」）。

### D6 `famPen` 用单值 `p6` 乘所有 v6 中继

- 见 D2 的数据：同族内差异巨大。
- 修正：`p(host, relay) = (okN + α·prior) / (okN + badN + α)`，`α=4`，`prior` 由族先验给出（`eg=4 → p4`、`eg=6 → p6`、未知 → 0.5）；排序用 `score = transport / max(0.08, p)`。

### D7 Happy Eyeballs 没进预算，且要 DoH 才有地址

- 一次双栈请求吃 2 个 connect（6 并发下砍掉 1/3 真实流量）；DoH 20–50 ms 全加在 TTFB 上。
- 修正：**懒加载族绑定** —— happy path 直接按域名连（不查 DNS）；只有「失败」或「tiny 响应」时才 DoH 取 A 记录重试一次。既不需要预算，也不给好路径加延迟。

### D8 `world` 单键的读改写竞争

- 两个 isolate 同时「读 → 改 → 写」`w:1`，后写覆盖前写，facts 丢更新（尤其 `eg`/`ps` 这类高频更新的字段）。**已解决**：§16.3 把 facts 移到 DO，写入用 `ON CONFLICT … WHERE excluded.at > facts.at`（§17.2）；本段保留为历史。
- 修正：按类分片（`w:dns` / `w:eg` / `w:site`）**并且**每条事实自带 `at`，读时按 `at` 取新（合并语义而非整体替换）。

### D9 TTL 与 cron 节奏踩线

- `blk` TTL 45 分钟、cron 45 分钟一轮 ⇒ 封锁事实在过期边界反复抖动（刚过期就被重新写）。
- 修正：`blk` TTL ≥ 2× cron（90 分钟），或 cron 回到 30 分钟；其余事实同理取 `max(TTL_min, 2×轮询间隔)`。

### D10 探测预算与候选规模不匹配

- 若 `alive` 扩到 32，一轮要「refill ≤6 + 探活 32 + tfb 1」> 48 子请求上限，且并发只有 6。
- 修正：探活分 3 轮（每轮 12 条），并把「回显探测」与「探活」合并（探测目标用回显服务 ⇒ 一次 connect 同时得到「活着」与「出口族」）；预算表写死 `refill 6 + 探活 12 + tfb 6 = 24 < 48`。

---

### D11 `eg` 会变：6 小时 TTL 会让「v4 出口」变成错误事实

- 42 次实测里出现过「同一条中继先 200 后 403」（§13.7 的 193.181.211.185：2/5），说明**出口地址族可能随时间/线路变化**，而 `eg` 的 TTL 是 6 小时 —— 一条已经切到 v6 的中继会在最长 6 小时内仍被当作 v4 优先使用，且因为「v4 优先」它会被**高频选中**，错误被放大。
- 修正（三条一起）：
  1. **失败即复核**：`eg=4` 的中继连续 2 次 `tiny` → 立刻安排一次回显探测（优先级高于「未知」，因为它正在被高频使用）。
  2. **TTL 分层**：`eg` 对「正在被使用的中继」按 1 小时刷新，对「闲置的」才用 6 小时（用的时候才值钱）。
  3. **不信任单点**：选路时 `eg=4` 只作为先验（`prior=0.95`），`p` 仍由个体 `okN/badN` 修正 —— 与 D6 的公式天然一致，不需要额外逻辑。
## 16. KV / DO 额度：现状、重算与优化

### 16.1 现有 KV 键与写节奏

| 键 | 内容 | 写入时机 | 估算/天 |
|---|---|---|---|
| `px:seed` | 节点名字表（≤800） | 最长 90 分钟一次 + 内容变化 | 16 |
| `px:pool:<gen>` | 代际池子 | refill 且 hash 变化 | 5 |
| `snap` | 全局快照（统计 + errs） | 1h/2h + 全局 45 分钟闸门 | ~30 |
| `usage:snap` | 用量快照 | 与上同源 | ~30 |
| `users` | 用户记录 | 管理操作 | <5 |
| `rtt:<id>` / `edge:pref` | 调试/偏好 | 变化时 | <5 |
| **合计** | | | **~85** |

### 16.2 若把 facts 放 KV

| 项 | 每天 | 说明 |
|---|---|---|
| facts 写（10 分钟节流 + hash 门） | +140 | 只要 4 类事实都在动就接近这个数 |
| 合计写 | **225** | 额度 1000 时还有 4.4× 余量 |
| 读 | 1/冷启动 ≈ 10k | 额度 10 万，10× 余量 |

**问题**：写额度消耗翻 2.6 倍，而「写」是最紧的额度（1000/天）。流量涨 10 倍时（isolate 10 万）写仍受 1000 限制，但**读**先到顶 —— 那时 facts 反而写不进去。

### 16.3 建议：facts 搬 DO，KV 只留冷数据

| 载体 | 放什么 | 为什么 |
|---|---|---|
| **DO 存储**（`Meter`） | `facts`（dns/eg/site/dead/cap）、计数器 | DO 请求额度 10 万/天，比 KV 写 1000/天 宽 **100 倍**；且可原子读改写，天然解决 D8 的竞争 |
| **KV** | `px:seed`、`px:pool:<gen>`、`users`、`snap`、`usage:snap` | 冷数据，写少、需要跨机房 |
| **Cache API** | `w:1` 世界快照（60 s/colo） | 读 10k → ~500/天，且 KV 读额度不再是瓶颈 |

```ts
// 新增：DO 上的一个端点，一次拿全量事实（冷启动用）
GET  /meter/facts?s=<shard>          → { v, dns, eg, site, dead, cap, at }
// 增量写：只提交变化项，服务端按 at 合并（解决 D8）
POST /meter/facts  { shard, items: [{ k, f: "eg"|"site"|"dns", ... , at }] }
```

预算（改后）：KV 写 ~85/天（不动）、KV 读 ~500/天、DO 请求 ~110/天（探活批 80 + facts 30）。

### 16.4 还能再压的三处

1. **`snap` 与 `usage:snap` 合并**（同一份数据两处写）：写 60 → 30/天。
2. **`rtt:<id>` 移进 DO**（它本来就是按 id 分片的调试数据）。
3. **`edge:pref` 只在有变化时写**（现在已经是变化才写，但要确认没有「空表覆盖」路径）。

**结论**：把 facts 放 DO 之后，KV 侧只承担「冷数据 + 用户数据」，读写在 10 倍流量下都还有 5–10 倍余量；DO 侧 100 倍余量，可以放心把「探测 + 事实」都放进去。

### 16.5 共享与不共享的边界（用户 2026-11-15 拍板）

> 原话：「在不超免费版额度的情况下，可以共享」。

这条拍板解决了 v8 里最关键的一个供给问题：**「哪条中继是 v4 出口」这件事，每个 isolate 都得从零试一遍**。实测 8 条活跃中继里有 **3 条** v4 出口（§13.6），而 v4 出口对 x 类站点 6/6、v6 出口 0–2/5。也就是说池子里的好中继够用，但每条新 isolate 都要靠「8 选 3」的盲抽去撞，撞不中就必然踩 403。

| 数据 | 共享？ | 载体 | 理由 |
|---|---|---|---|
| `dns[H]` 目标的 A/AAAA | **共享** | DO | 客观事实，与谁去连无关 |
| `eg[R]` 中继出口族 | **共享** | DO | **机器属性**：`45.136.117.194` 永远是 v4 出口，不会因 isolate 而变 |
| `blk[H\|R]` A 级封锁 | **共享** | DO | 用户 m13158：「机房级封锁对跨 isolate 没有影响，只要有绝对证据」+ §6 的两批次闸门 |
| `dead[R]` 握手必败 | **共享** | DO | 回自己证书/握手必败是机器属性 |
| `cap[R]` 相对容量 | **共享** | DO | 只存「相对池内中位数」的比值（§24 R2），且必须过噪声门（R1）；绝对 KB/s 不共享 |
| `ttfb`、`bps`（传输性能） | **不共享** | isolate 内存 | 这两项强依赖「本 isolate 到该出口的路径」，换 isolate 就换路径（最初「不跨 isolate 共享」的出发点） |
| `p(host,relay)` 成功率 | **共享，但只作软概率**（§22） | DO facts 的 `ps` | 它描述「这条中继的出口 IP 对某站点过不过」，与路径无关；但必须以 EWMA 小数共享，**绝不能变成二元封锁**（7.57 的教训） |
| 选路游标、冷启动钉住 | 不共享 | isolate 内存 | 本来就是探索状态 |

**额度账（共享之后）**：

| 项 | 每天 | 额度 | 余量 |
|---|---|---|---|
| DO 请求：isolate 启动读 facts | ≈ 5 万（按 5 万次启动） | 10 万 | 2× |
| DO 请求：探测写（12 条/轮 × 48 轮） | ≈ 576 | 10 万 | 170× |
| KV 写 | ≈ 85 | 1000 | 11× |
| KV 读 | ≈ 500（Cache API 兜住 world 快照） | 10 万 | 200× |

⇒ **共享是免费的**：真正贵的 KV 写只有 85/天，DO 请求的 5 万/天来自「每次冷启动读一次 facts」，而这一读换来的是「新 isolate 第一条请求就知道哪条中继是 v4 出口」。

**供给推论（这才是 x 类成功率的杠杆）**：

- 现状：每 isolate 8 条活跃中继、其中 v4 出口实测 3 条（37.5%）⇒ 盲选命中 v4 的概率 37.5%，剩余 62.5% 里 v6 出口只有 0–2/5 能过。
- 共享后：`eg` 是全队共享的，**任意 isolate 探到一条 v4 出口，全队立刻可用**。同样的 8 条中继，共享前后差别不是「多几条中继」，而是「每个新 isolate 第一条请求就能直接挑 v4」——盲选 37.5% → **排序后接近 100%**，对应「首次请求就 200」的实测曲线 96–98%（§14）。
- 因此 v8 的 `alive` 目标不是「越多越好」，而是「**保证 v4 出口 ≥3 条在线**」；`eg` 共享让这个目标从「每条 isolate 各自撞运气」变成「全队共同维护」。

**与旧约束的关系**：早期「不跨 isolate 共享统计」的原因（m00676）是「每个 isolate 到同一节点的 RTT 可能差一倍」——那条约束对**延迟/带宽统计**依然成立，本节的共享清单里没有任何延迟或带宽数字。

## 17. 迁移第 1 步施工图：事实层（不改选路）

目标：先把「跨 isolate 的客观事实」落地并跑起来，**选路逻辑一行不动** —— 这样任何问题都能靠 `SC.FACTS=0` 回滚，且收益（`firstTry` 提升）能单独归因。

### 17.1 开关与边界

| 开关 | 含义 | 行为 |
|---|---|---|
| `SC.FACTS = 0` | 关闭 | 不读不写，等同 7.86 |
| `1` | 影子 | 只写、`/health` 可见，但 `decide()` 不读 |
| `2` | 生效（默认） | 读 `eg` / `blk` / `dead`，写全部 |

第 1 步只做 `0 / 1` 两档；`2` 留到第 2 步（读进 `decide()`）。**本步不碰 KV**：写入量维持约 85/天，用来验证 §16 的账。

### 17.2 DO 存储（`Meter` 的 SQLite）

```sql
CREATE TABLE IF NOT EXISTS facts (
  kind TEXT NOT NULL,   -- dns | eg | ps | blk | dead | cap
  k    TEXT NOT NULL,   -- host / relayIP / "host|relay"
  at   INTEGER NOT NULL,
  j    TEXT NOT NULL,   -- 紧凑 JSON，如 {"f":4,"n":2}
  PRIMARY KEY (kind, k)
);
CREATE INDEX IF NOT EXISTS idx_facts_at ON facts(kind, at);
```

- **合并语义（解决 D8）**：`INSERT … ON CONFLICT(kind,k) DO UPDATE SET at=excluded.at, j=excluded.j WHERE excluded.at > facts.at` —— 只有更新的证据才覆盖，乱序到达也不会回退。
- **容量（每 kind）**：`dns 512 / eg 512 / blk 1024 / dead 256 / cap 256`；插入后按 `at` 升序删掉超出部分（同一事务）。
- **单行上限** 128 字节；`j` 里不放注释、不放浮点尾数（`toFixed(2)` 后存字符串）。

### 17.3 端点

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| GET | `/meter/facts?s=<kind>&since=<ts>` | `since=0` 该 kind 全量 | `{ v:2, now, n, rows:[[kind,k,at,j]] }`（**按 kind 分片**，单次 < 8KB；整库最坏 ~250KB，见 §28.4） |
| POST | `/meter/facts` | `{ rows:[[kind,k,at,j]] }`，≤64 行/次 | `{ ok, wrote, skipped }`（`skipped` 含 `at` 更旧的） |

- 只在 Worker 内部调用（`src/store/facts.ts` 走 `env.METER` 的 stub），不加入任何公开路由。
- 失败一律吞掉并计数（`factErr`）：**事实层不能让选路失败**。

### 17.4 `commitFact` 的 10 条拒绝用例（**早期草稿；落地以 §17.7 的表驱动版本为准**）

| # | 输入 | 期望 | 理由 |
|---|---|---|---|
| 1 | `blk` 只有一批 | `false` | 需两个独立批次（≥60s） |
| 2 | `blk` 同批无 2xx 对照 | `false` | 做不出差分，可能是站点级封锁 |
| 3 | `blk` 来自直连腿 | `false` | CF 边缘出站身份不可归属 |
| 4 | `blk` 两批方向相反 | `false` | 弃权，保留旧值 |
| 5 | `eg` 只有一次回显 | `false` | 需两次，或「200 ≥20KB vs 4 字节」强配对 |
| 6 | `eg` 回显响应 <64B | `false` | 可能是拒绝页冒充 |
| 7 | `dns` 两次结果不一致 | `false` | 弃权，下次再查 |
| 8 | `dead` 只有一次失败 | `false` | 需两次必败 |
| 9 | `cap` 样本 <3 | `false` | 先验不足 |
| 10 | 任意 kind 的 `at` 早于库内 `at` | `false` | 不许回退（D8 的另一半） |

### 17.5 六步迁移（每步独立可上线、可回滚）

| 步 | 内容 | 回滚 |
|---|---|---|
| 1 | 事实层：DO 表 + 端点 + 写入点（影子） | `SC.FACTS=0` |
| 2 | 读进 `decide()`：只用 `eg`（v4 优先）+ `blk`（过滤）+ `dead` | `SC.FACTS=1` |
| 3 | 探测改造：`alive`+`eg` 合并探测（§13.6 已验证），`v4` 保底（§7.3） | 关掉新探测，保留旧探活 |
| 4 | `ChanTable` 换代：`okN/badN/bigTypical` + `p(host,relay)` | 保留旧字段，新字段只读 |

## 18. `decide()` 的表驱动测试向量（第 5 步的验收标准）

第 5 步要重写选路，所以先把**行为**定死：下表每一行都是一个「可直接翻译成单测」的用例。约定：

- 先验：`prior(v4) = 0.95`、`prior(v6) = 0.5`（族未知）、先验强度 `α = 4`。
- `p = (okN + α·prior) / (okN + badN + α)`；`transport(tput) = ttfb + 512000 / max(32, bps)`，`transport(lat) = ttfb`；`score = transport / max(0.08, p)`。
- 排序：`score` 升序 → `okN` 降序 → `ip` 字典序（保证确定性，测试可断言具体哪一条）。
- 「有效率」= 不在 `dead`、不在未过期的 `blk`、不在黑名单/冻结。

| # | 输入摘要 | 期望通道 | `why` | 覆盖的规则 |
|---|---|---|---|---|
| 1 | 只有 v6 中继、全无样本 | `r:` 中 ttfb 最小者 | `relay-best` | 永不因「全是 v6」返回空 |
| 2 | v4（无样本，ttfb 800）vs v6（bps 2000 → transport≈800） | **v4** | `relay-best` | 族先验压过速度差 |
| 3 | v4 有 6 次失败（p≈0.35）vs v6 有 6 次成功（p≈0.9） | **v6** | `relay-best` | 个体样本覆盖先验 |
| 4 | 两条都在 `blk`（未过期） | `leastBad` 中的最优者 | `least-bad` | D1：绝不返回空 |
| 5 | 一条在 `dead` | 另一条 | `relay-best` | 机器属性直接排除 |
| 6 | 未知族（无样本）vs 已知 v6（有 3 次成功） | **未知族** | `relay-best` | 探索：未知先验 0.5 > v6 实测仍需样本 |
| 7 | `mode=lat`，v6 bps 极高但 ttfb 2000，v4 ttfb 300 | **v4** | `relay-best` | lat 不看 bps |
| 8 | `preferDirect` 且直连无 `tiny` 记录 | `d` | `direct` | 直连优先 |
| 9 | `preferDirect` 但直连 5 分钟内有 `tiny` | 中继最优 | `relay-best` | tiny 只降权直连 |
| 10 | `relays = []` 且 `cfHost` | `d` | `direct-only` | 没有中继可挑时的兜底 |
| 11 | 唯一一条中继，`dead` 已过期（>30 分钟） | 用它 | `relay-best` | TTL 过期即复活 |
| 12 | `blk` 的 `at` 早于 90 分钟 | 用该中继 | `relay-best` | D9 的 TTL |
| 13 | `tput` 且所有 `bps = 0` | 按 `ttfb` 排序 | `relay-best` | D5 小页面退化 |
| 14 | 两条完全同分 | `ip` 字典序小者 | `relay-best` | 确定性 tie-break |

**必须同时满足的三条不变量**（可写成 property test，随机输入 1000 次）：

1. 返回值永不为 `null`，且 `chan` 一定是「`d`」或一条**在候选中**的中继。
2. 若存在「有效且 `p ≥ 0.8`」的通道，则选中它的 `score` ≤ 任何其他通道 `score` × 1.05（容许 Thompson 抖动）。
3. 不存在「必然失败」的通道被选中：`dead` 命中率 0、未过期 `blk` 命中率 0。

> 这三条比任何具体用例都重要：它们保证重写之后**不会退化成「返回空/返回必败通道」**——而这正是 7.57 那次失败（通配封锁把池子标死）的本质。

## 19. 怎么判定「IP 级封锁」（v4 / v6），且不碰业务逻辑

这一节回答一个具体问题：**看到一次 4xx，凭什么说「这条出口 IP 被这个站点封了」？** 而且判定过程不能改变任何业务响应。

### 19.1 四件事必须分开，混在一起就会误伤

| 现象 | 真实含义 | 该怎么处理 | 能不能进封锁表 |
|---|---|---|---|
| 业务 4xx（401/403/404/415/429，带 1KB+ 站点页） | 目标说「你这个请求不对」 | **原样透传**，最多按状态码退避 | ❌ 永不 |
| 族级拒绝（站点不接受 v6 来源） | 站点策略，与具体 IP 无关 | 降权 v6 出口（`p6`），**不排除** | ❌ 只进统计 |
| 单 IP 封锁（这条出口被该站点拒） | 出口 IP 进了该站点的黑名单 | 只排这**一条** `(host, relay)`，90 分钟 | ✅ 需 A 级证据 |
| 中继自身坏（回自己证书/垃圾页/握手必败） | 中继坏了，与站点无关 | 进 `dead`，30 分钟 | ✅ 但记 `dead` 不记 `blk` |

我们实测过的四个真实输入，正好落在四个格子里：

| 输入 | 大小 | 判定 |
|---|---|---|
| `api.github.com` 经任意中继 → **415** | 1277 B，`bigTypical≈1277` ⇒ 比值 1.0 | 业务 4xx → 只计数 |
| `x.com` 经 v6 出口 → **403** | **737 B**，`bigTypical≈45 KB` ⇒ 1.6% | 疑似族级/单 IP，需差分 |
| `x.com` 经 v4 出口 → 200 | 45 KB | 正常 |
| `89.22.227.132` → 证书不匹配 | —— | `dead`（中继自身坏） |

### 19.2 判据只用「结构」，不读内容

**核心：生产环境不读响应体**（隐私 + 普适性 + 我们只看得到密文这件事的另一面：读了也没法泛化）。所以判据只有三个结构量：

```ts
// ① 是不是「小响应」：两个条件同时满足（§13.7 的 737B 拒绝页正是这么抓到的）
const tiny = down > 0 && down <= 2048 && down < 0.2 * (bigTypical[host] || 16384);

// ② 有没有「同窗口的对照成功」：另一条通道在同一 120s 窗口里拿到 ≥20KB
const hasBigPeer = (host, chan, now) =>
  others(host, chan).some((c) => row(host, c).bigAt > now - 120_000 &&
                                   row(host, c).bigTypical >= 20480);

// ③ 两批独立：同一结论在 ≥60s 之后再次出现
const confirmed = second(host, chan, now);
```

`tiny + hasBigPeer + confirmed` 三条同时成立，才允许写 `blk[host|relay]`。

### 19.3 v4 与 v6：判定方式的根本区别

**直连腿：族可控，所以能做「同窗口 A/B」** —— 这是唯一能干净判定「站点是否拒绝 v6」的地方：

```
同一 host、同一 120s 窗口：
  legA = connect(A 记录 → IPv4 字面量)   → 200 / ≥20KB
  legB = connect(AAAA → IPv6 字面量)     → 4xx / tiny
⇒ 站点级事实：site[host] 的 p6 低（族级拒绝），写 DO，6h 衰减
⇒ 若两条腿都 tiny ⇒ 站点级封锁，**不写任何封锁**（换出口重采）
⇒ 若 legA 也 tiny ⇒ 没有对照，弃权
```

**中继腿：族不可控，所以必须「先测族、再做差分」**：

```
第 1 步：eg[relay] = 回显（icanhazip）→ v4 | v6      // §13.6，一次 connect + 一次 GET
第 2 步：同窗口，relay 打 host → tiny
        且另一条 eg=4 的中继打 host → 2xx ≥20KB
        且 60s 后重复一次
⇒ 单 IP 封锁：blk[host|relay] = now（90 分钟）
```

**v4 与 v6 的判据完全对称，唯一差别是「先验」**：`prior(v4)=0.95`、`prior(v6)=0.5`。因为实测 v4 出口 6/6、v6 出口 0–2/5（§13.1/§13.6），v6 的每一次 tiny 需要**更多**证据才下结论（这也是为什么 v6 的 `blk` 要两批、而 v4 的可以一批加复核）。

### 19.4 证据分级与落库

| 级 | 构成 | 落库 | 生效方式 |
|---|---|---|---|
| **A** | 两批（≥60s），每批有 `tiny` 腿 + 同窗口 `≥20KB` 对照腿 | DO `blk` / `eg` / `dead` | 排序时排除 / 降权 |
| **B** | 单批差分，或同一 `(host, relay)` 连续 2 次 `tiny` | isolate 内存（`markNeg`） | 只降到队尾，10 分钟 |
| **C** | 单次 4xx；429；带站点页的 403；证书错误 | 计数器 | 不改变任何行为 |

**永不进 A 级的三种输入**：直连腿的 4xx（CF 边缘出口身份不可归属）、全通道 4xx（站点级，不是出口级）、429（限流，只需要退避）。

### 19.5 「不影响业务逻辑」的六条工程约束

1. **事实只影响排序，不影响返回**：`decide()` 的返回值永远是「`d` 或某条候选中继」，任何事实缺失/损坏都退化成今天的默认行为。
2. **热路径零 I/O**：facts 是 isolate 内存快照（启动读 1 次 + 10 分钟后台刷新），`decide()` 里不 `await`、不读 KV、不读 DO。
3. **写是旁路**：`POST /meter/facts` fire-and-forget，失败只加 `factErr` 计数，绝不影响请求。
4. **永不返回空**：所有候选都被 `blk`/`dead` 排掉时走 `leastBad`（§18 不变量 1）。
5. **可自愈**：5% 概率对「已封锁的 `(host, relay)`」复探一次，连续 2 次成功即解除——避免把一条好中继永久焊死（7.57 的教训）。
6. **判定本身要花额度**：每轮最多 2 条 connect 用于差分、每天每站点最多 3 批（现有 `tf` 预算不变）；不用新额度。

### 19.6 我们为什么有把握「不误伤业务」

用四个实测数字验证这条链：

| 站点 | 响应 | `tiny` 判据 | 结论 |
|---|---|---|---|
| `api.github.com` | 415 / 1277 B，`bigTypical≈1277` | `1277 ≤ 2048` ✅ 但 `1277 < 0.2×1277` ❌ | **不算 tiny** → 只计数，永不封锁 |
| `example.com` | 200 / 932 B | 比值 ≈1 ❌ | 正常小站，不误判 |
| `github.com` | 200 / 120 KB | 远超阈值 ❌ | 正常 |
| `x.com`（v6 出口） | 403 / **737 B**，`bigTypical≈45 KB` | 绝对 ✅ + 相对 1.6% ✅ | 疑似封锁 → 进差分 |

也就是说：**业务 4xx 因为「相对自身典型尺寸不算小」而天然逃过 `tiny`**，不需要任何站点名单，也不需要读内容。

## 20. 北极星指标 `firstTry` 与冷 isolate 自愈

### 20.1 指标定义（两个数，不能只报一个）

我们**唯一能观测到的"用户成功"代理量是响应字节数**，而字节数阈值是站点相关的：x.com 首页 45 KB、`github.com` 120 KB、`example.com` 932 B、封锁页 737 B。任何单一阈值都会说谎：

- 只看 `down > 0` → 把 737 B 的封锁页算成功（虚高）；
- 只看 `down >= 4096` → 把正常的 932 B 小站算失败（虚低）。

所以 `firstTry` 必须报**两个数**，并且用它们之间的差来定位问题：

```
firstTry   = 第 1 条连接就 down > 0 的 isolate 占比        // 连通率（含封锁页）
firstPage  = 第 1 条连接就 down >= 4096 的 isolate 占比     // 拿到真页面
gap        = firstTry - firstPage                          // 被"小响应"吃掉的差值
```

- `gap` 大 ⇒ 大量连接落在封锁页/错误页（这正是 7.86 的形态：`firstTry` 约 0.95、`firstPage` 约 0.40）；
- `firstTry` 与 `firstPage` 都低 ⇒ 问题是**连不上**（中继挂死/超时），不是被拒。

**已知的灰带**：`firstPage` 的 4096 与 `tiny` 的 2048 之间（2048–4096B）既不算「拿到页面」也不算「明确封锁」。这类响应在正常站点里极少（`example.com` 932B、`api.github.com` 1277B 都在 `tiny` 内；真页面多在 45–120KB），但为了不让它无声消失，单独计数 `ftGray`（同样只统计每个 isolate 的前 3 条连接）。若线上 `ftGray` 长期 >5%，说明 4096 这个阈值该改成「站点相对值」`max(2048, 0.05×bigTypical)`。

计数按 isolate 计（不是按请求），每个 isolate 只统计**前 3 条用户连接**：

```ts
// src/core/state.ts
S.ftN = 0;        // 已结算的用户连接数（封顶 3）
S.ftFirst = 0;    // 第 1 条连接就命中的次数（down > 0）
S.ftPage = 0;     // 第 1 条连接就拿到页面的次数（down >= 4096）
S.ft3 = 0;        // 前 3 条内拿到过页面的次数（用户"刷新两次能开"的部分）
S.ftGray = 0;     // 2048–4096B 的灰带（两边都不算，单独观察）
S.ftIso = 0;      // 观察到的 isolate 数（有 ≥1 条连接结算即 +1，封顶 1）
```

`/health` 读数：`{ firstTry: ftFirst/ftIso, firstPage: ftPage/ftIso, gray: ftGray/ftIso, within3: ft3/ftIso, n: ftN }`。

**为什么按 isolate 计而不是按请求计**：热态 isolate 会把总体成功率拉到 92–96%，把冷启动的洞完全稀释掉；而用户感受到的正是"新连接的第一下"。

### 20.2 冷 isolate 自愈（三档）

| 档 | 条件 | 行为 | 期望 |
|---|---|---|---|
| **warm** | `S.alive` 与 facts 快照都在 | 正常排序（`eg` 先验 + `p` 修正） | 95%+ |
| **cold+facts** | isolate 新起，但 DO 里有 `eg` | **最多等 200 ms** 读一次 facts 快照再拨号 | ~90% |
| **cold+empty** | 新 isolate 且 DO 里也没有 `eg` | 不等待，盲选；同时在后台发 1 条回显探测，结果写 DO | 40% → 下一条 90% |

**为什么值得为一次 DO 读阻塞 200 ms**：冷启动的 TTFB 已经是 2.5–3.3 s，200 ms 是 8%；换来的是首请求 40% → 90%。而 DO 读额度是 10 万/天，冷启动 ≈5 万/天（§16.5），**在额度内**。

**注意不能无限等**：`Promise.race([readFacts(), 200ms])`，超时就用「盲选 + 后台补探测」，绝不让 DO 抖动变成用户等待（7.81 的教训：`ensurePool` 就是这么把 p50 拖到 6.4 s 的）。

### 20.3 数值模型（用实测常数外推）

实测常数：`P(ok|v4)=0.95`（v4 出口 21/21 与 6/6）、`P(ok|v6)=0.125`（2/16）、活跃中继里 v4 占 37.5%（3/8）、`dead` 12.5%（1/8）。

| 情形 | 首请求期望成功率 |
|---|---|
| 盲选（现状 7.86） | 0.375×0.95 + 0.5×0.125 + 0.125×0 = **0.42**（实测 8/20 = 0.40 ✅） |
| `eg` 已知、v4 可用 | **0.95**（实测 21/21） |
| `eg` 已知、v4 全死（退 v6，试 1 次） | **0.125** |
| 同上，但 v6 试 2 次 | 1−0.875² = **0.23** |
| `eg` 未知（cold+empty） | 0.42，下一跳起 0.95 |

模型给出两个可验证的预言：① 只要池子里还有 1 条活的 v4 出口，`firstTry` 就该≥0.9；② **v4 全死时重试几乎无用**（23%），此时该做的是「别浪费用户时间」——直接回直连腿（§7.3）而不是连试两条 v6。

### 20.4 验收标准（迁移后必须同时满足）

| 指标 | 现状（7.86） | 目标 |
|---|---|---|
| `firstPage`（cold+facts） | 0.40（= 盲选命中率） | **≥ 0.85** |
| `firstPage`（warm） | 19/20 = 0.95 | **≥ 0.95**（不得退化） |
| `firstTry`（连通率，含封锁页） | ~0.95 | ≥ 0.98 |
| `gap`（连通 − 真页面） | ~0.55 | **≤ 0.10** |
| `?bench=`（源站腿） | 147 MB/s | ≥ 100 MB/s（不得退化） |
| 业务 4xx 误封 | 0（§19） | **仍为 0** |
| KV 写/天 | 85 | ≤ 100（§16.5） |

任何一项没达标，就不该继续往第 2 步迁移——**先修指标，再加功能**。

### 20.5 `readFacts` 的接口契约（三态 + 降级阶梯）

```ts
/** 事实快照：只有"客观、可共享"的那几类（§16.5），不含任何统计量 */
export interface FactsSnap {
  v: number;                  // 版本号，不匹配就整份丢弃
  at: number;                 // 快照时刻
  eg: Record<string, 4 | 6>;  // 中继 → 出口族
  blk: Record<string, number>;// "host|relay" → 写封锁的时刻
  dead: Record<string, number>;
  dns: Record<string, 0 | 4 | 6 | 1>; // host → 0 无记录 / 4 纯 v4 / 6 仅 v6 / 1 双栈
}

/** 只读一次 DO；超时/失败返回 null，永不 throw，永不重试第二次 */
export async function readFacts(env: Env, budgetMs = 200): Promise<FactsSnap | null>;
```

契约四条：

1. **全有或全无**：要么返回完整快照，要么返回 `null`；**不做部分应用**——半张表会让排序在两次请求之间抖动（7.57 的另一种形态）。
2. **只在冷 isolate 的第 1 条连接上阻塞**：`budgetMs = 200`，之后所有连接都读内存快照（`S.facts`），热路径零 I/O。
3. **每 isolate 每 10 分钟最多读 1 次**，失败后 60 秒内不再重试（避免 DO 抖动放大成额度浪费）。
4. **陈旧但可用**：快照超过 1 小时仍会被使用，只是标记 `stale: true`——因为出口族是小时级稳定的（§13.9），而"没有 facts"的代价（40% vs 95%）远大于"用了 1 小时前的 facts"。

降级阶梯（每一级都不改变业务响应）：

| 情况 | `readFacts` 返回 | `decide()` 行为 | 用户可见影响 |
|---|---|---|---|
| 内存有快照且 <10 min | 快照 | 正常排序（`eg` 先验 + `p` 修正） | 无 |
| 内存无快照，DO 200 ms 内返回 | 快照 | 同上 | 首字节 +20–50 ms |
| DO 超时/500 | null | 盲选 + 后台补一次回显探测 | 首请求约 40%，下一条恢复 |
| 快照版本号不符 | null | 同上 | 同 7.86 现状 |
| 快照 >1 h | 快照（`stale`） | 同上（仍需个体 `okN/badN` 修正） | 极小 |

### 20.6 `firstTry` 计数器的准确插入点

**唯一结算点是** `src/proxy/connection.ts` 的 `flush(closing?: boolean)`（第 238 行起）。那里已经具备全部三个观测量：
```
this.failed   // 中途断流（pipeBack 的 catch 置位），不算成功
this.down     // 下行字节数
this.node     // 有值 = 走中继；空 = 直连
```
插入位置：紧跟现有 `cnt(this.node ? "node" : "direct");`（第 301 行）之后、`nsOk` 之前：

```ts
// firstTry 只统计"用户连接"（有 host），不统计探活/内部隧道
if (this.host && S.ftN < 3) {
  const ok = !this.failed && this.down > 0;
  const page = ok && this.down >= 4096;
  if (S.ftN === 0) { S.ftIso = 1; if (ok) S.ftFirst += 1; if (page) S.ftPage += 1; }
  if (page) S.ft3 = 1;                 // 前 3 条内拿到过页面
  S.ftN += 1;
}
```

三个坑（都是我们踩过的同类）：

- **不要用 `this.ttfb > 0` 当成功判据**：直连失败时 `ttfb` 也可能是 0 而 `down > 0`（拿到了错误页）。
- **不要把探活/内部隧道算进去**：它们的 `host` 为空或为回显服务，会把 `firstPage` 拉高。
- **不要在 `pipeBack` 里计数**：那里会按块触发，一条连接会加多次。

### 20.7 指标被"做好看"的三个风险

1. **只优化 `firstPage` 会偏向大页面站点**：应当在 `/health` 同时看 `gap`，并在 sim 里按场景分组（小页面 / 大页面 / 封锁页）分别汇报。
2. **按 isolate 统计天然有幸存者偏差**（活得久的 isolate 才被观察到 3 条以上连接）：所以 `/health` 的 `n` 也要暴露，别只看比例。
3. **`ftN < 3` 的 isolate 会影响可读性**：低流量时几乎每个 isolate 只有 1 条连接，此时 `firstPage` 就等价于"最后一次单请求是否成功"——这正是我们要的，但要写明它不是长期平均。

## 21. 仿真验证：`eg` 是主杠杆，但它**不能单独上**（否则比盲选还差）

脚本：`.tmp-sim/v8sim.mjs`（策略对比 + DO 排队）、`.tmp-sim/v8sim2.mjs`（三场景 + colo 缓存）。常数全部来自实测：`P(ok|v4)=0.95`、`P(ok|v6)=0.125`、`dead` 12.5%、v4 占 37.5%；每个 isolate 最多 3 条连接，成功后不再重试；每次 4000 个 isolate。

### 21.1 三个场景 × 三种策略（first / within3）

| 场景 | A 盲选 | B 只按 `eg` 优先 | C `eg` 偏置 + `p(host,relay)` |
|---|---|---|---|
| **族分离**（x 类：v4 能过、v6 大多被拒） | 0.41–0.48 / 0.79–0.86 | **0.95 / 1.00** | 0.95 / 1.00 |
| 全族都一样（普通站） | 0.91 / 1.00 | 0.92 / 1.00 | **0.95 / 1.00** |
| **单条坏**（v4 组里混了一条 5% 的中继） | 0.79 / 0.99 | **0.65 / 0.97（比盲选更差！）** | **0.95 / 1.00** |

三个必须写进设计的结论：

1. **`eg` 是主杠杆**：族分离场景 0.41 → 0.95，与实测 40% → 100% 完全吻合；这种场景下 `p` 只加 +0.004，可以说不值钱。
2. **但 `eg` 单独上会倒退**：只要 v4 组里有一条坏中继，「优先 v4」就把它变成高频选择，first 从 0.79 掉到 **0.65**。→ **`eg` 只能是偏置（bias），永远不能硬过滤**；`p(host,relay)` 必须在同一版里就位，否则是把 7.86 的 40% 换成另一种 65%。
3. **普通站点上 `p` 是主要收益**（0.91 → 0.95），因为此时族没有信息量，能区分好坏的只有个体统计。

对 §10 迁移顺序的修订：**第 2 步（`p` 与 `ChanTable` 的 `okN/badN`）不能延后到第 3 步之后**——它可以先只做「读」（用于排序），写（`commitFact`）仍然晚一步，但 `eg` 上线的那一版必须同时具备「按个体成功率修正」的能力，否则就是上面第 2 行那个 0.65。

### 21.2 突发下 200 ms 的 DO 读会崩，colo 缓存是必需品

单实例 DO 串行、服务时间 15 ms、t=0 同时到达（新建 colo 的第一波流量）：

| 并发冷 isolate | 200 ms 内拿到 facts | 混合后 `firstPage`（有 facts 0.95 / 无 0.41） |
|---|---|---|
| 1 / 5 | 100% / 100% | 0.95 |
| 20 | **65%** | 0.76 |
| 40 | **33%** | 0.59 |
| 80 | **16%** | 0.50 |

加了 colo 级缓存（Cache API，同一 colo 60 s 内只有第 1 条去读 DO，其余 2 ms 命中）后，20/40/80 并发全部 **100%**，`firstPage` 稳在 0.95。

结论：**Cache API 不是优化项，是 §20.2 能否成立的前提**。落地时它必须和第 1 步一起做，且缓存键要含 `facts.v`（版本变了整份失效），TTL 120 s（比 DO 自身的 10 分钟刷新短，保证突发内共享、又不至于长期陈旧；为什么是 120 而不是 60，见 §30.3 的命中率扫描）。

> **§32 修正了本节的归因。** 上面的「并发 → 100%」只建模了 DO 读排队；把同一批连接要抢的 `connect()` 名额（免费计划 6 个、每次 250 ms）也算进去后，**p95 由名额决定，不由 DO 读决定**：40 并发时 p95 ≈ 675 ms，把探测限成「每波 ≤2 次」才回到 250 ms。single-flight 仍然必须做（消除尾部），但它不是 p95 的主因。详见 §32。

### 21.3 这轮仿真改变了什么

| 原设计 | 改后 | 依据 |
|---|---|---|
| `eg` 优先，先上、`p` 后上 | **同一版必须同时有 `p`** | 单条坏场景 0.65 < 0.79 |
| `eg` 作为候选过滤（只留 v4） | **只做 `+0.25` 的偏置** | 同上；v6 必须留在候选里 |
| facts 走 DO，200 ms 预算 | **DO + colo Cache 双层** | 20 并发只剩 65% |
| `p` 是「锦上添花」 | `p` 是**防倒退的安全网**，且是普通站点的主要收益 | 0.91→0.95、0.65→0.95 |

## 22. 关键可行性验证：`p` 必须共享，否则等于没做（这一轮推翻了 §21 的一半结论）

§21 给 `p(host,relay)` 记了「防倒退安全网」的功劳（单条坏场景 0.65 → 0.95），但那次仿真有一处不真实：**它让 4000 个 isolate 共用同一张统计表**。而 v8 的硬约束是「统计不跨 isolate 共享」，加上这个用户的实际形态是**几乎每条请求一个新 isolate**——每个 isolate 只有 1–3 条连接。所以本轮先把「本地统计能不能救」这件事算清楚。

脚本：`.tmp-sim/v8sim3.mjs`。场景：v4 组 `[0.95, 0.95, 0.05]`（含一条坏中继），v6 组 4 条 `0.12`，dead 1 条。

### 22.1 五种策略的 `firstPage`

| 策略 | isolate 只跑 1 条连接 | isolate 跑 3 条连接 | 失败落在坏出口的比例 |
|---|---|---|---|
| A 盲选 | 0.343 | 0.343 | 63–64% |
| B `eg` 偏置，无 `p` | 0.650 | 0.655 | 30–32% |
| **C 本地 `p` + `eg`（v8 原设计）** | **0.643** | 0.658 | 24–32% |
| **D 共享 `p`（EWMA 软概率）+ `eg`** | **0.950** | **0.947** | **0%** |
| E 共享 `p` + 硬封锁（7.55 复刻） | 0.951 | 0.954 | 0% |

**C ≈ B**：在短命 isolate 里，本地 `p` 拿不到第二个样本，后验永远停在先验——**它做的是零点几个百分点的事，等于没做**。

也就是说：

> **要么把 `p` 共享出去，要么干脆不做 `p`（只留 `eg` 偏置、接受 0.65）。**
> 做「本地 `p`」是最坏的选项：代码变复杂、指标不动。

### 22.2 与「统计不跨 isolate 共享」的调和

那条约束的原始理由是 **RTT 因 isolate 而异**（同一个节点在不同机房延迟能差一倍）。把统计拆成两类之后，这条理由依然成立，但不覆盖 `p`：

| 量 | 本质 | 是否随 isolate 变化 | 结论 |
|---|---|---|---|
| `ttfb`、`bps` | **路径**性能 | 会（换机房就换路径） | 不共享（维持原约束） |
| `p(host,relay)` | **中继出口 IP 对某站点的通过率** | 基本不会（出口 IP 是中继自己的） | 可共享，但必须是软概率 |

实测支撑：同一批 6 条中继 1.5 小时后出口族完全一致（§13.9）；出口族决定通过率（§13.1/§13.6/§13.8）。**该属性挂在「中继 × 站点」上，不挂在「isolate × 中继」上。**

### 22.3 为什么必须是「软概率」而不是「硬封锁」

仿真是打平的（D 0.950 / E 0.951），而且我这个场景里硬封锁也没崩（`v8sim4.mjs`：站点整体拒 v6 + v4 只 1 条时，D 0.688 / E 0.700，都没有出现「候选全封死」）。

**所以选软概率的依据不是仿真，而是生产实测**：7.55–7.57 那版把「这条中继出口走 v6」写进共享的硬封锁，30 分钟 TTL、几轮突发就把大半中继标死，可用池变薄，成功率从 97% 掉到 **2/20、4/20、5/20**（失败率 10% → 50%）。

这条要写清楚，因为它是一个方法论教训：**仿真在「共享是好事还是坏事」这种依赖历史事故的问题上给不出结论**——它没有 7.57 那次的池子变薄过程。仿真能给的结论是「本地统计无效」，给不了「共享用哪种形式」。

### 22.4 落地 schema（进 DO facts，与 `eg` 同级）

```ts
// 只存"证据"，不存"结论"：q 是 0..255 的通过率，n 是观测次数
interface PsRow { q: number; n: number; at: number }
// 键：host|relayIP（与 blk 同键空间），上限 512 行，TTL 45 分钟
// 更新：n' = min(32, n*0.98 + 1)   ← 窗口固定 ≤32，**不是 255**（§35.1：255 会让一次坏运气按住 29 次以上）
//       初值 n = 8；连续 3 次成功把 n 重置为 4（康复，§35.3）
//       q' = (q*n*0.98 + 255*ok) / (n*0.98 + 1)
// 使用：仅作为代价折价 p = q/255，score = transport / max(0.08, p)
// 写入：批量！每 isolate 攒 16 条样本或 60 秒（先到者）写一次，见 §34.4
//       逐条写会让 DO 请求数 = 用户请求数，10 万/天的额度会被打满
```

四条纪律：

1. **只折价，不过滤**：`p=0` 也只让代价变高（除 `max(0.08, p)`），永不从候选里删掉。
2. **衰减而非过期即清零**：`n` 的 0.98 衰减 ≈ 50 次观测的记忆，避免「昨天坏过就永远坏」。
3. **有界**：512 行、45 分钟；满了按 `at` 淘汰最旧（不是有坏就删——7.57 的 `drop()` 犯过这个错）。
4. **写入必须 A 级证据**（§19.4 / §17.7），单次观测只进 isolate 内存。

### 22.5 本轮修订汇总

| 原设计 | 改后 | 依据 |
|---|---|---|
| `p` 只在 isolate 内存（§16.5） | `p` 进 DO facts，作软概率共享 | C 0.643 ≈ B 0.650 |
| 「统计一律不共享」 | 拆成：路径性能不共享 / 站点-出口证据共享 | RTT 是路径属性，`p` 是出口属性 |
| `p` 可以后上 | `eg` 上线的同一版必须有 `p`（且必须共享） | 否则停在 0.65 |
| 硬封锁 vs 软概率「仿真说了算」 | **硬封锁禁用**，理由是 7.57 生产实测 | 仿真是打平的 |

## 23. 额度账：facts 读会不会先撞顶（答案：不会，先撞的是 Worker 请求本身）

前提是最坏形态：**几乎每条请求都是新 isolate**（实测 `/health` 反复返回 `candidates: 0`），所以「每 isolate 每 10 分钟 1 次读」在现实中退化成「几乎每请求 1 次读」。脚本：`.tmp-sim/budget.mjs`。

免费额度：Worker 请求 10 万/天、DO 请求 10 万/天、KV 读 10 万/天、**KV 写 1000/天**。按 4 个 colo（实测见过 AMS / HKG 等）计算 colo 级缓存上限 = 4 × 1440 = 5760 次/天。

| 请求/天 | isolate/天 | DO 读（无缓存） | 占 DO 额度 | DO 读（有 colo 缓存） | 占 DO 额度 | KV 写/天 | 占 KV 写 | 占 Worker |
|---|---|---|---|---|---|---|---|---|
| 200 | 200 | 200 | 0% | 200 | 0.2% | 85 | 9% | 0% |
| 1 000 | 1 000 | 1 000 | 1% | 1 000 | 1.0% | 85 | 9% | 1% |
| 5 000 | 5 000 | 5 000 | 5% | 5 000 | 5.0% | 85 | 9% | 5% |
| 20 000 | 20 000 | 20 000 | 20% | **5 760** | **5.8%** | 85 | 9% | 20% |
| 50 000 | 50 000 | 50 000 | 50% | **5 760** | **5.8%** | 85 | 9% | 50% |
| 100 000 | 100 000 | 100 000 | **100%** | **5 760** | **5.8%** | 85 | 9% | **100%** |

三条结论：

1. **DO 读与 Worker 请求同阶**（1 请求 ≤ 1 次读），所以它**不可能比请求额度先撞顶**。真正先到顶的永远是「请求/天」这一条——也就是说，v8 的事实层不是上限的来源，**套餐本身才是**。
2. **colo 缓存把常数项压到 5.8%**：一旦流量超过 ~5 760 请求/天，DO 读的增长就停住了（因为同一 colo 60 s 内只读 1 次）。这就是为什么 §21 把 Cache API 定为「前提」而不是「优化」。
3. **KV 是唯一可能先撞的**：现在 85 写/天（`px:seed` 16 + `px:pool:<gen>` 5 + `snap` 30 + `usage:snap` 30 + `users`/`rtt`/`edge:pref` < 10），要**涨 11 倍流量**才会碰到 1000/天。KV 读约 500/天（只在订阅与 admin 路径），0.5%，完全不是瓶颈。

补充两点容易被忽略的额度：

- **DO CPU 时间**：一次 SQLite `SELECT` 约 1–3 ms，5 760 次/天 ≈ 17 s CPU/天，远低于 DO 的 CPU 预算；但**读必须是单条 SELECT**，不要在一次 facts 读里做 N 条查询（那会把 3 ms 变成 30 ms）。
- **付费计划下三条线都放大一个量级**，KV 写不再是瓶颈；但设计不应依赖它——v8 的每一条机制都要在免费计划内成立，这是从 7.x 一路踩过来的前提。

### 23.1 于是「预算」这条约束可以关掉了

前 8 轮一直挂在「不要超额度」上的三个未知量，现在都有了结论：

| 未知量 | 结论 | 依据 |
|---|---|---|
| facts 读会不会撞 DO 额度 | 不会，与请求同阶且缓存后 5.8% | 本节表 |
| `p` 的写入会不会撞 KV 写额度 | 不会，`p` 进 DO 而不是 KV | §22.4 |
| 探测/差分会不会撞子请求额度 | 不会，每轮 ≤2 connect、站点 30 分钟 3 批 | §19.5/§20 |

剩下的唯一硬约束是 **6 个并发 `connect()`** 与 **DO 内存 128 MB**，两者都已经有对应的设计（`PROBE_CONC=6`、`alive ≤ 256`）。

## 24. 吞吐这半条目标的可行性：差异小于噪声时，"最优节点"不存在

第 9 轮结尾留下的洞：`perf`（ttfb/bps）被规定为不跨 isolate 共享，而短命 isolate 的本地统计等于没统计（§22）——那么"为特定站点把吞吐路由到最优节点"还能不能成立？本轮用实测回答。

### 24.1 实验：两轮交错测量 6 条中继（各拉 700 KB）

同一顺序跑两轮（r1、r2），脚本 `.tmp-sim/thrlearn.mjs`：

| `91.215.153.143` | 615 | 893 | 1.45 |
| `193.181.211.185` | 935 | 784 | 0.84 |
| `45.136.117.194` | 883 | 727 | 0.82 |
| `45.147.250.39` | 608 | 1056 | 1.74 |
| `45.151.183.22` | 838 | 715 | 0.85 |

- 单轮内极差：r1 **1.54x**、r2 **1.48x**；
- 同一条中继跨轮摆动：**0.82–1.74x**（噪声带约 1.7x）；
- **Spearman(r1 排名, r2 排名) = −0.49**（排名在两轮之间不但不稳定，甚至反向）；
- 用 r1 学到的排名去选，期望只有随机选中的 **94%**——而"随机"的期望就是池子平均。

也就是说，**此刻这 6 条中继之间没有可学的差异**：真实差异（1.5x）比噪声（1.7x）还小。

对照第 6 轮那次：`91.215.153.143` 1642 KB/s vs `45.147.250.39` 275 KB/s，**6x**，远超噪声带——那次是可学的，也确实靠它把下载从 295 拉到 568 KB/s。

### 24.2 为什么差异会消失

我们一直在测的两段链路里，**客户端→边缘**这一段在多数时段是瓶颈（本机直连 2.7 MB/s，隧道 600–1000 KB/s）。当瓶颈在客户端腿时，所有中继的端到端速率都被压到同一个平台（600–1000），中继自身的容量差被淹没；只有客户端腿有余量（深夜/链路好）时，中继差异才显现成 6x。

这解释了一个反复出现的现象：**同一份代码，白天测"中继容量差 6 倍"，凌晨测"全都一样慢"**——不是中继变了，是量尺变了。

### 24.3 设计规则（吞吐部分）

| 规则 | 内容 | 依据 |
|---|---|---|
| **R1 噪声门** | 只有「同一中继连续两次样本比值 ≤1.5x」**且**「它与池内中位数的差距 ≥2x」时才记录 `cap`；否则记 `unknown` | 噪声带 1.7x > 1.5x 真实差 |
| **R2 记比值不记绝对值** | 存 `cap = 该中继速率 / 本次池内中位数`（0.5–2.0 截断），不存 KB/s | 绝对值随链路漂移（本机 0.3–2.7 MB/s） |
| **R3 无可学差异时不装优化** | `tput` 模式按 `ttfb` 排序，并在 `/health` 标 `thr: "link-bound"` | 随机已达最优 94% |

R2 是这次唯一需要新增的字段：`cap` 与 `ps` 同表，但语义是"相对容量"，只用于 `transport()` 的加权，不参与 `p` 的计算。

### 24.4 对 objective 第二半的诚实结论

> **"把吞吐路由到最优节点"只在「中继之间真有 ≥2x 差异」时才成立。**  
> 当客户端→边缘是瓶颈时，所有路由选择的效果都在噪声内——此时正确的动作是**不假装优化**，把事实告诉用户（`link-bound`），并把探测预算省下来。

这不算失败：第 6 轮那次 6x 差异下，同一套机制把下载从 295 提到 568 KB/s（1.9x），已经证明机制本身有效；本轮只是把它的**适用条件**量清楚了。

### 24.5 对 §16.5 的第三次修订

| 量 | 第 8 轮结论 | 本轮修订 |
|---|---|---|
| `ttfb` | 不共享（路径属性） | **维持不共享**——它完全由「isolate→中继→站点」这条路径决定 |
| `bps`（绝对 KB/s） | 不共享 | **改为 `cap` 相对比值，可共享**，但必须过噪声门（R1） |
| `p(host,relay)` | 共享（软概率） | 维持 |

于是 §16.5 的边界最终形态是：**路径性的东西（ttfb）永不共享；中继自身属性的东西（出口族 `eg`、相对容量 `cap`、站点通过率 `p`）共享为带衰减的软证据。** 这条边界现在有了三组实测支撑（§13.6/§13.9 出口族稳定、§22 本地统计无效、本节噪声带）。

## 26. 事实写入决策表（`commitFact` 的唯一入口）

§19（判定）、§22（通过率）、§24（容量）分别定义了「什么样的观测算证据」。落地时最容易写错的地方不是规则本身，而是**规则的先后顺序**：同一条观测往往同时满足两三条规则，先判谁决定它变成哪种事实。本节把它收敛成一张表 + 一套理由码，并用 19 条表驱动向量验证过（原型 `tools/exp-commitfact.mjs`，19/19 通过）。

### 26.1 规则（自上而下，命中即返回）

| 序 | 条件 | 结果 | 理由码 |
|---|---|---|---|
| 0 | 同键 60s 内已写过 | 丢弃 | `R_THROTTLED` |
| 1 | `echoFam ∈ {4,6}` 且 `down ≥ 64` | 写 `eg[relay]={fam,at}` | `ok` |
| 1b | `echoFam` 有值但 `down < 64` | 丢弃（回显没读全，族不可信） | `R_ECHO_SMALL` |
| 2 | `err ∈ {x509,tls,reset,timeout}` 且中继腿 | 写 `dead[relay]`（30 分钟） | `ok` |
| 2b | 同上但直连腿 | 丢弃（CF 边缘身份不可归属） | `R_DEAD_DIRECT` |
| 3 | `status === 429` | 丢弃（只做退避） | `R_429_BACKOFF` |
| 4 | 4xx 且同窗口（≤120s）无任何通道 `down ≥ 20KB` | 丢弃（站点级拒绝，分不清是谁的问题） | `R_SITE_LEVEL` |
| 5 | `tiny`（`down ≤ 2048` 且 `< 0.2×bigTypical`）且中继腿且有大响应对照且两批 ≥60s | 写 `blk[host|relay]`（90 分钟） | `ok` |
| 5b | `tiny` 但直连腿 | 丢弃（**永不**写封锁） | `R_DIRECT_NEVER` |
| 5c | `tiny` 但没有 ≥20KB 的对照 | 丢弃（缺对照，弃权） | `R_NO_BIG_PEER` |
| 5d | `tiny` 但只有一批 | 丢弃（单批不足以证明） | `R_SINGLE_BATCH` |
| 5e | `tiny` 且这条通道 3 分钟内出过整页 | 丢弃（自相矛盾） | `R_CONTRADICTORY` |
| 6 | `down > 0` 且非 tiny | 写 `ps[host|relay]`（`ok=1`） | `ok` |
| 6b | `down > 0` 但 tiny 且没走成 blk | **不写 ps**（宁缺勿错） | 见 5b–5e |
| 7 | `down === 0` 且无 `err` | 丢弃 | `R_NO_BYTES` |

> 顺序的三条硬理由：
> 1. **节流在最前**：它是唯一能挡住「观测风暴」的闸门，放后面等于先算完再丢。
> 2. **429 在 tiny 之前**：429 的响应体天然很小（有的站点回 0 字节），不先拦会被判成封锁证据。
> 3. **站点级在 tiny 之前**：全通道 4xx 时我们**无法区分**「这个中继被封」与「站点拒绝所有人」，此时任何 `blk` 都是猜的（7.57 就是这么把池子标死的）。

### 26.2 理由码字典（也是 `/health` 的计数器键）

| 码 | 含义 | 运维解读 |
|---|---|---|
| `R_THROTTLED` | 60s 内重复观测 | 正常，说明节流在工作 |
| `R_ECHO_SMALL` | 回显只读到 <64B | 回显服务或中继异常，查 `eg` 命中率 |
| `R_DEAD_DIRECT` | 直连腿失败 | 正常（直连腿不写事实） |
| `R_429_BACKOFF` | 站点限流 | 该站点应降频，不是封锁 |
| `R_SITE_LEVEL` | 全通道 4xx | **站点级**问题：不要动中继池 |
| `R_DIRECT_NEVER` | 直连腿拿到 tiny | 正常（族不可归属） |
| `R_NO_BIG_PEER` | 缺对照整页 | 探测预算不足或同窗口没发对照腿 |
| `R_SINGLE_BATCH` | 只有一批 | 下一批再来（≥60s） |
| `R_CONTRADICTORY` | 同通道刚出过整页 | 说明是请求级抖动，不是封锁 |
| `R_NO_BYTES` | 一个字节都没拿到且非连接错误 | 罕见的静默失败，值得单独看 |

### 26.3 表驱动向量（19 条，与原型一一对应）

1. 回显 v4 写 `eg`；2. 回显太小丢弃；3. `tiny`+对照+两批 → `blk`；4. 403 tiny 无对照 → `R_SITE_LEVEL`；5. 200 tiny 对照只有 5KB → `R_NO_BIG_PEER`；6. `tiny` 只有一批 → `R_SINGLE_BATCH`；7. 直连腿 tiny → `R_DIRECT_NEVER`；8. 429 → `R_429_BACKOFF`；9. 全通道 415 → `R_SITE_LEVEL`；10. 业务 415 + 对照整页 → `ps(ok=1)`；11. 正常大响应 → `ps(ok=1)`；12. 证书错 → `dead`；13. 直连证书错 → `R_DEAD_DIRECT`；14. 3 分钟内同通道出过整页 → `R_CONTRADICTORY`；15. 60s 内同键 → `R_THROTTLED`；16. `api.github.com` 1277B/典型 1277 → `ps`；17. `example.com` 932B/典型 932 → `ps`；18. 737B 且典型未知（只按绝对值）→ `blk`；19. 零字节 → `R_NO_BYTES`。

### 26.4 写这张表时才发现的三件事

1. **`tiny` 的响应不能写 `ps`**。我最初的草稿是「非 blk 就记 `ps(ok=0)`」，但 `example.com` 这类真小站、以及被限流时的 200 空体都会因此被记成失败，反而把好通道排到最后。现在的口径是：**没把握就什么都不写，只加计数**（C 级证据）。
2. **`R_SITE_LEVEL` 与 `R_NO_BIG_PEER` 必须分开**。前者是「我们知道发生了什么事」（站点拒绝所有人），后者是「我们不知道」（探测腿不够）。混用一个码会让看板永远分不清「该扩探测」还是「该换站点策略」。
3. **`R_CONTRADICTORY` 是 7.57 的教训固化成规则**：同一条通道 3 分钟前还出过整页，现在回 737B，只可能是请求级抖动，写进 `blk` 就是 90 分钟的误伤。

## 27. 订阅结构（可执行原型 + 12 条断言）

> 原型：`node tools/exp-subv8.mjs`（12 组开关组合，全部通过）。它只渲染 + 断言，不碰 `src/`。

### 27.1 结构

```
🅰 模式 (select)
├── 🚀 吞吐优先 (fallback)          ← 客户端按顺序试，前一个全挂才用后一个
│   ├── 📡 目标实测 tput  (url-test, ?tu= 才发)
│   ├── 🌐 入口竞速 tput  (url-test: 8~16 个边缘 IPv4 → https://<host>/health)
│   ├── 🔁 中继竞速 tput  (url-test: 3~6 条中继 → ?rx=<ip>&px=1)
│   └── 📛 域名入口 tput  (select: 1 条，走域名，可能落 v6)
└── ⚡ 速率优先 (fallback)         ← 同构，但成员全是 lat 模式的条目
🎯 手动 (select)                   ← 全部条目平铺
```

三条设计上的硬要求（原型里都断言了）：

1. **每个模式一套竞速组**，不能两种模式共用一个 `🌐 入口竞速`——共用会让「吞吐」组里混进取速模式的条目，健康检查的结果也不可复用。
2. **每个模式至少有一条域名回退**。`?e=0&r=0` 时模式组里只剩它；任何成员为空的 fallback 组在客户端里等于「整组不可用」。
3. **组成员的写法是名字**，不是组对象。第一版我把 `{name,type,proxies,...}` 直接塞进 fallback 的成员列表，客户端会报「成员不存在」，整链失效。

### 27.2 开关矩阵（原型实测条目数）

| 开关 | 条目 | 组 | 说明 |
|---|---|---|---|
| 默认（vless，ei=8） | 30 | 10 | 每模式 8 入口 + 6 中继 + 1 域名 |
| `?e=0` | 14 | 8 | 只留中继 + 域名 |
| `?r=0` | 18 | 8 | 只留入口 + 域名 |
| `?e=0&r=0` | 2 | 6 | 只剩域名（最小形态） |
| `?ei=16` | 34 | 10 | 预算把中继压到 3 条 |
| `?ei=4` | 22 | 10 | |
| `?p=tj` | 30 | 10 | Trojan 单协议 |
| `?p=both` | 32 | 10 | 预算自动把 ei 压到 4、中继压到 3 |
| `?tu=https://x.com/` | 32 | 12 | 多 2 条目标实测条目 + 2 个组 |
| `?tu=…&?e=0` | 16 | 10 | |
| `?full=1` | 46 | 10 | 预算 60，ei 放到 16 |
| 只发 `lat` 模式 | 15 | 6 | |

预算算法：`perMode = (budget - modes) / modes`，再扣 1 条域名回退，剩余按 `入口 : 中继 = 8 : 6` 分；`?p=both` 时每个 (模式, 协议) 组合各自占一份，所以预算自动把条数压下来（**先算后分**，否则 both 会直接冲到 57 条）。

### 27.3 断言（12 组组合，16 类检查）

1. 每个组的成员都存在（条目名或组名）。
2. 模式组是 `fallback`，顺序固定为 目标实测 → 入口竞速 → 中继竞速 → 域名入口。
3. 组成员名与 `?e=0/?r=0` 一致（关掉的组不出现）。
4. 每个 `url-test` 组都有 `url` / `expected-status` / `interval` / `tolerance`。
5. `url-test` 组必须 `lazy: false`（否则客户端从不测速，等于随机）。
6. `url-test` 组至少有 1 个成员。
7. 没有条目用 80 端口（服务端 `checkTarget` 直接拒）。
8. 所有条目都有 `ip-version: ipv4` 与 `ed=2560`（首包和 TLS 一起走）。
9. SNI 必须是域名，不是 IP。
10. 中继条目必须带 `rx=`（否则钉不住，服务端会自己重选）。
11. 入口条目的 server 必须是 IPv4 字面量；域名条目的 server 必须是域名。
12. 条目名、组名都不重复。
13. 条目总数 ≤36（`?full=1` ≤60）。
14. `?p=tj` 时不能混进 vless 条目（反之亦然）。
15. 每个模式下都有域名回退。
16. `?tu=` 时目标实测组必须是 `url-test` 且 `url` 就是传入的地址。

### 27.4 健康检查的真实代价（必须写进订阅文档）

客户端 url-test 是**真发请求**，不是本地探测。默认配置下：8 入口 + 6 中继 = 14 个成员 × 2 个模式 = 28 个成员，`interval: 180` ⇒ 每天 13,440 次请求。这些请求会打到 Worker（`GET /health`，1KB 量级）并占用中继连接。

建议的节奏（写进订阅生成器的默认值）：

| 组 | interval | 说明 |
|---|---|---|
| `🌐 入口竞速` | 180s | 只打自己的 `/health`，便宜 |
| `🔁 中继竞速` | 300s | 走中继，贵；成员限制 3–6 条 |
| `📡 目标实测` | 300s | 打真站点，成员限制 ≤4 条，且只在显式 `?tu=` 时开 |

即使按这个节奏，最坏也是每天约 8,000 次 Worker 请求（占免费额度 8%），可接受；但它确实是「用客户端流量换准确率」，所以 `?tu=` 必须是**显式开启**而不是默认。

## 28. DO 事实表：语义与代价的实测（原型 `tools/exp-facts-db.mjs`）

> 用 `node:sqlite`（Node 24 自带）在内存库里跑同一套 DDL/DML，先把 **SQL 语义** 钉死；平台限额另按官方文档核对（见 28.3）。12 条断言全部通过。

### 28.1 表与语句（与 §17.2 一致）

```sql
CREATE TABLE facts (
  kind TEXT NOT NULL,   -- dns | eg | ps | blk | dead | cap
  k    TEXT NOT NULL,   -- dns: host  eg/dead/cap: relayIP  ps/blk: host|relayIP
  at   INTEGER NOT NULL,
  j    TEXT NOT NULL,   -- 短键 JSON
  PRIMARY KEY (kind, k)
) WITHOUT ROWID;
CREATE INDEX idx_facts_at ON facts (kind, at);   -- 淘汰按 (kind, at) 扫，必须有
```

```sql
-- 唯一写入口：旧证据不许覆盖新证据
INSERT INTO facts (kind, k, at, j) VALUES (?, ?, ?, ?)
ON CONFLICT (kind, k) DO UPDATE SET at = excluded.at, j = excluded.j
WHERE excluded.at > facts.at;
```

### 28.2 实测（12 条断言）

| # | 断言 | 结果 |
|---|---|---|
| 1 | 首次写入 `changes() = 1` | ✅ |
| 2 | **更旧的 `at` 到达时被忽略**（两个 isolate 乱序上报） | ✅ `changes() = 0`，行内容不变 |
| 3 | **相同 `at` 也被忽略**（严格 `>`，避免两个 isolate 乒乓覆盖） | ✅ `changes() = 0` |
| 4 | 更新的 `at` 覆盖 | ✅ `changes() = 1` |
| 5 | `ps` 的 `host|relay` 复合键不与 `eg` 冲突 | ✅ |
| 6 | `x.com` 与 `x.com.cn` 是两个键（前缀不误伤） | ✅ |
| 7 | 淘汰只删本 `kind`、按 `at` 升序 | ✅ 22 → 18 条，删掉的是最旧的 4 条 |
| 8 | `since` 过滤 + `LIMIT` | ✅ 只回 `at > since` 的行 |
| 9 | 单条 `ps` 行的 JSON < 40B | ✅ |
| 10 | 1000 次 upsert | 5.7 ms（进程内 0.006 ms/次） |
| 11 | 一次 `since` 读 1000 行 | 1.11 ms |
| 12 | 1000 行的整库 JSON | **81.9 KB** |

进程内的 0.006 ms 只是**下限**：真实 DO 的代价在「一次请求一个 RPC 往返」和计费行数，不在 CPU。

### 28.3 平台限额（官方文档，2026-11-13 版）

| 项 | Free | 备注 |
|---|---|---|
| 每个 DO 存储 | **1 GB** | 账号合计 5 GB；Paid 是 10 GB/DO |
| 单行（键+值） | 8 MB | 我们远低于 |
| 每表列数 | 100 | 我们 4 列 |
| 每请求出站连接 | 6 | 与 `SC.PROBE_CONC = 6` 同源（§19.5 的「每轮 ≤2 connect」要在这个总预算内） |
| 单 DO 软上限 | 1000 req/s | 超了回 `overloaded` |
| 存储写满 | `SQLITE_FULL` | **写失败但读/删仍可用** |

来源：<https://developers.cloudflare.com/durable-objects/platform/limits/>

### 28.4 实测暴露的一处设计错误（§17.3 的「< 8KB」不成立）

§17.3 原来写「全量 `GET /meter/facts?since=0` 压缩后 < 8KB」。实测 **1000 行 = 81.9 KB**，而各 kind 的上限之和是 `512 + 512 + 1024 + 256 + 256 + 512 = 3072` 行 ⇒ 全量快照最坏约 **250 KB**，比当初的估计大 30 倍。

- 稳态不需要担心：真实规模是 8 条中继 × 4 种 kind + 几十个站点 ≈ 1–2 KB。
- 但**冷 isolate 首次读**必须按 kind 分片（`?s=eg` / `?s=ps` …）或只读 `since`，否则一次 250 KB 的 JSON 解析会吃掉几十毫秒 CPU（免费计划只有几十毫秒）。
- 结论：把 §17.3 的全量读改成「**按 kind 分片 + since**」，单次目标 < 8 KB 是对**单个 kind** 说的，不是对整库。

### 28.5 落地时的四条纪律

1. **写入必须批量**：一次 `POST /meter/facts` ≤64 行（§17.3），否则每个观测一个 RPC，请求数直接翻十倍。
2. **`SQLITE_FULL` 必须捕获并降级**：读/删仍可用，所以先删过期行再重试一次，仍失败就当作「无事实」继续选路（绝不抛给用户）。
3. **淘汰要在写之前跑**：`SQLITE_FULL` 之后删也能救，但那时写入已经失败过一次，探测白跑。
4. **`since` 单调**：客户端记住 `lastSince`，只在成功应用后前移；否则一次失败会把区间丢掉（与 §20.5「全有或全无」一致）。

## 29. 验收口径：四套策略的端到端对照（原型 `tools/exp-v8sim.mjs`）

| 策略 | x 首连 | x 冷启动 | 无 AAAA 站点 | 普通站 | 业务 4xx 站 |
|---|---|---|---|---|---|

## 30. 冷启动：facts 的缓存命中率是**流量的函数**，不是可调参数

> 原型 `tools/exp-coldstart.mjs`（复用 `tools/exp-v8sim.mjs` 的模型）。上一轮把冷启动的 84.3% 归因到「拿不到事实」，这一轮把「拿不到」拆开，看它到底由什么决定。

### 30.1 命中率的来源：不是设计出来的，是泊松算出来的

缓存只被真实请求填充，TTL 内只要有**一次**请求就命中：

```
命中率 ≈ 1 − exp(−λ · TTL / 60)
```

`λ` = 单个 colo 每分钟的用户请求数。这条式子的含义很硬：**低流量时缓存必然不命中**，无论我们把 TTL 调多长、把代码写多优雅。

### 30.2 扫描结果（v8 策略，x 类站点）

| λ (请求/分) | TTL | 缓存命中 | 首连命中（200ms 预算） | 首连命中（0ms） | 冷 isolate 命中 |
|---|---|---|---|---|---|
| 0.2 | 30s | 9.5% | 91.2% | 82.3% | 64.7% |
| 0.2 | 60s | 18.1% | 92.1% | 83.5% | 70.2% |
| 0.2 | **120s** | 33.0% | **92.6%** | 85.6% | 72.8% |
| 0.5 | 120s | 63.2% | 95.8% | 92.1% | 87.7% |
| 1 | 60s | 63.2% | 95.8% | 92.1% | 87.7% |
| 2 | 60s | 86.5% | 97.2% | 96.0% | 95.3% |
| ≥5 | 任意 | ≥99% | 97.9% | 97.9% | 96.8% |

（完整 21 行见脚本输出；表里只留拐点。）

### 30.3 三条结论

1. **200 ms 阻塞预算几乎免费**：λ=0.2 时 91.2% vs 82.3%（值 9 个点），λ≥5 时两者都是 97.9%（代价 0）。因为代价只落在「缓存未命中的冷 isolate」，而它在高流量下本来就不存在。⇒ §20.2 的 200 ms **保留**。
2. **TTL 应该从 60 s 提到 120 s**：λ=0.2 时命中率 18.1% → 33.0%、首连 92.1% → 92.6%；λ=0.5 时 39.3% → 63.2%、首连 94.1% → 95.8%。高流量下没有代价（都到 99%+）。⇒ 改 §21 里「colo Cache（60s）」为 120s。
3. **天花板是 97.9%，不是 100%**：就算命中率 100%，残差来自「25% 中继族对但站点拒 + 8% 探索 + 2% 连不上」。⇒ **96–98% 的承诺在 λ≥2/分 时才成立**，低流量时应承诺 91–95%。

### 30.4 一个比「提高命中率」更有效的方向

冷 isolate 的 64.7%（λ=0.2）说明：**事实不是唯一缺的东西**——冷 isolate 连「哪 6 条中继活着」都没有。对它来说 `eg` 全空、`ps` 全空，只能盲选（退化到 A 的 40%）。

⇒ 真正该给冷 isolate 的不是更多事实，而是**更短的到达路径**：把「本 colo 近 30 分钟最好用的 3 条中继」直接写进订阅条目（§27 的 `🔁 中继竞速` 已经在做这件事，只是它由客户端 url-test 决定，不占服务端预算）。

> **§31 修正了本段的一半。** `🔁 中继竞速` / `🌐 入口竞速` 的 `url:` 都是 `https://<host>/health`，只能证明「这条入口/中继能到 CF」，**看不到出口族**；仿真实测它与「完全没有竞速组」逐位相同（52.6% / 54.6% / 47.8%）。要修冷启动必须用 `?tu=<站点>` 的目标实测组（`target` 组：6 成员 + 连测 2 次 → 92.6%，10 成员 → 97.4%），代价是每 5 分钟几条真实请求。详见 §31。

### 30.5 验收口径（写进 §14 的承诺表）

| 场景 | 承诺 | 依据 |
|---|---|---|
| λ ≥ 2/分、暖 isolate | 96–98% | §30.2 的 97.2–97.9% |
| λ ≥ 2/分、含冷启动 | 94–97% | 同上，冷启动占比 20% |
| λ < 0.5/分（个人使用） | 91–95% | §30.2 的 92.1–92.6% |
| 业务 4xx 站点 | ≥97% 不误伤 | §29.2 的 98.2% |

## 31. 客户端竞速组能不能补上冷启动？（能，但只有 `?tu=` 一种写法有效）

§30.5 把「冷 isolate 的 64.7%」指向客户端订阅组，说让它去补。这一节把这件事量化，结论**修正了那句话的一半**：`/health` 型竞速组在这件事上**信息量为零**，只有把健康检查指向真站点的 `?tu=` 组才有效。

### 31.1 为什么 `/health` 组没用

`🌐 入口竞速` 与 `🔁 中继竞速` 的 `url:` 都是 `https://<host>/health` —— 请求打的是我们自己的 Worker。它只能回答「这条入口/中继能不能到 CF」，**回答不了「它的出口是 v4 还是 v6」**，而后者才是 x 类站点成败的决定因素（§13.6：v4 出口 6/6、v6 出口 2/16）。

仿真实测（`tools/exp-clientrace.mjs`）：`health` 组与「完全没有竞速组」的结果**逐位相同**（52.6% / 54.6% / 47.8%，成员数 4/6/10）——因为「所有成员都健康」意味着选择退化成盲选。

### 31.2 `?tu=` 组有效，但必须配「连测通过」

坏中继（v6 出口、或族对但站点拒）**单次测试有 12.5% 的概率蒙对**（§13.8 的 2/5 现象就是它），所以「测一次通过就算健康」会让它频繁混回候选池。要求连续 N 次通过才算健康，能把蒙对概率压到 `0.125^N`。

| 组类型 | 成员数 | 连测通过 | 平均成功率 | 最差种子 |
|---|---|---|---|---|
| none（无组） | 6 | 1 | 54.6% | 46.7% |
| health | 10 | 1 | 47.8% | 30.8% |
| target | 4 | 1 | 82.1% | 70.0% |
| target | 6 | 1 | 85.3% | 72.1% |
| target | 6 | **2** | **92.6%** | 80.8% |
| target | 10 | 1 | 89.6% | 85.4% |
| target | 10 | **2** | **97.4%** | 95.8% |
| target | 10 | 3 | 98.7% | 97.5% |

参数：好中继 37.5%、坏中继 p=0.125、测试间隔 180 s、请求间隔 120 s、每周期状态翻转 2%、6 小时 × 8 种子。

### 31.3 四条结论

1. **`health` 组与无组等价** ⇒ 现在的 `🌐 入口竞速` 只能剔除「死入口」，不能提高站点成功率。它的价值在别处（入口 IP 被干扰时快速切换），不要指望它修冷启动。
2. **`?tu=` 组是唯一端到端证据**，且必须 `连测 ≥2 次通过才健康`（在 mihomo 里用 `expected-status: 200` + `interval` 实现不了「连续 N 次」，需要**两条同名组串联**或用 `fallback` 里先 `url-test` 再 `fallback`；实现细节见 §31.5）。
3. **成员数是最便宜的那个旋钮**：6 → 10 让 92.6% → 97.4%（好中继被抽到的概率按比例上升）。
4. **代价是真实请求**：10 成员 × 180 s = 4800 次/天到真站点；默认取 **6 成员 × 300 s ≈ 1728 次/天**（≈92%），重度用户可 `?tu=&rn=10&ti=180` 换 97%（≈4800 次/天）。这是**唯一一处用流量换成功率**的地方，必须让用户知情。

### 31.4 与服务端 v8 的关系（别重复计功）

- 服务端 v8 已经在**单请求内**把出口族选对（§29 的 94.7%），客户端组能补的是**冷 isolate** 那一段（84.3% → 97%+，§29/§30）。
- 两者不是简单相加：暖 isolate 上客户端组只会增加切换抖动；冷 isolate 上它才是主力。
- 因此订阅里 `?tu=` 组**应当可选**（默认关），并把「开它意味着每 5 分钟几条真实请求」写进说明。

### 31.5 mihomo 里怎么表达「连测 2 次通过」

客户端只有「本次健康检查成功/失败」这一个布尔量，没有「连续 N 次」原语。可行的两种写法：

1. **双层 `fallback`**：内层 `url-test`（`interval: 180`、`tolerance: 0`）在上游失败时整体判失败，外层 `fallback` 只有在内层给出可用成员时才使用 —— 效果是「至少要有一轮成功」，等价于 confirm=1，**不是 confirm=2**。
2. **显式两组**：`x-t1`（浅测）与 `x-t2`（深测，`interval` 更长且 `url` 带 `?probe=2` 让服务端多打一次），组内 `fallback: [x-t2, x-t1]` —— 用服务端返回的 `probe=2` 结果模拟「第二次确认」。

**诚实结论**：客户端侧只能做到 confirm≈1，表里的 confirm=2/3 需要服务端配合（在 `/health?probe=2` 里对同一中继再打一次站点并把结论合并返回）。§18 的 `decide()` 测试向量已经覆盖「同一请求内多次采样」，服务端侧实现成本很低；客户端侧则不必改。

## 32. 冷 isolate 的并发撞车：**瓶颈是 connect 名额，不是 facts 读**

§21 断言「加 colo 缓存后 20/40/80 并发都能在 200 ms 内拿到 facts」。那只是**排队模型**：它只算了 DO 的串行读，没算同一批连接还要抢 `connect()` 名额。这一节把两者放进同一个离散事件模型（`tools/exp-concurrency.mjs`），结论是 §21 那句话**结论对、归因错**。

### 32.1 模型

- K 条用户连接在 100 ms 内陆续到达一个冷 isolate。
- facts 读：DO 单实例串行 15 ms/次；colo 缓存命中 2 ms；命中率 70%（§30）。
- `connect()`：全局 6 个并发名额（免费计划硬限制，与 `SC.PROBE_CONC` 同源），每次 250 ms。
- 冷 isolate 里约 35% 的连接会落到「出口族未知」的中继上，需要一次 `connect()` 探测。

### 32.2 结果（p50/p95 毫秒，12 种子取中位）

| 并发 | A 每条各自读 | B single-flight + 200ms 预算 | C 不阻塞（后台读） | **D B + 每波探测 ≤2** |
|---|---|---|---|---|
| 1 | 15 / 15 | 15 / 15 | 0 / 0 | 15 / 15 |
| 5 | 2 / 252 | 2 / 250 | 0 / 250 | 2 / 250 |
| 20 | 2 / 442 | 0 / 433 | 0 / 433 | **0 / 250** |
| 40 | 2 / 678 | 0 / 675 | 0 / 671 | **0 / 250** |

### 32.3 四条结论

1. **p95 由 `connect()` 名额决定，不是 DO 读。** 40 并发 × 35% = 14 次探测 × 250 ms ÷ 6 名额 ≈ 583 ms 排队，正好对应 A/B/C 的 671–678 ms。
2. **探测限流是唯一能压低 p95 的手段**：每波最多 2 次探测，40 并发从 675 → **250 ms**（少了一整轮排队）。超出的连接不是「等」，而是**直接用事实里最稳的那条**（`dead`/`blk` 已排除），代价是牺牲一点「探索新中继」的多样性。
3. **single-flight 的收益有界但要保留**：A 与 B 在高并发下只差 9 ms（差距被探测队列掩盖），但在「探测需求低、缓存未命中」的形态（低并发、冷、`cacheHit=false`）下它能把 N 次 15 ms 串行压成 1 次。它的价值是**消除尾部**，不是提升中位。
4. **不要把 facts 读做成「每条连接各读一次」**：A 在 40 并发下把 DO 队列推到 40×0.3×15 = 180 ms，与探测队列叠加后 p95 反而最高。

### 32.4 对设计的修改

- §8 的预算要新增一格：**`probeWave = 2`**（每波用户连接最多 2 次 `connect()` 用于探测；拨号本身不计入，因为它是请求的必经路径）。原预算表只有「准入 / 审计 / 退款 / 入口」，漏了这格。
- §20.2 的三档自愈里，`cold+empty` 的「后台补 1 条回显」也要受 `probeWave` 约束，否则一批冷连接会把名额吃干（这一条与 7.86 修过的 socket 泄漏是同一类问题：名额被占着比被用掉更糟）。
- `readFacts` 的四条契约（§20.5）保持不变，补一条：**同一 isolate 内并发读必须共享同一个 Promise**（single-flight），否则等于策略 A。
- 观测：`/health` 加 `probeWaveUsed` 与 `connectWaitMs`（当前波次等待名额的累计时长）。这两个数是「并发是否撞车」的唯一直接证据。

### 32.5 模型没覆盖的东西（诚实边界）

- **拨号与探测共享名额**：真实连接里每条用户连接至少 1 次 `connect()`（拨中继或直连），所以 6 名额其实只够 6 条并发用户连接**同时**拨号。40 并发在真实世界会被切成多批 —— 这一节只比较相对差异，不代表 40 并发能同时首字节 250 ms。
- **DO 的 1000 req/s 软上限**：本节 K≤40 远没碰到。
- **`connect()` 的失败率**：失败也占 250 ms（超时是 2500 ms，见 7.84），失败会放大排队。§19.5 的「每轮 ≤2 connect」是同一个约束的另一面。

```powershell

```

断言：40 并发下「各自读」p95 > 300 ms（证明模型确实撞车）、single-flight 优于各自读、探测限流不劣化 p95、single-flight 的 p50 被 200 ms 预算兜住。
## 33. 端到端验收：成功率与延迟必须放进同一条时间轴（原型 `tools/exp-e2e.mjs`）

§29 只算成功率、§32 只算延迟，两套模型各自成立但**没有交叉验证**。本节把它们合成一个事件循环：同一条请求既记录「有没有拿到真页面」，也记录「花了多久」。这也是唯一能回答「上线后用户体感是变好还是变差」的口径。

### 33.1 模型

- 700 波 × 3 条 = 2100 条请求，波间隔 1 s；20% 落在冷 isolate，冷 isolate 70% 命中 colo 缓存。
- 8 条中继：3 条 v4 出口（x 类站点 p=1.00）、1 条「族对但站点拒」（p=0.125）、4 条 v6 出口（p=0.125）。
- 基线 TTFB 2500 ms ± 600 ms 抖动；被封锁页 60 ms（4xx 很快，这不是好事，见 §33.3）。
- `connect()` 6 名额 × 250 ms；每波探测 ≤2（§32）。
- v8 用共享 `ps`（EWMA，§22）+ `eg` 族偏置 + 8% 探索。

### 33.2 结果（8 种子取中位，单位 ms）

| 策略 | 成功率 | p50 | p95（全体） | **p95（只算成功）** | **成功且 ≤3 s** |
|---|---|---|---|---|---|
| base（盲选） | 45.6% | 310 | 3218 | 3287 | **32.4%** |
| eg（只按出口族） | 74.8% | 2555 | 3270 | 3288 | 53.9% |
| **v8** | **95.6%** | 2714 | 3292 | 3294 | **68.2%** |

### 33.3 三条结论

1. **v8 让「成功且 ≤3 s」从 32.4% 翻到 68.2%**。这是唯一同时包含成功与速度的指标，也是唯一能拿来对用户承诺的数字（§30.5 的分档承诺应该用这个口径重述）。
2. **延迟必须只在「成功请求」之间比**：全体 p95 从 3218 → 3292（+74 ms）看着像变慢，其实是被封锁页只要 60 ms 造成的**选择偏倚**——成功率从 45.6% 涨到 95.6%，慢的样本占比变大，p95 自然上升。只看成功请求，p95 是 3287 → 3294（**+7 ms**），即 v8 **没有让成功的请求变慢**。
   - 落地要求：`/health` 与 `?rt=` 的延迟指标必须拆成 `p95all` 与 `p95ok` 两个，并把 `good3s`（成功且 ≤3 s）作为一等指标。只有一个「平均延迟」的数字，在成功率变化时无法解读。
3. **`eg` 单独上是中间态，不是终点**：74.8% 说明它把族选对了，但「族对但站点拒」的那 1 条会稳定吃掉约 25%——与 §21「`eg` 不能单独上」的结论一致，也解释了为什么 §29 的 B 策略（族 + 确定性）反而更差：确定性选择会**永久钉死**在那一条上。

### 33.4 与既有模型的交叉校验

| 结论 | 独立来源 | 本节复现值 | 偏差 |
|---|---|---|---|
| 盲选成功率 | 生产实测 8/20 = 40% | 45.6% | +5.6 pt（模型里 8 条中继的 p 是均匀的） |
| v8 成功率 | §29 端到端仿真 94.7% | 95.6% | +0.9 pt |
| 冷启动 200 ms 预算收益 | §30 扫描 9 个点 | — | 未在本模型内单独拆 |

三个独立模型给出同一量级的结果，是这套设计目前**唯一**的可信度来源；任何新结论都必须能被其中至少两个同时复现，否则只是单个模型的产物。

```

断言：基线 <60%、v8 比基线高 30 个点以上、**成功请求 p95 不劣于基线 60 ms 以上**、`good3s` 比基线高 30 个点以上。
## 34. 迁移风险：六步里只有一步真正改变成功率，其余必须用别的指标验收

前面 13 个原型都在验证「设计能不能成立」，没有回答「按 §17 分步上线，每一步会不会退」。这一节把六步做成同一套模型里的开关（`tools/exp-migration.mjs`），每步只加一件事，其余保持上一步的状态——与真实发版节奏一致：一次只动一处。

### 34.1 结果（700 波 × 3 条，冷 20%，8 种子中位）

| 步骤 | 内容 | 成功率 | `good3s` | `p95ok` | 空候选 | DO 读 | DO 写 |
|---|---|---|---|---|---|---|---|
| S0 | 现状（7.86） | 44.6% | 32.0% | 3290 | 0 | 0 | 0 |
| S1 | 只加事实层（`eg`/`dns` 进 DO），**选路不变** | 45.5% | 32.2% | 3294 | 0 | 44 | 0 |
| S2 | 选路开始用 `eg` 族偏置 + 共享 `ps` | **95.9%** | **68.1%** | 3294 | 0 | 44 | 2100 |
| S3 | 加 `blk` 硬过滤 | 97.8% | 69.3% | 3294 | 0 | 44 | 2100 |
| S4 | 探测波次限流 + 冷启动 200 ms 阻塞读 | 97.8% | 69.3% | 3297 | 0 | 41 | 2100 |
| S5 | 客户端 `?tu=` 目标实测组 | 97.8% | 69.3% | 3297 | 0 | 41 | 2100 |

逐步增量：`S0→S1 +1.0 pt`、**`S1→S2 +50.4 pt`**、`S2→S3 +1.9 pt`、`S3→S4 0`、`S4→S5 0`。

### 34.2 四条结论

1. **价值几乎全在 S2**（+50.4 pt）。S1 是纯地基（+1.0 pt 属噪声），S3 是锦上添花（+1.9 pt），S4/S5 在成功率上是 **0**。
2. **S1 的验收标准必须是「指标不变」**，而且要真的不改选路——一旦在 S1 就让选择依赖 `eg`，就会退化成 §29 的 B 策略（14.3%，比盲选还差，因为族先验 + 确定性会永久钉死在「族对但站点拒」的那条上）。这条是这个迁移计划里最容易做错的一步。
3. **S3 的收益不是成功率，是「少发注定失败的请求」**。`ps` 已经把那条中继的权重压低了，`blk` 只是把它的**剩余 2%** 再削掉一点；它的真正价值是省流量与减少超时等待。
4. **S4/S5 的成功率增量是 0，因为它们的收益在延迟与冷启动**。这一模型里冷 isolate 只占 20%、且 70% 命中缓存，所以两个步骤的收益被稀释；要用「冷 isolate 的 `good3s`」与「`p95ok`」单独验收（§30/§31 已给出各自的数字），不能拿全局成功率来判它们「没用」。

### 34.3 每步的回滚线（写进 §11 的开关表）

| 步骤 | 观测指标 | 回滚条件 |
|---|---|---|
| S1 | 全局 `firstPage` | 掉 >6 pt ⇒ 说明「不改选路」没做到（检查是否有代码路径读了 `eg`） |
| S2 | 全局 `firstPage` | 上线 2 小时未见 +30 pt ⇒ `ps` 没生效（先查 A 级证据是否被闸门全拒） |
| S3 | 空候选率 / `leastBad` | 空候选 >0.1% 请求 ⇒ `blk` 键或 TTL 写错（§15 D1 复现） |
| S4 | `p95ok` | 涨 >60 ms ⇒ 阻塞读吃掉了收益，退回「不阻塞 + 后台补」 |
| S5 | 客户端 `?tu=` 组内的成功次数 | 组内成功率不涨 ⇒ 关掉（它是唯一用真实流量换成功率的步骤，不值得就关） |

**共同纪律**：每步都要能单独关掉（配置开关而不是回滚发版），且「关掉」后行为**逐位等于上一步**——否则出问题时无法二分定位。

### 34.4 这一轮暴露的一个新问题：`ps` 写入必须批量

模型里 2100 条请求产生 **2100 次 DO 写**。按天推到 10 万请求，就是 10 万次 DO 请求——正好撞上免费额度的 10 万/天（§23）。所以 S2 落地时必须带批量写入：

- 每 isolate 攒 **16 条样本**或 **60 秒**（先到者）写一次，写入量降到 1/16 ≈ 6250/天；
- 批量写失败不影响选路（`ps` 是可丢的软证据），但要计入 `psDrop` 计数器；
- 同一 `host|relay` 在一个批次内只写最终值（EWMA 已在内存里合并），避免「一次请求一行」。

这条在 §22.4 的 schema 里没写，是这一轮才发现的（写量与读量不同：读能被缓存吸收，写不能）。

### 34.5 诚实边界

- 模型假设 `blk`/`ps` **没有证据滞后**：真实世界里新中继要失败若干次才被压低，所以 S2 的 +50.4 pt 是**上界**；7.86 的生产经验是「冷 isolate 前几条请求仍会撞坏出口」，与这里的 S5 讨论一致。
- 模型没有建模「`ps` 学错」：如果某个好中继因为一次偶发失败被压到 0.5，需要若干次成功才恢复（§22.4 的 `n*0.98` 衰减就是为此）。
- 空候选在真实系统里还有一个来源没建模：`alive` 池本身为空（冷 colo + 无缓存），此时 `leastBad` 也救不了，只能直连。

## 35. 学错了能不能爬回来？（D12：`ps` 的窗口是单调增长的，惩罚几乎不可逆）

§22 定的更新式是 `n' = min(255, n*0.98 + 1)`。它的意图是「样本越多越平滑」，但副作用是：**窗口 n 只增不减，一次坏运气会把好中继按住很久**。这一节量化它（`tools/exp-recovery.mjs`）。

### 35.1 恢复速度（连续 k 次失败后，重新回到 score 前 3 需要几次成功）

| 有效窗口 | k=2 | k=3 | k=5 | k=8 |
|---|---|---|---|---|
| n≈64（nCap 255/64/32 都一样） | 8 | 17 | **29** | **>40** |
| n≈16（nCap=16） | 7 | 13 | 20 | 26 |

为什么 nCap=64/32 与 255 效果相同：n 从 16 起步、每次只按 `n*0.98+1` 增长，在几百次观测内根本到不了上限——**真正起作用的是起始 n 与增长规律，不是那个 255**。这条写进 §22.4 时必须改成「n 的初始值」而不是「n 的上限」。

### 35.2 为什么这是 D12（比数字更严重的问题）

模型再往下推一步就会看到死锁：**一个被降权的中继如果永远不被选中，它就永远拿不到成功样本，也就永远恢复不了**。§22.4 只规定「学习怎么更新」，没规定「谁来给它新样本」——`ps` 自己不会自愈。

7.86 的生产经验正好印证：`probeBad`/`neg` 那种「失败就沉底」的机制一旦缺乏复检，节点就再也不会被用到（第 23 轮加 `PROBE_BAD_TTL=30min` 就是为了拆这个死锁）。

### 35.3 三条修改（写回 §22.4 与 §7）

1. **窗口固定，不做增长**：`n` 初值 8，上限 32；即「最近约 32 个样本的指数平均」。恢复从 29 次成功降到 ~8 次（nCap=16 一列）。
2. **`blk` 门槛从「两批」改「三批」**：

   | 真实通过率 p | m=2 假阳性 | m=3 假阳性 |
   |---|---|---|
   | 0.95 | 0.25% | 0.01% |
   | 0.90 | 1.00% | 0.10% |
   | 0.80 | 4.00% | 0.80% |
   | 0.125（坏中继） | 76.56% | 66.99% |

   代价是坏中继多活一个批次（仍 67% 概率被封），换来好中继被误封的概率降到 1/25。**误封的代价远大于晚封一批**：好中继被封 90 分钟，这段时间只能走 p=0.5 的备选，等于把 45 pt 的成功率丢掉。
3. **选路层必须有康复通道**：每 20 条请求里放 1 条走「当前分数最低、但历史上有过整页」的中继。它不是探索新节点，而是**给被误判的节点供样本**——没有这条，第 1 条「窗口固定」也救不了死锁。

### 35.4 一条没做成的实验（诚实记录）

本想顺带算「1% 的请求遇到连续 3 次失败时，整体成功率损失多少」。写了两次模型都不对：第一次把「谁被选中」写成了与分数无关，第二次用常数门槛判「是否被降权」，导致四条中继的成功率完全一样（65.5%）。**这种「跑出来所有策略数值相同」的结果只有一个解释：模型没有真正把选择连到分数上。**该段已从原型里标注为「勿引用」，本节所有结论只用 Q1/Q3 两段可解释的数。

原则：**能讲清每个数字从哪来的，才写进文档；讲不清的先删掉。**

```
