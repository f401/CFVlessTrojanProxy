# 节点选择：带地面真值的批量仿真

> 目的：不是测"代码跑不跑得通"，而是测**选中的节点离真·最优有多远**。
> 工具：`tools/sim-select.mjs`（伪造节点 → 真实 `pick`/`region`/`bumpFail`/`nsProbe`/`nsSpeed` → 与上帝视角对比）

## 1. 方法

- 每个节点有 4 个**真实**参数：`tcp`、`pFail`（真实请求失败率）、`bw`、`stall`；
  另有 `probeTcp` 可单独伪造（用来验证"探活很快、实际很慢"的节点）。
- 时钟可控（`Date.now` 打桩），1 tick = 1 秒；每 30 分钟跑一次 cron（探活 + `afterScan`）。
- 每 tick 走真实路径：`SEL.pick()`（或 `SEL.region()`）→ 按真实 `pFail` 掷骰 →
  成功则 `nsOk` / `nsSpeed` / `nsStall`，失败走 `SEL.bumpFail()`。
- 上帝视角代价：
  `lat = (rtt + 0.2MB/bw) / (1-pFail)`，`tput = (rtt + 10MB/bw) / (1-pFail)`。
- 指标：`代价倍率 = 实际代价 / 上帝视角最优`；`>1.5x` = 明显选错；`末段命中` = 后 25% 请求落在真·最优上的比例。

复现：

```bash
node test/mk_test.mjs
node tools/sim-select.mjs 4          # 小时数
ONLY=静态异质 node tools/sim-select.mjs 24
TRIAL_N=30 node tools/sim-select.mjs 8   # 调 SC 参数做对照
```

## 2. 结果（4 小时，1 请求/秒，20 个节点）

| 场景 | 模式 | 失败% | 代价倍率 | >1.5x | 末段命中 | 切/小时 |
|---|---|---|---|---|---|---|
| 静态异质 | lat | 0.1 | **1.66x** | 99.9% | 0% | 1.8 |
| 静态异质 | tput | 0.4 | 1.21x | 5.0% | 79% | 15.5 |
| 中途上新 | lat | 0.1 | 1.73x | 90.7% | 0% | 5.3 |
| 中途劣化 | lat | 0.1 | 1.64x | 96.4% | 0% | 2.8 |
| 同质池（10 个 95–115ms） | lat | 1.2 | 1.00x | 0% | 30% | **44.3** |
| 探活伪装（探活 25ms / 真实 350ms） | lat | 0.0 | **3.73x** | 99.9% | 0% | 0.3 |
| 地区池（rg=DE） | lat | 0.4 | **2.50x** | 71.7% | 0% | 0.5 |

24 小时长跑：静态异质 lat 仍是 **1.66x**、`>1.5x` 100%、切换 0.3 次/小时 —— 不是"还没收敛"，是收敛到了错的地方。

## 3. 结论

### 3.1 冷启动锁死（主因）

一次 8 小时长跑结束时的真实分布：

```
n10  28552 次请求  0 失败  pFail=0.0001  score=296   ← 游标
n3     107 次请求  0.4 失败 pFail=0.038   score=566
n18     10 次请求  0.4 失败 pFail=0.125   score=1268
n0       8 次请求  0.4 失败 pFail=0.128   score=1258   （真·可靠最优，125ms）
```

游标拿到 99% 流量 → 样本多 → `pFail` 趋近 0 → 分数更低 → 继续拿 99% 流量。
非游标节点只有 3–10 个样本，`Beta(1,9)` 先验让它们的失败率停在 10%–13%（≈800–1000ms），
**一次试用期失败就再也翻不了身**。`TRIAL_N` 从 3 调到 30/100000、失败阶梯首档 60s→5s、
试用失败不再 30 分钟冻结 —— 三个对照实验都没把 1.66x 拉下来，说明瓶颈是
"用后验均值排序 + 0 失败的大样本节点不可战胜"，不是探索预算或冷却时长。

### 3.2 真实连接的延迟从不回流

`Connection.flush` 调用的是 `nsOk(node, 0, 0)` —— 真实握手耗时被丢弃，`s.tcp/s.tls`
只由探活写入。于是"探活 25ms、真实 350ms"的节点分数 198ms，永久排第一，
吃掉 100% 流量，真实代价 3.73x。这不是极端构造：探活只是 TCP 连接 proxyip，
真实请求要过它的上游，两者本来就可以差一个数量级。

### 3.3 tput 比 lat 好，是因为信号大

带宽差 20MB/s vs 11MB/s 在 10MB 任务上是 400ms 级差异，压得住 800ms 的失败先验噪声；
lat 模式的有效信号只有 60ms，压不住。**同一个先验，在两种模式下等价于两种算法。**

### 3.4 同质池：每 80 秒换一次

10 个节点真实代价只差 5%，但失败率 1–2%，每次失败都走 `nsFail` → 60s 冷却 →
`pick` 发现游标被冷却就 `bestFor` 换人（这条路径**绕过 10 分钟驻留**）。
结果 44 次切换/小时，而代价倍率 1.00x —— 切换没有收益，只有连接重建成本。

### 3.5 地区池同样中招

`rg=DE` 的 5 个节点里，55ms/1% 输给 210ms/0%，代价 2.50x。地区是硬要求，
但"国内选最优"仍然沿用同一套后验均值排序。

## 4. 本轮顺带修掉的两个 bug

| 问题 | 表现 | 修复 |
|---|---|---|
| `pFailFast` 的 `+1/+10` 平滑 | 空闲 18 分钟的节点被算成 9.4% 失败率（+750ms），而**每个非游标节点都是空闲的** —— 等于给所有候选固定加罚，游标坐稳就再也换不下来 | 有效样本 <3 直接返回 0，不再用平滑常数造假信号 |
| `sched` 冷启动抢跑 | `lastSwitch=0` 时 `now-last` 是 50 年，第一条 cron 就把刚选出的第 1 名换成第 2 名，第 2 名白拿最初 10 分钟的全部样本 | 没有任何切换记录时直接返回 |

## 5. 建议（按性价比排序，尚未实施）

1. **真实握手/首字节回流**：`dial` 已经在测 TCP/TLS 耗时，把它传给 `nsOk(k, tcp, tls)`，
   和探活样本一起进 EWMA。改动最小，直接消掉 3.73x 的盲点。
2. **给"完美节点"设下限**：`pFail` 排名时不低于 0.3%–0.5%（16–40ms）。
   0/28552 这种估计本来就过置信，现实里没有 0 失败率的节点。
3. **试用期按不确定性给流量**，而不是"3 个样本就毕业"：可以用 `1/sqrt(n)` 的持续配额，
   或直接上 Thompson/UCB。注意：只调 `TRIAL_N` 无效（已验证）。
4. **失败路径不要绕过驻留**：同质池 44 切/小时 是纯损耗；可以给"换人"加 30–60s 的最小间隔，
   失败只做记账，让 cron 统一决策。

前两条是低风险改动，第 3 条会改变选路的整体性格（探索期会明显变长），需要单独评估。

## 6. 第 2 轮：修完再跑

### 6.1 这一轮改了什么

| 改动 | 说明 |
|---|---|
| 真实首字节回流 | `Connection.flush` 把 `ttfb` 交给 `nsLatency`；`scoreParts` 里真实值超过 `2×探活+150ms` 时以真实值为准，并且**先验也被真实值兜底**（否则 `confL=0` 时只看探活 ms，撒谎节点照样第一） |
| 试用期按模式分开 | `TRIAL_LAT=60`（延迟模式的信号弱，3 个样本不够）、`TRIAL_TPUT=3`（每个试用样本都是 10MB，贵） |
| 试用队列表 | 从"最久没试"改成"样本最少优先，同档挑探活更快的" |

### 6.2 结果（4 小时）

| 场景 | 改前 | 改后 |
|---|---|---|
| 探活伪装（25ms/350ms） | 3.73x，吃掉 100% | **3.10x，吃掉 73%**（24h 后 2.11x） |
| 静态异质 lat | 1.66x | 1.66x |
| 静态异质 tput | 1.21x | 1.21x |
| 地区池 | 2.50x | 2.50x |
| 同质池 | 44 切/小时 | 42 切/小时 |

### 6.3 为什么撒谎节点还没被立刻踢掉

`scoreParts` 里它的延迟确实从 65ms 变成了 398ms（实测），但它的失败率是 0/7648 → `pFail≈0.0002`（≈1.6ms）；
而所有**没被采样**的节点都是 10% 先验 → 800ms。398+125 仍然打不过 100+800+125。
要把 800ms 的先验压下去，只能靠样本：60 个样本后 `pFail≈1.4%`（114ms），分数 347 < 525，才换得动。
5% 探索摊到 9 个节点，凑够 60 个样本要 3 小时 —— 这就是"改后仍然 73%"的全部原因。

### 6.4 试过但没用的（都跑过对照）

| 尝试 | 结果 |
|---|---|
| `BETA` 先验 10%→2% | 撒谎节点降到 47%，但 tput 从 1.21x 退到 1.61x（未采样节点变得太便宜，游标在弱节点间游走） |
| 失败率下限 `PFAIL_MIN=0.4%` | 指标无变化（挑战者的估计噪声比下限大） |
| `TRIAL_LAT` 3/20/60/200 | 静态场景 1.66x→1.67x，无变化 |
| 失败阶梯首档 60s→5s | 无变化 |
| 试用失败不冻结 | 无变化 |
| 后验均值→置信下界（LCB） | 无变化（一次失败就把 LCB 拉到 5%+） |
| `FAIL` 8000→2000/1000/500 | 延迟倍率 1.66→1.65→1.52，但失败率 0.1%→0.6%，切换 1→23 次/小时；是拿可靠性换速度，不是免费优化 |

### 6.5 结论

- 能修的已经修了：探活撒谎、空闲节点假风险、冷启动抢跑、试用样本太少。
- 剩下的 1.66x **不是 bug，是策略**：`FAIL=8000` 意味着一 次失败按 8 秒计，0.5% 失败率就值 40ms；
  60ms 的延迟优势扣掉 40ms 只剩 20ms，低于滞回（25%×延迟≈42ms），算法选择不动。
  换句话说：**当前算法是"稳定优先"的，它认为 0 失败的 120ms 节点和 0.5% 失败的 60ms 节点差不多**。
- 如果产品要"延迟优先"，正确做法是把 `FAIL` 拆成 `FAIL_LAT/FAIL_TPUT`（例如 2000/8000），
  并接受失败率从 0.1% 涨到 0.5–0.6%、切换从 1 次/小时涨到 20 次/小时。这是产品取舍，不是代码缺陷。
