# 节点选择：带地面真值的批量仿真

> 目的：不是测"代码跑不跑得通"，而是测**选中的节点离真·最优有多远**。
> 工具：`tools/sim-select.mjs`（伪造节点 → 真实 `pick`/`region`/`bumpFail`/`nsProbe`/`nsSpeed` → 与上帝视角对比）

## 1. 方法

- 每个节点有 4 个**真实**参数：`tcp`、`pFail`（真实请求失败率）、`bw`、`stall`；
  另有 `probeTcp` 可单独伪造（用来验证"探活很快、实际很慢"的节点）。
- 时钟可控（`Date.now` 打桩），1 tick = 1 秒；每 30 分钟跑一次 cron（探活 + `afterScan`）。
- 每 tick 走真实路径：`SEL.pick()`（或 `SEL.region()`）→ 按真实 `pFail` 掷骰 →
  成功则 `nsOk` / `nsSpeed` / `nsStall`，失败走 `SEL.bumpFail()`。
- 上帝视角代价：
  `lat = (rtt + 0.2MB/bw) / (1-pFail)`，`tput = (rtt + 10MB/bw) / (1-pFail)`。
- 指标：`代价倍率 = 实际代价 / 上帝视角最优`；`>1.5x` = 明显选错；`末段命中` = 后 25% 请求落在真·最优上的比例。

复现：

```bash
node test/mk_test.mjs
node tools/sim-select.mjs 4          # 小时数
ONLY=静态异质 node tools/sim-select.mjs 24
TRIAL_N=30 node tools/sim-select.mjs 8   # 调 SC 参数做对照
```

## 2. 结果（4 小时，1 请求/秒，20 个节点）

| 场景 | 模式 | 失败% | 代价倍率 | >1.5x | 末段命中 | 切/小时 |
|---|---|---|---|---|---|---|
| 静态异质 | lat | 0.1 | **1.66x** | 99.9% | 0% | 1.8 |
| 静态异质 | tput | 0.4 | 1.21x | 5.0% | 79% | 15.5 |
| 中途上新 | lat | 0.1 | 1.73x | 90.7% | 0% | 5.3 |
| 中途劣化 | lat | 0.1 | 1.64x | 96.4% | 0% | 2.8 |
| 同质池（10 个 95–115ms） | lat | 1.2 | 1.00x | 0% | 30% | **44.3** |
| 探活伪装（探活 25ms / 真实 350ms） | lat | 0.0 | **3.73x** | 99.9% | 0% | 0.3 |
| 地区池（rg=DE） | lat | 0.4 | **2.50x** | 71.7% | 0% | 0.5 |

24 小时长跑：静态异质 lat 仍是 **1.66x**、`>1.5x` 100%、切换 0.3 次/小时 —— 不是"还没收敛"，是收敛到了错的地方。

## 3. 结论

### 3.1 冷启动锁死（主因）

一次 8 小时长跑结束时的真实分布：

```
n10  28552 次请求  0 失败  pFail=0.0001  score=296   ← 游标
n3     107 次请求  0.4 失败 pFail=0.038   score=566
n18     10 次请求  0.4 失败 pFail=0.125   score=1268
n0       8 次请求  0.4 失败 pFail=0.128   score=1258   （真·可靠最优，125ms）
```

游标拿到 99% 流量 → 样本多 → `pFail` 趋近 0 → 分数更低 → 继续拿 99% 流量。
非游标节点只有 3–10 个样本，`Beta(1,9)` 先验让它们的失败率停在 10%–13%（≈800–1000ms），
**一次试用期失败就再也翻不了身**。`TRIAL_N` 从 3 调到 30/100000、失败阶梯首档 60s→5s、
试用失败不再 30 分钟冻结 —— 三个对照实验都没把 1.66x 拉下来，说明瓶颈是
"用后验均值排序 + 0 失败的大样本节点不可战胜"，不是探索预算或冷却时长。

### 3.2 真实连接的延迟从不回流

`Connection.flush` 调用的是 `nsOk(node, 0, 0)` —— 真实握手耗时被丢弃，`s.tcp/s.tls`
只由探活写入。于是"探活 25ms、真实 350ms"的节点分数 198ms，永久排第一，
吃掉 100% 流量，真实代价 3.73x。这不是极端构造：探活只是 TCP 连接 proxyip，
真实请求要过它的上游，两者本来就可以差一个数量级。

### 3.3 tput 比 lat 好，是因为信号大

带宽差 20MB/s vs 11MB/s 在 10MB 任务上是 400ms 级差异，压得住 800ms 的失败先验噪声；
lat 模式的有效信号只有 60ms，压不住。**同一个先验，在两种模式下等价于两种算法。**

### 3.4 同质池：每 80 秒换一次

10 个节点真实代价只差 5%，但失败率 1–2%，每次失败都走 `nsFail` → 60s 冷却 →
`pick` 发现游标被冷却就 `bestFor` 换人（这条路径**绕过 10 分钟驻留**）。
结果 44 次切换/小时，而代价倍率 1.00x —— 切换没有收益，只有连接重建成本。

### 3.5 地区池同样中招

`rg=DE` 的 5 个节点里，55ms/1% 输给 210ms/0%，代价 2.50x。地区是硬要求，
但"国内选最优"仍然沿用同一套后验均值排序。

## 4. 本轮顺带修掉的两个 bug

| 问题 | 表现 | 修复 |
|---|---|---|
| `pFailFast` 的 `+1/+10` 平滑 | 空闲 18 分钟的节点被算成 9.4% 失败率（+750ms），而**每个非游标节点都是空闲的** —— 等于给所有候选固定加罚，游标坐稳就再也换不下来 | 有效样本 <3 直接返回 0，不再用平滑常数造假信号 |
| `sched` 冷启动抢跑 | `lastSwitch=0` 时 `now-last` 是 50 年，第一条 cron 就把刚选出的第 1 名换成第 2 名，第 2 名白拿最初 10 分钟的全部样本 | 没有任何切换记录时直接返回 |

## 5. 建议（按性价比排序，尚未实施）

1. **真实握手/首字节回流**：`dial` 已经在测 TCP/TLS 耗时，把它传给 `nsOk(k, tcp, tls)`，
   和探活样本一起进 EWMA。改动最小，直接消掉 3.73x 的盲点。
2. **给"完美节点"设下限**：`pFail` 排名时不低于 0.3%–0.5%（16–40ms）。
   0/28552 这种估计本来就过置信，现实里没有 0 失败率的节点。
3. **试用期按不确定性给流量**，而不是"3 个样本就毕业"：可以用 `1/sqrt(n)` 的持续配额，
   或直接上 Thompson/UCB。注意：只调 `TRIAL_N` 无效（已验证）。
4. **失败路径不要绕过驻留**：同质池 44 切/小时 是纯损耗；可以给"换人"加 30–60s 的最小间隔，
   失败只做记账，让 cron 统一决策。

前两条是低风险改动，第 3 条会改变选路的整体性格（探索期会明显变长），需要单独评估。

## 6. 第 2 轮：修完再跑

### 6.1 这一轮改了什么

| 改动 | 说明 |
|---|---|
| 真实首字节回流 | `Connection.flush` 把 `ttfb` 交给 `nsLatency`；`scoreParts` 里真实值超过 `2×探活+150ms` 时以真实值为准，并且**先验也被真实值兜底**（否则 `confL=0` 时只看探活 ms，撒谎节点照样第一） |
| 试用期按模式分开 | `TRIAL_LAT=60`（延迟模式的信号弱，3 个样本不够）、`TRIAL_TPUT=3`（每个试用样本都是 10MB，贵） |
| 试用队列表 | 从"最久没试"改成"样本最少优先，同档挑探活更快的" |

### 6.2 结果（4 小时）

| 场景 | 改前 | 改后 |
|---|---|---|
| 探活伪装（25ms/350ms） | 3.73x，吃掉 100% | **3.10x，吃掉 73%**（24h 后 2.11x） |
| 静态异质 lat | 1.66x | 1.66x |
| 静态异质 tput | 1.21x | 1.21x |
| 地区池 | 2.50x | 2.50x |
| 同质池 | 44 切/小时 | 42 切/小时 |

### 6.3 为什么撒谎节点还没被立刻踢掉

`scoreParts` 里它的延迟确实从 65ms 变成了 398ms（实测），但它的失败率是 0/7648 → `pFail≈0.0002`（≈1.6ms）；
而所有**没被采样**的节点都是 10% 先验 → 800ms。398+125 仍然打不过 100+800+125。
要把 800ms 的先验压下去，只能靠样本：60 个样本后 `pFail≈1.4%`（114ms），分数 347 < 525，才换得动。
5% 探索摊到 9 个节点，凑够 60 个样本要 3 小时 —— 这就是"改后仍然 73%"的全部原因。

### 6.4 试过但没用的（都跑过对照）

| 尝试 | 结果 |
|---|---|
| `BETA` 先验 10%→2% | 撒谎节点降到 47%，但 tput 从 1.21x 退到 1.61x（未采样节点变得太便宜，游标在弱节点间游走） |
| 失败率下限 `PFAIL_MIN=0.4%` | 指标无变化（挑战者的估计噪声比下限大） |
| `TRIAL_LAT` 3/20/60/200 | 静态场景 1.66x→1.67x，无变化 |
| 失败阶梯首档 60s→5s | 无变化 |
| 试用失败不冻结 | 无变化 |
| 后验均值→置信下界（LCB） | 无变化（一次失败就把 LCB 拉到 5%+） |
| `FAIL` 8000→2000/1000/500 | 延迟倍率 1.66→1.65→1.52，但失败率 0.1%→0.6%，切换 1→23 次/小时；是拿可靠性换速度，不是免费优化 |

### 6.5 结论

- 能修的已经修了：探活撒谎、空闲节点假风险、冷启动抢跑、试用样本太少。
- 剩下的 1.66x **不是 bug，是策略**：`FAIL=8000` 意味着一 次失败按 8 秒计，0.5% 失败率就值 40ms；
  60ms 的延迟优势扣掉 40ms 只剩 20ms，低于滞回（25%×延迟≈42ms），算法选择不动。
  换句话说：**当前算法是"稳定优先"的，它认为 0 失败的 120ms 节点和 0.5% 失败的 60ms 节点差不多**。
- 如果产品要"延迟优先"，正确做法是把 `FAIL` 拆成 `FAIL_LAT/FAIL_TPUT`（例如 2000/8000），
  并接受失败率从 0.1% 涨到 0.5–0.6%、切换从 1 次/小时涨到 20 次/小时。这是产品取舍，不是代码缺陷。

### 7.1 新发现的三个问题

**① 带宽崩塌后学不动**（`4.56x`，最差 8.3x，P95 18x，事件后仍有 23% 流量压在崩塌节点上）。

把 n1 的真实带宽从 20MB/s 改成 0.5MB/s 后，它 10MB 要 20 秒，
但**未采样节点的 `e10` 先验是 51 秒** —— 20 秒的塌方节点仍然比"不知道"的节点快，
于是它继续被选中。把直方图半衰期从 6h 缩到 1h 复测：4.71x，**没有改善**，
说明瓶颈不是旧样本没衰减，而是"已知慢"打赢了"未知"。

**② 撒谎节点一多就失效**（三个撒谎节点吃掉 97% 流量，2.87x）。

TTFB 回流只让三个撒谎节点的分数从 198ms 涨到 ~525ms，
但诚实节点全是 10% 先验（800ms）+ 探活延迟（~108ms）≈ 1033ms，还是输。
一个撒谎节点时靠 5% 探索还能在 3 小时内翻盘，三个一起上就翻不动了。

**③ 全坏池会疯狂切换**：所有节点 15–40% 失败时，86% 流量回落到直连，
剩下 14% 在坏节点之间来回跳，**100 次切换/小时**。
失败路径绕过驻留（`pick` 发现游标被冷却就换人），在"没有好节点"时这条路径最吵。

### 7.2 两个"意外地还行"的结果

- **低流量**（1 请求/分钟，24 小时才 1400 个请求）：1.25x、0.6 次切换/小时。
  样本少到几乎学不动，但也因此不乱切，实际体验不会比高流量差多少。
- **抖动节点**（每 10 分钟完全挂 2 分钟）：1.47x、14.5 次切换/小时。
  失败阶梯能把它按下去，恢复后也能重新用起来。

### 7.3 大池：切换变多，命中变差

100 个节点时 lat 1.52x（区间 1.18–1.96）、**46 次切换/小时**、末段命中 60%。
5% 探索摊到 100 个节点，每个节点一小时只能拿到 1.8 个样本，
所以"排在前面的节点"一直在变；tput 反而更稳（1.26x，10% > 1.5x）。

### 7.4 这一轮没有改代码

上面三条都属于策略/模型层面（先验、失败路径、探索预算），
不是一两行能改对的。下一步如果要动，优先级建议：

1. `e10` 先验从 51s 降到 5–8s（或按池子实测中位数），让"已知慢"不再赢过"未知"。
2. 失败路径的换人加 30–60s 最小间隔（全坏池 100 次/小时 → 预计 <20）。
3. 撒谎节点检测到后直接降级（比如强制走一次 `nsFail` 记账），而不是等样本累积。

| 链路 | 卡顿 30% | tput | 0.4 | 0 | 1.14x | 1.3x | 0% | 16.2 |
| 链路 | 带宽崩塌 | tput | 0.1 | 0 | 2.68x | **15.3x** | 23% | 4.2 |
| 池变动 | 加 5 个节点 | lat | 0.2 | 0 | **1.74x** | 1.9x | 94% | 2.9 |
| 池变动 | 删当前最优 | lat | 0.4 | 0 | 1.55x | 1.9x | 77% | 11.1 |
| 长跑 | 24h | lat | 0.1 | 0 | 1.66x | 1.7x | 99% | 0.3 |

### 8.1 六个新结论

**① 加更多流量没用。** 1/秒和 5/秒都是 1.64–1.66x、95–100% 请求落在 >1.5x 的节点上。
样本多了，但都在游标身上；`TRIAL_LAT=60` 让每个节点毕业更快，可算出来的结论仍然是
"0.5% 失败 + 60ms" 和 "0% 失败 + 120ms" 差不多（分差 20ms < 滞回 42ms）。

**② 规模不是越大越好，池子构成才是。** 20 节点最差（1.64x，因为池里有一个
120ms/0 失败的强诱饵），100/300 节点反而 1.33x/1.17x（诱饵被稀释）。
代价是切换变多：36–47 次/小时。

**③ 池子变动后，新节点进不来。** 2 小时后加 5 个 40–100ms 的更优节点，
倍率仍 1.74x（比不加还差一点），末段命中 0%。删掉当前最优后 1.55x、11 次切换/小时 ——
会换人，但换到的是"有样本的次优"，不是新来的最优。

**④ 探活是单向门。** "探活快、真实慢"能靠 TTFB 回流纠正（虽然慢）；
"探活慢、真实快"（probe 420ms / real 60ms / 20MB/s）**永远发现不了**：
`trial()` 有 `a.ms <= 250` 的门槛，`Lprior` 只取 `max(探活, 真实)`，没有任何路径能把估计往下拉。
8 小时里它吃掉 0% 流量，倍率 1.69x。

**⑤ 恢复要 44 分钟。** 节点 2 小时前完全死掉、2 小时后满血复活，
要 **44 分钟**才重新被用上 —— 失败阶梯最后一档是 60 分钟冷却，冷却期内 `nsOk` 跑不到，
只能等它自然过期。线性恢复（失败率从 40% 平滑降到 0.5%）只要 3 分钟，因为一直有流量在试。

**⑥ 只有一个节点时，一次失败 = 23% 的直连。** 单节点池 4 小时里 23% 的请求回落到直连
（失败一次就冷却 60 秒，期间没有候选）。`rg=` 单节点更严重：26% 的请求直接 1011 断开
（硬要求不允许回落，这是预期行为，但用户侧就是 26% 失败率）。

### 8.2 仍然最差的两个

- **带宽崩塌**：2.68x（最差 3.45x）、P95 15.3x。10MB 任务上，"已知 20 秒"仍然赢"未知 51 秒"。
- **三个撒谎节点**：2.87x、97% 流量。诚实节点的 10% 先验（800ms）打不过撒谎节点的 0 失败。

### 8.3 全坏池的两种表现

全局模式：85% 回落直连、22.4% 失败、**110 次切换/小时**；
`rg=` 模式：89% 直接 1011 断开、20.6% 失败。前者还能用（只是没了代理 IP），
后者是硬要求下的正确行为，但切换仍然是 110 次/小时量级 —— 失败路径绕过驻留的代价。

## 9. 规模：50 → 6400 个节点

工具：`tools/sim-scale.mjs`（每档 3 个种子、2 小时、1 请求/秒；
池子 = 1 个 60ms/0.5% 的最优 + N-1 个 ≥150ms/2–4% 的填充）。

| 节点数 | candsFor（冷） | region/次 | pick 平均 | 内存 | 倍率 | >1.5x | **有样本节点** | 切/小时 |
|---|---|---|---|---|---|---|---|---|
| 50 | 140 µs | 24 µs | 2.5 µs | 0.1 MB | 1.38x | 36% | **40%** | 35.5 |
| 100 | 55 µs | 16 µs | 1.1 µs | 0.1 MB | 1.35x | 36% | 40% | 35.7 |
| 200 | 115 µs | 18 µs | 2.1 µs | 0.1 MB | 1.36x | 37% | 40% | 35.2 |
| 400 | 254 µs | 52 µs | 4.4 µs | 0.5 MB | 1.35x | 36% | **15%** | 35.3 |
| 800 | 496 µs | 63 µs | 8.9 µs | 1.0 MB | 1.35x | 36% | **1%** | 35.8 |
| 1600 | 976 µs | 127 µs | 17.9 µs | 1.9 MB | 1.34x | 36% | 1% | 36.3 |
| 3200 | 2089 µs | 351 µs | 45.7 µs | 3.8 MB | 1.34x | 36% | 0% | 36.3 |
| 6400 | 4546 µs | 748 µs | 114.6 µs | 7.7 MB | 1.34x | 36% | 0% | 36.3 |

"有样本"= 2 小时后 `okW+failW ≥ 2` 的节点占比。

### 9.1 三个结论

**① 加节点不再改变结果。** 50 → 6400，倍率稳定在 1.34–1.38x、`>1.5x` 36%、末段命中 62–63%。
算法实际只在"游标 + 5% 探索"这一小撮节点里工作，池子再大也只是多了没被看过的候选。

**② 采样覆盖率随规模塌陷。** 5% 的探索摊到 N 个节点：200 节点时 40% 能拿到 2 个样本，
400 节点掉到 15%，800 节点 1%，3200 以上基本是 0。
换句话说：**超过 200 个节点之后，池子里大部分节点在做决策时是"不存在"的。**

**③ CPU 是线性的，400 以内很便宜。**

- `candsFor` 冷算 ≈ **0.7 µs/节点**（400 → 254 µs，每 20 秒一次）；
- `region()` 每次连接重算 ≈ **0.12 µs/节点**（400 → 52 µs）；
- `pick()` 平均 4.4 µs（400）；其中 5% 的探索会 `trial()` 全表扫描，单次约 90 µs；
- 内存 ≈ 1.2 KB/节点（6400 → 7.7 MB）。

按 100 连接/秒算：400 节点时 `region` 占 5.2 ms/s、`pick` 占 0.44 ms/s；
6400 节点时 `region` 占 74.8 ms/s（约 7.5% 单核）—— 能用，但没有收益。

### 9.2 真正卡住规模的是三个常量

| 常量 | 值 | 含义 |
|---|---|---|
| `ALIVE_MAX` | 400 | 长期运行 `S.alive` 上限，超了按"不在当前池 / 更慢"淘汰 |
| `POOL_MAX` | 800 | 上游候选名单硬上限 |
| `SEED_MAX` | **40** | 每个机房**最多只有 40 个节点**能把统计带过 isolate 重启 |
| `SEED_COLD_N` | 8 | 冷启动只从 seed 灌 8 个节点进 alive |

所以在 400 节点的池子里：**只有 10% 的节点统计能跨 isolate 存活**，冷启动只有 8 个节点带着历史。
这不是算法问题，是持久化预算问题：40 个节点的 seed 实测 **4.4 KB**（110 B/节点，含 hp 共 4.5 KB），400 个约 44 KB；
KV 单值上限 25 MB，**空间完全够，卡的是常量**。

### 9.3 建议

- 池子维持在 **150–250 个节点**：采样覆盖率 ≥40%，`candsFor` <0.2 ms，`region` <30 µs。
- 如果确实要用更大的池子，`SEED_MAX` 至少要跟 `ALIVE_MAX` 同量级（400 → seed ≈ 60 KB），
  否则每个新 isolate 都要从 8 个节点重新学。
- 不想加 `SEED_MAX` 的话，折中是把 `ALIVE_MAX` 降到 200 —— 覆盖率和 CPU 都更好，选路质量不变。

## 10. 算法优化清单（每条都有实测）

工具里加了 `ROUTE=softmax TEMP=... KTOP=...`：把 `pick()` 换成"在候选前 K 名里按
`exp(-(v-v0)/T)` 抽签"，其余（评分、探活、失败记账）完全不变。

### 10.1 路由层：softmax 替换"单游标 + 滞回"（收益最大）

| 场景 | 单游标 | softmax T=30 | 变化 |
|---|---|---|---|
| 20 节点 | 1.64x | **1.36x** | −17% |
| 5 节点 | 1.32x | **1.27x** | −4% |
| 100 节点 | 1.33x | 1.31–1.46x | 持平（噪声内） |
| 探活撒谎 | 2.83x | **1.31x** | −54% |
| 撒谎×3 | 2.87x | **1.30x** | −55% |
| 带宽崩塌 | 2.68x（P95 15.3x） | **1.31x（P95 2.2x）** | −51% |
| 地区 DE | 1.70x | 1.74–1.93x | **变差** |

结论：
- **全局 `pick()` 应该改成加权抽签**。它同时解决了三件事：游标锁死、探活撒谎、
  带宽崩塌（新样本一进来权重立刻下降，不用等游标轮换）。
- **`region()` 不要用 softmax**。国家池小、里面常有"快但抖"的诱饵，
  摊流量等于主动喂失败；`rg=` 保持"选最优 + 失败换人"更稳。

实现（`src/px/selector.ts`，约 20 行）：

```ts
pickByScore(mode, T = 20, K = 12) {
  const list = candsFor(mode).slice(0, K);
  if (!list.length) return "";
  const v0 = list[0].v;
  let tot = 0;
  const w = list.map((x) => { const e = Math.exp(-(x.v - v0) / T); tot += e; return e; });
  let r = Math.random() * tot;
  for (let i = 0; i < list.length; i++) if ((r -= w[i]) <= 0) return list[i].k;
  return list[0].k;
}
```

配套要改两处：
- `pick()` 返回的节点写进 `st.node`，但**不要再写 `S.curs`**（游标只用于面板/健康）；
- `nsFail()` 现在每次失败都 `S.rankCache.t = 0`，抽签把失败摊到更多节点后，
  大池子会频繁重算 400 个节点 —— 改成只清 `hostRankCache`，`rankCache` 交给 20 秒 TTL。

### 10.2 估计层：两个单向门

| 问题 | 证据 | 改法 |
|---|---|---|
| 探活慢、真实快永远发现不了 | probe 420ms / real 60ms 的节点 8h 吃 0% 流量，1.69x | `Lprior = min(探活, 真实 TTFB)`；`trial()` 的 `a.ms <= 250` 改成 `min(a.ms, msLocal) <= 250` |
| 带宽崩塌后"已知 20 秒"赢"未知 51 秒" | 2.68x、P95 15.3x | `PRIOR_BPS` 200KB/s → 1–2MB/s（e10 先验 51s → 5–10s），或按池子实测中位数 |

softmax 已经把带宽崩塌从 2.68x 压到 1.31x，所以第二条降级为"可选"。

### 10.3 失败处理层：三处噪声

| 问题 | 证据 | 改法 |
|---|---|---|
| 失败路径绕过驻留 | 全坏池 110 次切换/小时；同质池 44 次 | `onFail` 里换人加 30–60s 最小间隔，失败只记账，换人交给 cron |
| 恢复要 44 分钟 | 死亡 2h 后复活，44 分钟才重新用上 | 阶梯最后一档 60min → 20min；冷却到期强制探活一次 |
| 单节点池 23% 直连 | 一次失败 = 60s 没有候选 | `alive < 5` 时首次失败只冷却 10s（或要求连续 2 次） |

### 10.4 规模层：探索预算要跟池子大小解耦

400 节点时只有 15% 的节点能拿到 ≥2 个样本，800 节点 1%，3200 节点 0%。
5% 摊到 N 个节点等于没探索。建议改成**固定 32 个 watchlist**：

```ts
// 每次 cron 重算：探活快 + 样本少 + 分数靠前
watch = alive.filter(a.ms <= 250)
             .sort((a,b) => (a.ms + 300/Math.sqrt(n(a)+1)) - (b.ms + 300/Math.sqrt(n(b)+1)))
             .slice(0, 32);
```

探索流量只在这 32 个里轮转（每个每小时能拿到 ~20 个样本），
池子从 20 涨到 400 都不影响探索质量，CPU 也从 O(N) 降到 O(32)。

### 10.5 优先级

| 顺序 | 改动 | 预期 | 风险 |
|---|---|---|---|
| 1 | `pick()` 改加权抽签（T=20–30，K=12） | 常规 −17%，撒谎/崩塌 −50% | 面板"当前节点"语义变化；失败会分散，需同步改 `nsFail` 的缓存清理 |
| 2 | 失败换人节流 + 阶梯封顶 20min | 全坏池 110 → <20 次/小时；恢复 44min → ~10min | 低 |
| 3 | `Lprior` 取 `min(探活, 真实)` | 反向撒谎 1.69x → ~1.2x | 低（只影响撒谎节点） |
| 4 | watchlist 固定 32 个 | 大池子探索覆盖率不再塌陷 | 中（要改 trial 的选点逻辑） |
| 5 | `PRIOR_BPS` 1–2MB/s | 崩塌场景兜底 | 中（冷启动排名会变） |
| 6 | `FAIL` 拆模式 | — | **不建议**：实测 FAIL=3000/2000/1000 + softmax 只把 1.36x 变成 1.34x，失败率却从 0.3% 涨到 1.4% |

### 12.1 真实的四个结论

**① tput 是短板。** 3.18x、88% 请求落在 >1.5x 的节点上，种子间 1.60–6.30 —— 
在"带宽差 20 倍"的池子里，粘滞游标 + 3 个试用样本找不到最快的那个。
对照实验（都跑过）：

| 尝试 | 结果 |
|---|---|
| `ROUTE_T_TPUT` 100/300/1000ms | 3.44 / 3.58 / 3.87x（无改善） |
| `TRIAL_TPUT` 10 / 30 | 3.85 / 3.75x（无改善） |
| `PRIOR_BPS` 1 / 2 / 4 MB/s | 2.93 / 2.82 / 2.73x（改善有限） |
| `trial` 门槛 250 → 600ms | 3.93x（无改善） |

说明瓶颈不是"抽签温度"或"试用次数"，而是**根本没人测过大部分节点的带宽**：
30 个节点里只有游标和少数试用节点有 10MB 样本，剩下的 `e10` 永远是 51 秒先验。
要修得加"带宽普查"（每 6h 给每个节点 1–2 个 10MB 样本），而不是继续调参。

**② 相关故障很便宜。** 节点 up 30–120 分钟 / down 2–15 分钟的 Markov 模型下，
1.33x、只有 0.7% 的请求打在死节点上 —— 失败阶梯 + 60 秒冷却足够处理"整段挂掉"。

**③ 站点侧失败不会被算到节点头上。** 30% 的失败是站点侧（0 字节关闭），
倍率 1.34x、和基线一样 —— `nsSiteFail` 的 0.2 权重是对的。

**④ 换血场景是抽签的直接收益。** 每 30 分钟换 3 个节点，**50.8% 的流量给了上线 <1 小时的新节点**，
倍率 1.31x。换成 6.25 的单游标实现，新节点要等游标冷却/轮换才吃得到流量。

### 12.2 真实画像的方差比合成池大

lat 1.21–1.83、tput 1.60–6.30。原因是"上帝视角"是 30 个对数正态样本里的最小值 ——
经常是一个离群点（比如 40MB/s 或 30ms 的节点），能不能找到它决定了倍率。
绝对差距没有倍率看起来那么大：lat 的中位节点约 150ms，最优约 100ms，1.5x 就是"第二个最好的"。

| 方案 | 做法 | 实测/预期 | 代价 |
|---|---|---|---|
| **ε-greedy + watchlist**（建议） | 固定 32 个"探活快 + 样本少"的节点，5% 流量只在里面轮转 | 覆盖不再随池子规模塌陷（400 节点 15% → 32 个全拿到样本） | 改 `trial()` 选点，约 30 行 |
| **softmax 抽签**（已上线 lat） | 前 K 名按 `exp(-(v-v0)/T)` 抽 | lat 20 节点 1.64→1.39、撒谎×3 2.87→1.38、24h 1.66→1.41 | 已上线 |
| **乐观初始化** | 没测过的节点按"当前最好"估，而不是 51s/10% 先验 | 真实画像 lat **1.50 → 1.28x**，>1.5x 49%→21% | 改 `scoreParts` 的先验，约 10 行；tput 反而更抖（3.18→3.53） |
| **Thompson 采样** | 从 Beta 后验里抽 pFail，按抽到的值排序 | 理论上最适合"小样本 + 高不确定性"；未实测 | 需要 Beta 采样器（两个 Gamma），约 40 行；每条连接多一次采样 |
| **UCB1** | `score - c·sqrt(ln N / n)` | 和乐观初始化同源，但按样本量衰减；未实测 | 约 15 行 |

### B. 目标函数

| 方案 | 说明 | 适配度 |
|---|---|---|
| **期望时间**（现状） | `延迟 + 8000×pFail` | 稳定，但对 p95 不友好 |
| **CVaR / 尾延迟** | `mean + λ·sd`，或直接用 p95 | 浏览器场景更关心"最差那 5%"，需要按连接记延迟分布（现在只有 EWMA，没有分布） |
| **每站点独立 bandit** | 每个域名族各维护一份候选权重 | 已有 `hostNode`，但只在 `sampled>=3` 时才用；可以直接接 softmax |
| **对冲请求** | 同时发两个节点，取先到的 | p95 收益最大，但流量 ×2；只适合首字节/TLS 握手阶段 |

### C. 测量

| 方案 | 说明 | 实测 |
|---|---|---|
| **带宽普查** | 每 N 小时给每个节点一个 5MB 样本 | 仿真里被种子方差淹没（1.60–6.30），**结论不明确**；理论上必须有，否则 30 个节点里只有几个有 `e10` |
| **被动观测**（现状） | 只在被选中时采样 | 冷门节点永远没有带宽数据 |
| **真实 TTFB 回流**（已上线） | 每条连接回填首字节 | 修掉"探活快真实慢"，但只能上调延迟 |

### D. 结构

| 方案 | 说明 | 适配度 |
|---|---|---|
| **两级选择**（region → global） | `rg=` 先按国家筛，再在全球榜里选 | 已是现状（`region()` 独立排序） |
| **把 pFail 换成存活曲线** | 记"距上次成功的时长"而不是计数 | 对"整段挂掉"更敏感，但和现有 Beta 模型冲突，改动大 |
| **按连接类型分池** | 小请求走低延迟池、大请求走高带宽池 | 需要客户端声明意图（已有 lat/tput 两套订阅，等于已经分了） |

### 建议顺序

1. **watchlist**（A1）：解决"池子一大就没人被采样"，改动小、收益确定。
2. **乐观初始化**（A3）：lat 实测 −15%，但只对延迟模式开；tput 会更抖。
3. **Thompson**（A4）：如果要一个统一框架，它比"温度 + 先验"少两个超参；代价是多一个采样器。
4. 对冲请求（B4）先不做：流量翻倍，和"省流量"的产品目标冲突。

## 14. 第 6 轮：watchlist + 热路径 O(K)（6.27）

### 14.1 改了什么

| 改动 | 说明 |
|---|---|
| **watchlist** | `trial()` 不再全表扫描后挑"样本最少"，而是先按 `探活延迟 + 300/√(n+1)` 排出 32 个候选，5% 探索只在这 32 个里轮转（60 秒缓存） |
| **`rankedCands` 拆分** | `candsFor()` 原来每次调用都对全表 `filter` 一遍（400 节点 ~60µs/次），现在把"排序 + 缓存"和"过滤"分开；`pickByScore` 只取前 12 个可用候选 |

### 14.2 热路径成本（`pick` 每次连接）

| 节点数 | 改前 pick | 改后 pick |
|---|---|---|
| 400 | 79 µs | **3.5 µs** |
| 800 | 155 µs | **3.4 µs** |
| 1600 | 421 µs | **3.8 µs** |

`candsFor` 冷算仍是 O(N log N)（1600 节点 2.4ms，每 20 秒一次），但不再出现在每条连接上。

### 14.3 选路质量（35 场景，3 种子）

| 场景 | 6.26 | 6.27 |
|---|---|---|
| 300 节点 | 1.26x | **1.20x** |
| 探活撒谎 | 1.37x | **1.33x** |
| 撒谎×3 | 1.38x | **1.32x** |
| 20 节点 | 1.39x | 1.38x |
| 100 节点 | 1.35x | 1.38x |
| 双峰 | 1.18x | 1.24x |
| 1/秒 | 1.39x | 1.45x |
| 其余 | — | 持平 |

净效果：质量基本持平，**大池子略好（300 节点 −5%）、热路径便宜 20 倍**。
"有样本节点占比"从 400 节点的 15% 降到 9% —— 这是设计使然：探索预算从"摊给 400 个"
改成"集中给 32 个"，每个被看节点拿到的样本多 12 倍。

### 14.4 另外两条备选，测了但不采纳

| 方案 | 实测 | 结论 |
|---|---|---|
| **乐观初始化**（没测过的节点按当前最好估） | 真实画像 lat 1.50 → 1.28x、>1.5x 49%→21%；tput 3.18 → 3.53x | 对 lat 有效、对 tput 有害，而且原型是把整个路由换掉，无法归因到"初始化"本身 |

| **Thompson 采样** | 未实测 | 需要 Beta 采样器；在 softmax 已经工作的前提下没有证据表明更好 |

## 15. 第 7 轮：快速节点从不进直方图 + SEED_MAX（6.28）

### 15.1 找到 tput 的真正短板

真实画像 tput 的坏种子（6.28x）里，dump 出来是这样：

```
oracle r27: bw=57.8MB/s  cost=280ms   score=52138   hits=8
cursor r7 : bw= 7.1MB/s  cost=1520ms  score=1157    hits=16651
```

最快的节点 `score=52138` —— 它还停在 **51 秒先验**上，8 次请求一次样本都没留下。

原因：`Connection.flush` 的吞吐采样闸门是 `dt >= 300ms`。
10MB 在 57.8MB/s 上只要 **173ms**，永远进不了直方图 → `e10` 永远是先验 →
分数永远最差 → 永远选不上。**节点越快，越测不到。**

修法：字节够多时不再要求 300ms（1MB 已经过了慢启动）：

```ts
dt >= 50 && (dt >= 300 || bytes >= 1048576)
```

仿真验证（真实画像 tput，3 种子）：

| | 改前 | 改后 |
|---|---|---|
| 倍率 | 3.18x | **2.36x** |
| P95 | 4.3x | **3.4x** |
| >1.5x | 90% | **74%** |
| 坏种子 | 6.28x | 3.82x |

合成场景不受影响：客户端限速 1.00x、卡顿 30% 1.14x、带宽崩塌 2.68x。

### 15.2 SEED_MAX 40 → 200

| 常量 | 改前 | 改后 | 理由 |
|---|---|---|---|
| `SEED_MAX` | 40 | **200** | 400 节点池里只有 10% 的统计能跨 isolate 存活；110 B/节点，200 个约 22 KB |
| `SEED_COLD_N` | 8 | **24** | 冷启动灌进 alive 的节点数，池子大了 8 个太少 |

对应测试从"截断在 40 条"改成"不超过 SEED_MAX"（45 条全保留）。

## 17. 第 9 轮：Thompson + 门槛 —— 原型 1.18x，集成后 1.54x，回滚

### 17.1 原型（替换整个 `pick`）

真实画像 lat：1.43x → **1.18x**、>1.5x 35% → **11%**、P95 2.3 → 1.5。
做法：失败率做 2% 门槛，排序从 `N(latency, latency/√样本数)` 抽一个。

### 17.2 集成进 `pick()` 之后

| 版本 | 倍率 | 失败% |
|---|---|---|
| 现状（softmax + 分数） | 1.43x | 0.8 |
| 集成 v1（门槛按池内中位数×2） | 1.76x | 1.5 |
| 集成 v2（门槛固定 2%） | 1.80x | 1.4 |
| 集成 v3（未测节点不受门槛约束） | **1.54x** | 0.6 |
| 集成 v3 + 去掉 20 秒缓存 | 1.59x | 0.9 |
| 集成 v3 + 关闭失败回滚 | 1.91x | 1.6 |

### 17.3 已排除的原因

| 假设 | 处理 | 结果 |
|---|---|---|
| 门槛把未测节点锁死（先验 10% > 2%） | 改成 `样本数≥3` 才用门槛 | 1.80 → 1.54（有效，但还不够） |
| 20 秒候选缓存导致估计滞后 | 每条连接重算 | 1.59（无改善） |
| `onFail` 回滚冻结了好节点 | TS 模式下关掉回滚 | 1.91（更差） |

### 17.4 未解释的差异

原型是**整个替换** `SEL.pick`，不经过：游标维护（`bestFor`）、host 分支、`onFail` 记账、
`cnt` 计数。集成版保留了这些。剩下的 1.54 vs 1.18 应该就藏在这里，但没有定位到。

### 17.5 结论

**不发布。** 保留现有 softmax + 分数排序（1.43x / 0.8% 失败）。
原型数据留档；下一步如果要继续，应该用"逐分支开关"把 `pick` 拆开对比，
而不是直接把 TS 塞进去。

工具里保留了 `RANK=ts` / `RANK=raw` / `RANK=rawsoft` 三个原型开关，方便复现。

## 18. 第 10 轮：TS 逐分支定位 —— 找到真凶：候选缓存

把 `pick()` 的四个可能因素做成开关，两两组合跑真实画像 lat（2 种子）：

| `TS_CURSOR` | `TS_COLD_PASS` | `TS_FB` | `TS_TTL` | 倍率 |
|---|---|---|---|---|
| 0（不碰游标） | 0 | 0 | 20s | 1.75x |
| 1（保留游标） | 0 | 0 | 20s | 1.75x |
| 0 | 0 | 1（分数兜底） | 20s | 1.75x |
| 1 | 0 | 1 | 20s | 1.75x |
| 0 | 1（冷节点放行） | 0 | 20s | 1.47x |
| 1 | 1 | 1 | 20s | 1.48x |
| **0 / 1** | **0** | **1** | **0（每条连接重算）** | **1.22x** |
| 1 | 1 | 1 | 0 | 1.26x |

### 18.1 结论

- **游标维护、兜底策略：完全无影响**（0/1 两组数字一模一样）—— 之前怀疑的两项排除。
- **冷节点放行**：1.75 → 1.47，真有效，但不是主因。
- **缓存是主因**：`TS_TTL` 从 0 改到 **1 秒**，倍率就从 1.22 掉到 1.59；1 秒和 20 秒几乎一样差。

也就是说：**Thompson 采样要求每条连接都用最新的后验**。哪怕只缓存 1 秒，
那些"刚刚拿到样本、后验应该收窄"的节点仍然按未知处理，继续被大量抽中，
把探索预算浪费在已经测过的节点上。

### 18.2 为什么不能直接上线

每条连接重算 = 每个候选一次 `scoreParts`：

| 池子大小 | 每条连接成本 |
|---|---|
| 30（仿真） | ~30 µs |
| 64（主动集） | ~60 µs |
| 800（现在） | **~800 µs** |

800 个节点时这个成本不可接受（100 连接/秒 = 8% CPU）。

### 18.3 所以 TS 的前置条件是主动集

TS 的收益（1.43 → 1.22）只有在候选集足够小、可以**每条连接重算**时才拿得到。
主动集（64 个）把这一步的成本压到 ~60µs，正好可行。

**顺序因此确定：先做主动集（Phase 1），再开 TS。** 现在 `LAT_TS=0` 默认关闭，
四个开关（`TS_CURSOR` / `TS_COLD_PASS` / `TS_FB` / `TS_TTL`）都留在 `SC` 里，方便复现。

## 19. 第 11 轮：主动集（Active Set）实测 —— 回滚

按 `docs/主动集设计.md` 实现了 Phase 1：`active.lat=64 / active.tput=16`、
每 60 秒补员、路由只排主动集、缓存键 `lat:a` / `tput:a`。

### 19.1 结果：没有净收益

| 场景 | 改前 | 主动集 |
|---|---|---|
| 真实画像 lat | 1.43x | **1.30–1.36x** |
| 真实画像 tput | 1.61x | **1.83–1.97x** |
| 规模 400 节点 | 1.34x | 1.43–1.69x |
| `candsFor`（400） | 519 µs | 341 µs |
| `pick`（400） | 8.3 µs | 12.9 µs |

lat 好了 5–9%，tput 差了 14–22%，规模场景差了 7–25%。**不划算，回滚。**

### 19.2 过程中挖出的两个真问题

**① `rankCache.t` 被多个缓存键共用。**
`lat:a` 的 20 秒 TTL 会被 `lat`（全量）的任何一次重建"续命"，导致主动集排行几小时不更新。
改成 `rankAt[key]` 之后又发现：`nsFail` 里的 `rankCache.t = 0` 失效了，
必须同时清 `rankAt`，否则失败后排行永远不失效（这一条会让 tput 从 1.61 掉到 1.97）。

**② `ensure` 只"空了才补"会被冷却成员越削越小。**
成员被 60 秒黑名单冷却 → `prune` 移出 → 集合从 64 掉到 20，而补员只在 cron 跑。
改成"掉到一半且距上次补员 >60 秒才补"，恢复到 63–64。

### 19.3 为什么主动集没兑现

设计假设是"64 个候选 × 每条连接重算"能同时提升覆盖率和排序精度。
实测里覆盖率确实上去了（`candsFor` 从 519µs 降到 341µs），但**排序精度没有**：
- tput 的候选从 30 缩到 16，抽签的方差变大；
- 规模场景里好节点被冷却时，主动集里没有足够的替补（储备池进不来）。

### 19.4 结论

主动集不发布。要重做的话，前提是先把 `rankCache` 的键粒度问题解决干净
（或者干脆对主动集不用缓存 —— 64 个节点的 `scoreParts` 只要 ~60µs），
并且给 tput 的主动集留足够的替补（24–32）。

代码已回滚，src 回到 6.31 + TS 开关关闭的状态；工具和本节保留。
