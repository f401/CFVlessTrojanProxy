# proxyip 轮换模块重构设计

目标：**每个 isolate 各自挑自己最优的节点**，同时把 KV 写入压到免费额度以内，并且冷启动不空手。

---

## 1. 现状问题盘点

| # | 问题 | 后果 |
|---|---|---|
| 1 | `cur` 是 KV 里的**单一全局值** | 所有 isolate 共用一个节点，但各自看到的延迟/带宽不同 |
| 2 | `alive` 的 `ms` 是**探测它的那个 isolate** 测的 | A 机房测 20 ms，B 机房复用这个数字，实际可能 200 ms |
| 3 | `NS_STATS`（吞吐/成败）是内存态，落盘又互相覆盖 | 只能"只增不减"合并，信息越滚越旧 |
| 4 | `px:meta` 每 60 秒回读 | 读放大；且本地脏时不采纳远端，跨 isolate 行为不一致 |
| 5 | 落盘节流拍脑袋定（10 s / 30 min） | 稍不注意就打出 8000 写/天 |
| 6 | 重建脚本 DO 清零 | 已用 `usage:snap` 修好，但同类问题在设计上要避免 |

核心矛盾：**"选哪个节点"本质是 per-isolate 状态，却被放在了全局 KV 里。**

---

## 2. 设计原则

```
① KV 只放「冷启动必需 + 重建成本高 + 体量小」的数据
② 所有「最优性判断」相关的状态留在 isolate 内存
③ 跨 isolate 只同步「信誉」，不同步「选择」
④ 任何一次写入都必须能回答：丢了会怎样？
```

按这条原则过一遍：

| 数据 | 丢了会怎样 | 该放哪 |
|---|---|---|
| 候选池（2000 条） | 要重新抓 6 个源，约 1–2 s | **KV**（重建成本高） |
| 节点信誉（Top 40） | 冷启动没有种子，需先探测才有节点可用 | **KV**（冷启动必需） |
| 当前节点 `cur` | 从信誉表里取第一名即可 | 内存（KV 只作种子） |
| 可用列表 `alive` | 重新探测 | 内存 |
| 本地延迟/吞吐/失败计数 | 重新积累 | 内存 |
| 黑名单 | 重新积累 | 内存 |
| 探测游标 `idx` | 从头扫，无所谓 | 内存 |
| 用户表 / 用量 | 业务数据 | KV / DO（现状不变） |

**结论：KV 里只保留 2 个轮换相关键 —— `px:pool:<gen>` 和 `px:seed`。**

---

## 3. 键设计

### 3.1 `px:pool:<gen>`（候选池，≈223 KB）

```jsonc
[
  { "h": "43.169.18.179", "p": 443, "src": "ipdb" },
  ...
]
```

- 写：**≤1 次/天**（TTL 到期重建，且有 60% 缩水守卫）
- 读：冷启动首次需要探测时读一次
- 代际切换：新池写 `px:pool:<gen+1>` 成功后才改 `px:seed.poolGen`

### 3.2 `px:seed`（节点信誉 + 池指针，≈4–6 KB）

```jsonc
{
  "v": 2,
  "ts": 1793970000000,
  "poolGen": 11,
  "nodes": [
    {
      "k": "91.215.153.143:443",   // host:port
      "cc": "BG",
      "ms": 218,                    // 最近一次探测延迟（任意 isolate）
      "bps": 178452,                // 吞吐 EWMA（字节/秒）
      "ok": 17,                     // 累计成功次数
      "fail": 2,                    // 累计失败次数
      "at": 1793969000000           // 最近一次失败时间
    }
    // 最多 40 条，按 (ms + 失败惩罚) 升序
  ]
}
```

- 写：**48 次/天**（每次 cron 一次）
- 读：冷启动一次 + 每 30 分钟刷新一次

### 3.3 不存在的键

| 旧键 | 处理 |
|---|---|
| `px:meta` | 废弃（内容拆进 `px:seed` + 内存） |
| `px` / `px:pool` / `px:alive` / `px:cur` | 已删，保留只读兼容一个版本周期 |

## 4. 内存状态（每个 isolate 一份）

```js
let POOL = [];            // 候选池（懒加载）
let POOL_IDX = 0;         // 探测游标
let ALIVE = new Map();    // "h:p" -> { h, p, cc, ms, src, atProbe }
let STATS = new Map();    // "h:p" -> { ok, fail, at, bps, msLocal }
let CUR = "";             // 本 isolate 当前使用
let BLACK = new Map();    // "h:p" -> 拉黑时间
let FAIL_MEM = 0;         // 连续失败计数
let SEED_TS = 0;          // 上次读 px:seed 的时间
```

---

## 5. 算法

### 5.1 打分（纯本地）

```js
function score(k) {
  const s = STATS.get(k) || {};
  const a = ALIVE.get(k) || {};
  const ms = s.msLocal || a.ms || 400;          // 优先本地实测
  const ok = s.ok || 0, fail = s.fail || 0;
  const rate = fail / (ok + fail + 2);          // 拉普拉斯平滑
  const mbps = Math.min((s.bps || 0) / 1048576, 20);
  const recent = s.at && Date.now() - s.at < 600000 ? 1 : 0;
  return Math.max(1, ms * (1 + 3 * rate) + fail * 40 + recent * 300 - mbps * 60);
}
```

### 5.2 取节点

```js
function pick() {
  const cands = [...ALIVE.keys()].filter((k) => !BLACK.has(k));
  if (!cands.length) return "";
  cands.sort((a, b) => score(a) - score(b));
  return cands[0];
}
```

### 5.3 失败与切换

```
连接失败（直连失败后连 proxyip 也失败 / 0 字节关闭）
  → STATS[cur].fail++ ; STATS[cur].at = now
  → FAIL_MEM++
  → FAIL_MEM >= 3 ? { BLACK.set(cur, now)（10 分钟）; CUR = pick(); FAIL_MEM = 0 } : 不动

连接成功（收到第一个下行字节）
  → STATS[cur].ok++ ; FAIL_MEM = 0
  → 记录本次吞吐样本：bps = bytes*1000/duration，EWMA 0.7/0.3
```

### 5.4 主动升级（每轮 cron 或每 10 分钟一次惰性检查）

```
best = pick()
if (best && CUR && score(CUR) - score(best) > max(30, score(CUR)*0.15) && score(best) < 250)
    CUR = best
```

滞回两个条件同时满足才切，避免抖动。

### 5.5 冷启动

```
if (!CUR) {
  seed = 读 px:seed（缓存 30 分钟）
  ALIVE  ← seed.nodes 前 8 条
  CUR    ← seed.nodes[0]        // 只要有一个可用节点，CF 站点就不会全挂
  POOL   ← 懒加载 px:pool:<seed.poolGen>
}
```

### 5.6 上报（每轮 cron，1 次写）

```
合并本地 STATS 到 seed.nodes：
    ok/fail 取 max，bps 取本地 EWMA，ms 取本地实测（没有则保留旧值）
排序、截断 40 条 → 写 px:seed
```

## 6. KV 预算（每天）

| 键 | 次数 |
|---|---|
| `px:pool:<gen>` | ≤ 1 |
| `px:seed` | 48 |
| `users` | 按面板操作 |
| `usage:snap` | 48 |
| `snap`（RTT/错误） | ≤ 48 |
| 轮换导致的额外写 | **0**（cur 不进 KV） |
| **合计** | **≈ 145 / 1000** |

读：冷启动 1–2 次 + 每 30 分钟 1 次/isolate ≈ 3 万/天，远低于 10 万上限。

---

## 7. 与现状的差异

| 维度 | 现在 | 新设计 |
|---|---|---|
| `cur` 存哪 | KV（全局） | 内存（per-isolate） |
| 冷启动节点来源 | KV 的 cur | `px:seed` 第一名 |
| 延迟数据 | 全局共享，可能失真 | 本地实测优先 |
| KV 写频率 | 30 分钟 + 轮换 + 惰性 | 30 分钟，**轮换不写** |
| 跨 isolate 同步 | 全量 meta（60 s 回读） | 只有信誉表（30 分钟） |
| 键数量 | `px:meta` + `px:pool:N` | `px:seed` + `px:pool:N` |

---

## 8. 迁移

1. 新代码启动时：若 `px:seed` 不存在 → 读旧的 `px:meta`，把 `state.ns` + `alive` 转成 `seed.nodes`，写一次 `px:seed`（1 次写）
2. `poolGen` 从旧 `state.poolKey` 里解析出来
3. 旧键保留只读兼容，一个版本周期后删除

---

## 9. 风险

| 风险 | 缓解 |
|---|---|
| 冷启动时 `px:seed` 读失败 → 没有节点可用 | 兜底：直接用 `EXTRA_HOSTS`（硬编码的公开池域名）先探一个 |
| 所有 isolate 都从 seed 第一名起步 → 短期集中在一个节点 | 加 10% 抖动：冷启动时从 seed 前 3 名里随机取 |
| 本地没有吞吐样本时，评分退化成延迟排序 | 与现状一致，可接受；样本随流量自然积累 |
| 池子重建失败 | 沿用 60% 缩水守卫，且新池写成功才切换代际 |

## 10. 待你确认

1. **seed 里放几个节点？** 建议 40（约 4–6 KB）；放更多对冷启动没帮助，只是多占空间。
2. **冷启动抖动要不要？** 建议要（前 3 名随机），否则所有 isolate 同时压在同一个节点。
3. **`px:meta` 是否直接废弃？** 建议保留一个版本周期只读兼容，之后删。
4. **探测频率**：现在每轮 cron 探 12 个。要不要每轮额外重测 `cur` + alive 前 3 名（+4 次探测，很便宜，能让本地延迟更准）？
