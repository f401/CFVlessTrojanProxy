# 已知限制清单（写 plan 用）

> 标注：`[实测]` 本系统量出来的　`[平台]` Cloudflare 文档口径，需以官方为准　`[设计]` 我们自己定的约束，改起来代价高

---

## A. 运行时（最硬的一层）

| # | 限制 | 影响 |
|---|---|---|
| A1 | `[平台]` Worker 是无状态 isolate，**没有跨请求的全局变量保证** | 所有“当前最优/统计”都是 per-isolate，随时可能归零 |
| A2 | `[实测]` isolate 生命周期从几十秒到几小时不等，**不可控、不可观测** | 任何“定时器驱动”的设计都不可靠 |
| A3 | `[平台]` 免费版 CPU **10 ms / 请求** | 解密大对象、大数组排序、正则大文本都会直接 1102 |
| A4 | `[实测]` 内存 128 MB/isolate，但真正的瓶颈是 A3 | 池子 308 KB 解密就曾把 CPU 打爆 |
| A5 | `[平台]` 只有 `connect()` 出站 TCP，**没有 TLS 客户端** | 无法主动打流测速；只能握手不能拉数据 |
| A6 | `[平台]` 无监听端口、无 UDP、无原生 socket 选项 | 端口/用户名做策略识别不可行 |
| A7 | `[实测]` WS 单帧有大小上限，超了要自己拆 | 现有 256 KB / 1 MB 分批逻辑 |
| A8 | `[设计]` 数据面**不得 await 持久化**，一律 `ctx.waitUntil` | 否则每连接多 100–300 ms |
| A9 | `[平台]` cron 在**独立 isolate** 里跑，且**拿不到 `request.cf.colo`** | cron 不知道自己在哪个机房 → 只能写“候选名单”，不能写统计 |

## B. 配额（免费额度）

| 项 | 限制 | 现状 |
|---|---|---|
| Worker 请求 | `[平台]` 100,000/天 | 连接数级别，远未到 |
| KV 读 | `[平台]` 100,000/天 | `[实测]` ~1,750/天 |
| KV 写 | `[平台]` **1,000/天** | `[实测]` ~288/天（余量 ~700） |
| KV 单值 | `[平台]` 25 MB | `[实测]` 池子 308 KB、seed 5.4 KB |
| KV 同键写频 | `[平台]` 1 次/秒 | 我们 30 分钟一次 |
| subrequest | `[平台]` 50/请求（免费） | cron 一轮约 28 个 TLS 握手 |
| DO | `[平台]` 不止请求数：**请求 / duration(GB-s) / 存储 / SQLite rows** | 目前只管计量，未做额外对象 |
| 出站流量 | `[平台]` 不限但有公平使用 | — |

**留给 plan 的预算：新增 KV 写 ≤ 700/天，新增 DO 请求 ≈ 0。**

## C. 数据面

| # | 限制 |
|---|---|
| C1 | 协议是 VLESS / Trojan **over WebSocket**，首包解析目标 `host:port` |
| C2 | **直连优先**：`dial(target)` 成功就不经过任何节点 |
| C3 | 只有直连失败（CF 托管站点、被隔离网段）才走 proxyip 中转 |
| C4 | `[实测]` 因此**大多数流量不经过节点** → 节点吞吐样本天然稀疏 |
| C5 | CF 隔离 IPv4 到自家网段，需要 IPv6 或中转才能通 |
| C6 | 背压：`bufferedAmount > 1 MB` 暂停读，最长等 30 s |
| C7 | 单连接只能近似计时（chunk 到达时间），拿不到 TCP 层信息 |
| C8 | 目标地址受策略拦截：私网/保留段 + 23 个危险端口（23/25/135/137/138/139/445/465/587/1433/1521/2049/3306/3389/5432/5900/6379/9200/11211/27017） |

## D. 状态模型（写 plan 时最容易踩）

| # | 事实 |
|---|---|
| D1 | `CURS{lat,tput}` / `ALIVE` / `NSTAT` / `FUNNEL` **全部 per-isolate** |
| D2 | 同一时刻不同 isolate 的“最优节点”**可以完全不同**，这是正确行为不是 bug |
| D3 | 面板 `/proxyip` 只反映**处理这次请求的那个 isolate** |
| D4 | 跨 isolate 只能靠 KV/DO，而 KV 有 B 的写额度、DO 有 duration 成本 |
| D5 | KV 没有 CAS，读-改-写**必丢更新**（多 isolate 同时写） |
| D6 | `px:seed` 单键装所有机房 → 必须分桶，否则冷启动继承到别的机房的延迟 |

## E. 观测能力边界（做选路算法必须知道）

**能测：**
- TCP 建连耗时、TLS 往返、首字节（三段计时）
- 探活失败的原因分布（`ok` / `err` / `notTls` / `noCf`）与探测所在机房：`/proxyip.probeWhy`、`.probeColo`
- 每连接上下行字节、每连接时长
- 成功/失败（可按阶段细分）
- 主动探测：TLS 握手 + 证书链（**只能拿到几 KB**）

**测不到：**
- 端到端带宽（除非有真实流量经过该节点）
- 客户端侧速度（客户端零上报）
- 链路丢包率（只能从 TLS 往返异常间接推断）
- 未来速度
- 直连流量的节点质量（根本不经过节点）
- 某个节点在**别的机房**的表现

## F. 已定死的设计决策（改 = 重做）

| # | 决策 | 原因 |
|---|---|---|
| F1 | 评分单位 = **毫秒当量** | 可解释、可调 |
| F2 | 吞吐**只**在 `tput` 模式参与排序，且靠影子采样覆盖 | 否则正反馈死锁 |
| F3 | 吞吐死锁由**采样机制**打破，不由公式打破 | — |
| F4 | `lat` / `tput` **双游标**，通过 `?mode=` 选择 | 一份订阅多分组 |
| F5 | `px:seed` 按 `byColo` 分桶；`*` 桶只存名单 | 防跨机房污染 |
| F6 | 吞吐**不进 KV**（除 seed 里的快照），DO 只做计量 | 额度 |
| F7 | 部署方式：`PUT` 且 **metadata 去掉 `migrations`** | 不删脚本、不重建 DO |
| F8 | 加密 `ENC1:`（AES-256-GCM，key=SHA-256(kek)） | 明文不上 KV/DO |

## H. 已知缺陷（未解，写 plan 时当作输入）

1. 吞吐样本只活在承载流量的那一个 isolate 里，**跨 isolate 最长 30 分钟才可见**。
2. 样本量普遍 `n = 1~3`，LCB / 置信区间**目前用不了**。
3. 直连占大头 → 很多节点**永远没有吞吐样本**（现在靠 5% 影子补）。
4. `schedSwitch` 关掉后，冷节点可能**长期不被使用**。
5. ~~影子流量是永久成本（5%），没有"置信后停止"的机制。~~ 已验证：降到 2%/1% 更差（§25.3），5% 是必要的探索预算。
6. cron 不知道自己的 colo，只能写名单，统计靠服务 isolate 自己写。
7. 没有 CV / 漂移检测，链路**慢慢变差**要几小时才反映。
8. 没有历史会话日志，**无法离线回放调参**。
9. 面板看不了别的机房；跨机房比较只能逐机房看。
10. ~~采样窗口按墙钟算，**把 stall 也算进分母**，会低估速度。~~ 已验证：stall 是同比例缩放，不影响排序；卡顿另有 `STALL×pStall` 项（§25.3）。

## I. 新 plan 的硬性验收条件

- 数据面不得 `await` 持久化
- 热路径不得解密 >10 KB 的对象
- 单请求 CPU 不得逼近 10 ms
- 新增 KV 写 ≤ 700/天
- 新增 DO 请求 ≈ 0（除非能证明 duration 可控）
- 部署不能删脚本（否则丢 DO 用量）
- 每一步必须可单独回滚
