# 吞吐采样设计 v1（真实中转流量 · 观测型）

> 目标：让「面板上的 kbps」变成一个**可信、可解释、不牺牲线上速度**的观测值。
> 前提：吞吐只能来自真实中转连接，Worker 无法主动测速（无 TLS 客户端，proxyip 只握手不给大流量）。

---

## 0. 一句话结论

把吞吐做成 **观测系统**，而不是 **测速系统**：

```
真实连接 → 每秒切窗 → 窗口样本(节点, 字节, 时长)
   → isolate 内存聚合(5 秒节流)
   → DO 单写者(唯一写者, 无丢更新)
   → DO alarm 定时滚动聚合(60s)
   → 面板直读 DO(不再走 KV, 不再等 30 分钟)
```

评分（选哪个节点）**不使用**吞吐，只用 RTT + 失败率。理由见 §8。

---

## 1. 数据通道要先分层，否则统计一定是骗人的

同一个 Worker 里其实有三种出站：

| 通道 | 触发条件 | 是否经过节点 | 现在有没有记账 |
|---|---|---|---|
| `direct` | 目标可直连（绝大多数） | ✗ | ✗（也不能记到节点上） |
| `node` | 直连失败 / 指定地区 / 空关闭重试 | ✓ | 只记到 `CUR` |
| `v6` | 配了 `env.cfIpv6` 且 IPv4 被隔离 | ✗ | ✗ |

**设计要点**：`st.via` 显式标注通道，三种分别计数。

面板顶部必须有一行：

```
今日 直连 96.8% · 中转 3.2% · 中转节点 2/14 有样本
```

没有这一行，用户永远会问「为什么 12 个节点是空的」。
真有 96.8% 走直连，那 12 个空节点就是**正确结果**，不是 bug。

---

## 2. 采样：窗口化，不要用整连接平均

### 2.1 为什么不用整连接平均
一条 2 GB 下载的平均值会被三样东西污染：
- TLS 握手 + TTFB（前 300 ms 恒为 0）
- TCP 慢启动（前 1~3 MB 速度爬坡）
- 客户端背压（最后一段是 0）

整连接平均必然**系统性偏低**，而且长连接和短连接不可比。

### 2.2 窗口规则

```js
// 每个连接一个窗口
st.win = { t0: now, bytes: 0 };

onDown(n) {
  st.win.bytes += n;
  const dt = now - st.win.t0;
  if (dt >= 1000 || st.win.bytes >= 262144) closeWindow();
}

closeWindow() {
  const dt = now - st.win.t0, b = st.win.bytes;
  st.win = { t0: now, bytes: 0 };
  if (dt < 200 || b < 32768) return;        // 太短/太小 → 丢弃，不进统计
  if (st.firstWin) { st.firstWin = false; return; }  // 首个窗口含慢启动，丢弃
  emit({ node: st.node, bps: b * 1000 / dt, w: 1 });
}
```

- **1 秒切窗**（或 256 KB 提前切）：样本密度与时间成正比，与速度无关
- **200 ms / 32 KB 门槛**：低于此无法区分"慢"和"噪声"
- **丢弃首窗**：慢启动 + TTFB 一律不算
- **每连接每 5 秒最多 1 个样本**：长连接不刷爆 DO

### 2.3 连接收尾的"尾巴样本"

连接关闭时若剩余 ≥ 32 KB 且 dt ≥ 200 ms，产出一个 `w = 0.3` 的低权重样本。
短连接（大量 20~200 KB 的页面）就靠这个进统计，否则它们永远采不到。
`w` 在 DO 侧折算成 EWMA 的 α：`α = 0.3 * w`。

## 3. 归因：`st.node`

```js
// 三条拨号路径都打标，直连不打
sock = await connect(...); st.node = px.host + ":" + px.port;
```

- 连接中途换路（空关闭 → proxyip 重试）：**重置窗口并丢弃换路前的窗口**，否则两段不同链路被平均成一条
- `st.node === ""` → 直连，只进 `funnel.direct`，不进任何节点
- 节点被拉黑/淘汰后，历史样本保留 24 小时（面板显示"已淘汰 · 2 天前"），不清零

---

## 4. 聚合：三件事必须同时记

单值 EWMA 不够，会掩盖"某节点时快时慢"。每个节点存三个量：

```js
NSTAT[k].spd = {
  ewma: 0,       // 常态值，α = 0.3 * w，用于面板主列
  p90:  0,       // 峰值能力，8 桶 log2 直方图插值（16 KB/s ~ 16 MB/s）
  n:    0,       // 样本数（面板显示 n=3 代表"结论不可靠"）
  at:    0,      // 最后样本时间
  up:   { ewma, n }   // 上行单独记，永不参与评分/主列
}
```

**上行必须分离**：上行速度由客户端上行带宽决定，和节点能力几乎无关。混在一起算，会得出"节点只有 30 KB/s"的错误结论（很多家宽上行就是 30 KB/s）。

**时间衰减**：`now - at > 24h` 的样本在展示上加 `·` 标记，评分权重线性衰减到 0。

---

## 5. 上报：DO 单写者 + alarm 定时

### 5.1 为什么不用 KV
| 方案 | 丢更新 | 跨 isolate 延迟 | 写次数/天 | 结论 |
|---|---|---|---|---|
| KV 直写 seed | **会**（RMW 无 CAS） | ≤ 30 min | 240 | 只够兜底 |
| cron 汇总 | 不会 | 30 min（cron 周期） | 48 | cron 的 isolate 没有内存，拿不到别人的样本 |
| **DO 汇总** | 不会（单实例串行） | **实时** | 见下 | ✅ |

cron 方案的根本问题：样本在**服务 isolate 的内存里**，cron 跑在**另一个 isolate**，它看不见。

### 5.2 结构

复用已有的 `Meter` 类，用另一个实例名，避免再加 migration：

```js
const spdDO = env.METER.get(env.METER.idFromName("spd"));
```

```
Worker(任一 isolate)                 DO "spd"
  ── 每 30 s 或满 32 条 ──►  POST /spd/add   （批量样本）
  ctx.waitUntil(...)          串行累加 ewma/hist/ring
                                    │
                             alarm 每 60 s
                                    ▼
                            滚动聚合 + ENC1 加密落盘
  ── 面板打开时 ──────────►  GET /spd/get   （一次读完 14 个节点）
```

`ctx.waitUntil` 保证不阻塞数据面；DO 冷启动即使慢，也只影响面板。

### 5.3 DO 内部数据结构

```js
{
  v: 1, ts,
  funnel: { direct: bytes, node: bytes, v6: bytes },
  nodes: {
    "h:p": { ewma, p90, n, at, r5: bps, r1h: bps, bytes, ok, fail }
  }
}
```
- `r5` / `r1h`：10 秒桶 × 6 / × 360 的环形，alarm 时滚出
- 全部 `ENC1:` 加密后 `storage.put("spd", ...)`，每 5 分钟最多落一次（写放大 = 12 次/小时/一个对象，可忽略）
- 重启后从 storage 恢复；恢复不出来就空跑，不影响数据面

## 6. 面板语义

| 列 | 含义 | 空值显示 |
|---|---|---|
| 握手 | 探活测得的 TLS 到证书字节（cron 每 30 min 全 alive 刷新） | `-` |
| 下行(5m) | DO 的 5 分钟窗口吞吐 | `未用` |
| 下行(24h p90) | 峰值能力 | `未用` |
| n | 样本数 | `0` |
| 最后 | 最后一次承载流量的时间 | `从未` |

`未用` 与 `0 KB/s` 必须区分：前者是"没数据"，后者是"测过，很慢"。

## 7. 成本

| 项 | 量级 |
|---|---|
| DO 请求（/spd/add） | 5 isolate × 2/min = **≤ 14,400/天**（有流量才发，实际约 1~3 k） |
| DO 请求（面板 /spd/get） | 你打开面板的次数，~ 20/天 |
| DO alarm | 1,440/天 |
| DO storage 写 | 288/天（5 分钟一次落盘） |
| KV 写 | **0**（吞吐彻底移出 KV；seed 里只留一个 60 分钟兜底快照，可选） |

注：若担心 DO 请求额度，把 `/spd/add` 的节流从 30 s 放宽到 120 s，量级直接除 4。

---

## 8. 关键决策：吞吐不参与选节点

看起来"用 bps 奖励快节点"很自然，实际上是个**死锁**：

```
只有被用过的节点才有 bps
  → 有 bps 的节点分数更高
  → 更会被选中
  → 冷节点永远没 bps
```

这就是现在"14 个节点只有 23 个里 1 个有数"的成因放大版。
所以：

- **选节点**：RTT（探活主动可测）+ 失败率 —— 这两个对**所有**节点都可得
- **吞吐**：只用于面板观测 + 一条**单向淘汰**规则：`ewma < 8 KB/s 且 n ≥ 5 且 at < 1h` → 打分加 200（降级），但不因此抬升任何节点

这保证了统计系统不会反过来扭曲选择系统。

## 10. 落地顺序

**P0（半天，纯本地改动，零新基础设施）**
- `st.via` 三通道计数 + `funnel` 展示
- 窗口采样替换现在的"整段 dt + 单一 CUR"
- 面板 `未用` / `0 KB/s` / `n` 三态

**P1（一天，加 DO 路由）**
- `Meter` 类加 `/spd/add`、`/spd/get`、alarm
- isolate 侧批量上报（30 s 节流）
- 面板改读 DO，KV 退出吞吐

**P2（可选）**
- 外部探针 `wsprobe.py --bench` 定时跑一遍，POST 真值给 DO 的 `/spd/bench`
- 这条才给得出"端到端 MB/s"，也是唯一能验证 DO 统计准不准的手段

## 11. 不变量（实现时必须守住）

1. 数据面绝不 `await` DO —— 一律 `ctx.waitUntil`
2. 任何统计失败都不得影响连接（`catch` 到底）
3. 直连字节永远不进节点桶
4. 上行永远不进主列与评分
5. `n = 0` 与 `bps = 0` 在展示层必须是两种状态
6. 删/换节点不清空历史，只让它自然过期

# v2 修订：观测主键必须是 (colo, node)

## V2-0 你说的是对的，而且它推翻了 v1 的两个假设

每个 isolate 的网络位置不同（不同 colo / 不同出口），所以：

1. **聚合键不能是 `node`** —— 必须 `(colo, node)`
2. **面板不能有"全局最优"** —— 只能有"某机房的视图"

还有第三个已经存在的隐性污染：

`px:seed` 是**单个全局键**，里面一张 `nodes` 表混着所有机房的 `ms`/`bps`。
`ensureAlive()`（`_worker_v3.js:1663`）冷启动时直接
```js
const top = (SEED.nodes || []).slice(0, SEED_COLD_N);
ALIVE.set(n.k, { ..., ms: n.ms || 400, src: "seed" });
```
把**别的机房测出来的延迟**当成本机房的值，然后立刻用它挑 CUR。
这不是"小瑕疵"：新 isolate 的第一个连接就建立在错误信号上。

## V2-1 分层结论：本地统计一直是准的，错的只有出口

| 层 | 现状 | 判定 |
|---|---|---|
| 每条连接采样 | 只记 CUR、整段平均 | ✗ 要改（v1 §2/§3） |
| isolate 内 NSTAT | 天然 per-isolate | ✅ **本来就是对的** |
| 本地评分 scoreOf | 只读本地 NSTAT/ALIVE | ✅ 对 |
| `px:seed` 出口 | 单键单表，跨机房混合 | ✗ 主要污染源 |
| 面板 `/proxyip` | 展示混合后的表 + 一个 `current` | ✗ 误导 |

所以 v2 不碰数据面，只改**出口与键空间**。

## V2-2 键空间

```js
const COLO = (request.cf && request.cf.colo) || "??";   // 每请求取一次，放 st 上
const vkey = COLO + "|" + node;                          // 观测主键
```

- **样本**：`{ vkey, colo, node, bps, w }`
- **DO**：
  ```js
  { v:2, byColo: { "AMS": { at, cur, nodes: { "h:p": {ewma,p90,n,at,r5,r1h} } }, ... } }
  ```
  只保留**最近 7 天出现过**的机房，上限 6 个（超出淘汰最久未上报的整个桶）
- **KV `px:seed`**：改为按机房分桶
  ```js
  { v:3, byColo: { "AMS": { nodes:[...], builtAt, lastSwitch }, "SIN": {...} } }
  ```
  读只取 `byColo[COLO]`；写只更新自己那一桶（**同机房共享经验，跨机房零污染**）

为什么选分桶而不是拆成多个 KV 键：键数不变 → 读次数不变；单值从 2 KB 长到 ~8 KB（3 个机房），远低于 25 MB 上限。

## V2-3 冷启动改为"继承同机房经验"

```js
const mine = (SEED.byColo && SEED.byColo[COLO]) || { nodes: [] };
for (const n of mine.nodes.slice(0, SEED_COLD_N)) ALIVE.set(...);
```
- 有同机房历史 → 直接继承，首连不慢
- 没有 → ALIVE 空，等 cron 探一批（首连走直连或随机，可接受）

## V2-4 面板：默认本机房，跨机房只做摘要

```
机房 AMS · 阿姆斯特丹        本机房 CUR 45.147.250.39 (2 分钟前)
今日 直连 96.8% · 中转 3.2% · 有样本节点 2/14

节点                 国家  握手   下行(5m)     下行(24h p90)  n    最后
45.147.250.39:443    IT    56ms   210 KB/s     193 KB/s      132  2 分钟前
91.215.154.80:443    BG    80ms   4 KB/s       4 KB/s        3    1 小时前
45.136.117.194:443   US    65ms   未用         未用          0    从未

其他机房（只读摘要，不混进上表）
SIN  91.215.154.80:443 · 上报于 1 分钟前
```

`?colo=SIN` 切视图。**绝不跨机房求平均。**
机房 ≥2 时可展开矩阵：

| 节点 \ 机房 | AMS | SIN |
|---|---|---|
| 45.147.250.39 | 56 ms · 193 KB/s (n=132) | 310 ms · 未用 (n=0) |
| 91.215.154.80 | 92 ms · 4 KB/s (n=3) | 88 ms · — (n=0) |

## V2-5 淘汰与降级也必须 per-colo

`AMS` 里 45.x 慢，不代表 `SIN` 里慢。v1 §8 的单向降级规则改成：

```
对每个 (colo, node)：
  if ewma < 8 KB/s && n >= 5 && at < 1h  → 该 colo 的评分 +200
```
黑名单 `PX_BLACK` 本来就是内存、本来就 per-isolate，天然 per-colo，不用改。

## V2-6 「当前节点」这个概念要拆开

现在是 `/proxyip` 返回一个 `current`，但实际有 N 个 isolate、N 个 CUR。
改成：DO 里记 `byColo[colo].cur + at`，每个 isolate 每次上报带 `{colo, cur}`（最后写者赢，够用）。
面板显示"本机房 CUR"，其他机房只显示名字 + 时间。

# v3 补充：额度预算与熔断（回答"会不会超套"）

## V3-1 结论

不会。原因是 v2 把吞吐**彻底移出了 KV**：

| 项 | v1（现状） | v2/v3 |
|---|---|---|
| 吞吐数据存放 | KV `px:seed`（每 isolate 都在写） | DO（不计 KV 额度） |
| KV 键数 | 5 | 5（不变） |
| KV 写 | ~205/天 | ~288/天（bps 变化驱动 + cron，≤30%） |
| KV 读 | ~1,750/天 | 不变 |
| **唯一新增计费项** | — | **DO 请求**，且有硬上限 |

## V3-2 DO 请求的硬上限

节流是"批量 + 时间窗"双闸门，所以请求数**只跟 isolate 数有关，跟连接数无关**：

```
每次上报条件：缓冲 ≥ 32 条样本  或  距上次上报 ≥ SPD_POST_MS
单 isolate 上限 = 86400 / SPD_POST_MS * 1000 次
```

| SPD_POST_MS | 天/isolate | 5 isolate |
|---|---|---|
| 30 s | 2,880 | **14,400** |
| 60 s（建议） | 1,440 | **7,200** |
| 120 s | 720 | **3,600** |

7,200 / 100,000 = **7%**。即使全开到 30 s 也只有 14%。

面板 `/spd/get`：你打开面板的次数，~20/天，可忽略。

**alarm 可以不要**：滚动窗口在 `GET` 时从 10 秒桶现算，落盘按"每 20 次 /add 落一次"触发（~144/天），
既不占 alarm 额度，也不需要定时器。

## V3-3 三种"会超套"的写法（别写）

1. **每个连接结束就 POST 一次** → 5,000 连接/天 × 5 机房 = 25,000 起步，流量大时 10 万+，直接打穿
2. **每个样本 POST 一次** → 一条 2 GB 下载 = 8,000 次请求，单连接就能打穿
3. **每秒 alarm 落盘** → 86,400 次/天，且触发存储写计费

共同点：把"上报"和"事件"绑定。必须绑在**时间窗**上。

## V3-4 熔断（最后一道保险）

每个 isolate 一个日计数器，写死在内存：

```js
let SPD_SENT = 0, SPD_DAY = "";
function spdGuard() {
  const d = new Date().toISOString().slice(0, 10);
  if (d !== SPD_DAY) { SPD_DAY = d; SPD_SENT = 0; }
  if (SPD_SENT >= 800) return false;   // 单 isolate 每天硬顶 800 次
  SPD_SENT++;
  return true;
}
```

800 × 5 = 4,000/天，比正常值还宽松，但一旦代码写错（比如误把上报放进 `onDown`），
**最多浪费 4,000 次请求就会被掐断**，不会一夜之间把额度烧光。这条比前面所有估算都重要。

## V3-5 还有两处会随机房数增长，但都无关紧要

| 项 | 1 机房 | 6 机房 | 上限 |
|---|---|---|---|
| `px:seed` 单值大小 | 2.1 KB | ~12 KB | 25 MB |
| seed 解密 CPU | ~0.3 ms | ~1.5 ms | 10 ms/请求 |
| DO 存储落盘 | ~9 KB × 144 | ~50 KB × 144 | — |

seed 解密那 1.5 ms 要小心：`seedWrite` 在 cron 里跑，cron 的 CPU 预算更宽；
但**别在连接热路径上解密 seed**（现在也没有）。超过 6 个机房就该把 seed 拆键了。

# v4 修订：DO 有额度 → 不新开对象，搭便车

## V4-1 DO 额度是 4 个维度，不只是请求数

| 维度 | 触发方式 | 谁最容易被忽略 |
|---|---|---|
| 请求数 | 每次 `stub.fetch()` | 容易数清楚 |
| **duration（GB-s）** | 对象"醒着"的时间 | **最隐蔽**：被定时器敲的对象几乎不睡 |
| 存储 | `storage.put` | 单次小，频率高了也可观 |
| SQLite rows 读/写 | 每次 SQL | SQLite-backed DO 才有 |

粗算：一个常驻的 DO，128 MB × 86400 s ≈ **11,000 GB-s/天**。
也就是说"每 60 秒上报一次"这种设计，请求数只有 7,200 看着很省，
但很可能先把 duration 那条线顶穿。**v3 里"新开一个 spd DO"的方案是错的。**

不该为了看一个数字，去跟计费计量抢额度。

## V4-2 改法：搭 Meter 的便车，0 新增请求

Meter 本来就在被 `pendFlush` 敲（自适应 3~60 s 一次），把一个几百字节的数组塞进**同一个 body**：

```js
// flushStat 里：样本只进内存队列
SPD_PEND.push({ c: st.colo, k: st.node, bps, ts, w });
if (SPD_PEND.length > 64) SPD_PEND.shift();

// pendFlush 里：附在第一封 /meter/add 的 body 上
body = JSON.stringify({ ...d, spd: primary ? SPD_PEND.splice(0) : undefined });
```

DO 侧：
```js
if (body.spd) for (const s of body.spd) merge(byColo[s.c].nodes[s.k], s);
```

收益：

| 项 | v3（新开 spd DO） | v4（搭便车） |
|---|---|---|
| DO 请求 | +7,200/天 | **+0** |
| DO 对象数 | 2 | 1 |
| alarm | 需要 | 不需要 |
| 新鲜度 | 60 s | **和 flush 同频（3~60 s）** |
| 一致性 | 串行 | 串行（同一对象） |
| 新增成本 | 额度 | **每次 body 多 300 B** |

而且它的生命周期是自洽的：**没有流量 → 没有样本 → 不需要上报**。

## V4-3 两个必须写清楚的约束

1. **只挂在主 uuid 的那封 flush 上**（`env.uuid` 的第一个）。
   挂到所有用户会在多个对象里各存一份，读的时候还得合并。
   副作用：主 uuid 长期不用时，面板数据会停住 —— 面板要显示"数据于 X 前"。
2. **`SPD_PEND` 有上限（64 条）**，超出丢最旧的。
   它是观测数据，丢了下次 30 秒又有一条，不值得为它做可靠投递。

## V4-4 降级路径（连那 300 B 都不想给）

纯 KV 版：样本进 `px:seed` 的 byColo 桶，跟着已有的 30 分钟写走。
- DO 请求 +0、KV 写 +0
- 新鲜度 ≤ 30 min
- 代价：单键 read-modify-write，多 isolate 同时写会丢一次观测（自愈，不致命）

`spdMode = "kv" | "do"`，一个绑定切。

# v5 备选方案盘点（跳出"观测真实流量"这条线）

v1~v4 其实是**同一条路线的四次迭代**（观测真实中转流量 → 换个地方存）。
真正不同的方案有六种：

| # | 方案 | 核心思路 | 额外请求 | 覆盖节点 | 真实性 | 新鲜度 | 复杂度 |
|---|---|---|---|---|---|---|---|
| A1 | 三段计时 | 不测速度，测"距离 + 链路质量" | 0（复用 cron） | **全部** | 中 | 30 min | 低 |
| A2 | 卡顿率 | 不测速度，测"卡不卡" | 0 | 有过流量的 | **高（体感）** | 实时 | 低 |
| B | 客户端真值 | 让真正的客户端上报 | 外部 | 全部 | **最高** | 看跑数频率 | 中 |
| C | 明文端口实测 | 走 :80 真拉 64 KB | cron 内 | 仅 :80 节点 | 低 | 30 min | 中 |
| D | 事件溯源 | 每条样本落 R2，查询时算 | 0（搭车） | 有过流量的 | 高 | 实时 | 高 |
| E | 按 colo 分片 DO | `idFromName(colo:uuid)` | 有 | — | — | 实时 | 中 |
| F | 人工试用 | 面板点一下切过去自己看 | 0 | 任意 | 最高（人） | 手动 | 极低 |

## A1 三段计时（推荐做默认）

```
t0 ──TCP──► t1 ──TLS──► t2 ──证书链──► t3
```
- `t1-t0` = 网络 RTT（距离）
- `t2-t1` = TLS 往返，**丢包/拥塞会让这段显著变长**
- `t3-t2` = 服务端处理

面板：`45.147.250.39  TCP 38 · TLS +52 · 首包 +120 ms`
价值：能分开"远"和"链路差"——这正是 kbps 想表达、但测不准的东西。
成本：`probeProxy` 已经在做这件事（`_worker_v3.js:1285`），只要把三个时间点记下来。

## A2 卡顿率（最贴近体感，且零成本）

每个节点承载的连接上统计：
```
stall = ws.bufferedAmount > WS_BUFFER_LIMIT 的累计毫秒 / 连接总毫秒
```
面板：`卡顿 0.4%`。
优点：**与连接大小、客户端带宽无关**，长短连接可比；直接对应"卡不卡"。
缺点：不直观，用户第一眼看不懂。

## B 客户端真值（唯一真速度）

探针从 `/cl` 拉节点列表 → 逐个 `wsprobe --bench 1MB` → POST `{node, colo, MB/s}`
→ 走 v4 的搭便车存进 DO / 或直接进 KV。
要一台常开设备：路由器、NAS、手机 Termux 都行。
它是**校准其他所有指标的基准**，但不该是唯一来源。

## C 明文端口实测（实验性）

对池子里 `:80` 的节点：`connect` 后发 `GET / HTTP/1.1\r\nHost: <cf托管域>\r\n\r\n`，
读 64 KB 计时。**能真测出速度**，但：
- 只覆盖明文节点
- CF 的 80 会 301 到 https，路径与生产（443）不同，数据不可直接比
结论：只能当"这个 IP 出口大概多快"的旁证，不进主表。

## D 事件溯源

每条样本一行写 R2（100 万写/月免费），查询时拉回算 p50/p90。
好处：任意时间窗、可回溯排查。坏处：多一个绑定、查询要全量拉。
只有当你打算"认真做网络分析"时才值得。

## E 按 colo 分片 DO

`idFromName(colo + ":" + uuid)` —— 天然分片、天然 per-colo、单写者。
但会重建现有用量数据（不可接受），只适合"将来真要上 DO"时用。

## F 人工试用

`/proxyip?use=<h:p>` 一键切过去，跑两分钟自己看。
零统计成本、最真实（人肉感知），适合个人自用。

---

## 推荐组合

```
默认 = A1（全覆盖、0 成本）+ A2（体感、0 成本）+ F（想较真时点一下）
可选 = B（要一条"真速度"基准线时开）
不做 = C（数据不可比）、D（过度设计）、E（会重建用量）
```
