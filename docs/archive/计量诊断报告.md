---

## 2. 结论：不是"计数器算错"，是"计数来不及落地"

### 2.1 算式验证

旧实现的结算时机只有两种：

1. 连接结束（`.finally` → `flushStat`）
2. 累计满 1 MB 时的中间结算

若连接在 `[已结算点, +1 MB)` 之间被强制中断，这段就永久丢失，**平均损失半档 ≈ 0.5 MB**。

实测缺口 ÷ 连接数 = **429 KB/条**，与"平均丢半档"几乎完全重合。

### 2.2 旁证：连接数异常

一次 5.73 GB 的下载产生 **4,084 条连接**，平均每条只跑 **1.4 MB**。

正常情况一条长连接能跑几百 MB。说明连接在被持续中断，客户端不断重连续传。

连接中断 → 尾部字节未结算 → 每条丢几百 KB × 4,084 = 1.7 GB。数字对得上。

---

## 3. 为什么连接会被频繁中断（同时解释"降速"）

按可能性排序：

| # | 假设 | 依据 | 验证方法 |
|---|---|---|---|
| 1 | 客户端侧网络不稳（重传/断流自动重连） | 同机直连 jsdelivr 实测 23–115 KB/s 剧烈波动 | 换网络或换客户端再跑 |
| 2 | Worker CPU 上限触发 | 混淆后每字节多几条指令；免费版 CPU 配额低 | 换明文版跑同一文件，比较连接数 |
| 3 | 中转节点质量差 | 当前 `cur` 为 732 ms 的日本节点 | `/proxyip` 看 alive 延迟 |
| 4 | 客户端启用多线程分段下载 | 4,084 连接 / 5.73 GB | 看下载器设置（IDM/aria2 默认 8–32 线程） |

假设 1、4 会同时放大连接数，也同时放大计量缺口。

## 4. 修复方案

### 4.1 已改代码、尚未部署

| 改动 | 位置 | 效果 |
|---|---|---|
| 增量结算阈值 **1 MB → 256 KB** | `handleUpgrade` 两处 | 单连接最坏丢 256 KB，平均 128 KB |

预期：同等条件下缺口从 1.79 GB 降到 **~0.5 GB**。

### 4.2 已部署（上一轮）

| 改动 | 效果 |
|---|---|
| `flushStat()` 每满阈值即结算并推 DO | 不再依赖连接结束 |
| PEND 推送 5 s → 3 s | 缩小"已推进 PEND 但没送到 DO"的窗口 |
| `usage:snap` 自动续接 + `?restore=1` | 重建后不再从 0 开始 |

### 4.3 进一步收紧（需权衡）

| 方案 | 缺口 | 代价 |
|---|---|---|
| 阈值 256 KB（待部署） | ~0.5 GB / 5.7 GB（9 %） | 无 |
| 阈值 64 KB | ~0.13 GB（2 %） | DO 请求数 ×4 |
| 每 500 ms 定时结算 | 通常 <2 % | 需要定时器，复杂度上升 |
| 数据面 `await` 推 DO | 接近 0 | 每 256 KB 增加 5–20 ms 延迟，不建议 |

## 5. 需要你确认的四件事

1. **5.73 GB 从哪来**：Clash 配置页"已用"？连接面板单条连接的"下载"？下载器显示？系统流量监控？
2. **下载方式**：单线程，还是多线程/分段（IDM、aria2、迅雷类）？
3. **是否中途切换过节点**（切换会强制断开所有连接）。
4. **同时间段 Clash 显示的总量** —— 用于判断是"我们漏记"还是"客户端把重传也算进去了"。

判据：

```
我们增量 ≈ 客户端显示   → 口径一致，之前的差额来自历史重置
我们增量 <  客户端 30 %+ → 中断丢尾（本报告结论）
我们增量 >  客户端显示   → 客户端做了去重
```

---

## 6. 建议执行顺序

```
1. 你确认第 5 节的四个问题
2. 部署 256 KB 阈值版
3. 再跑一次同规模下载
4. 复核：缺口应降到 10 % 以内；若仍 >20 %，说明中断频率才是主因，
   下一步查"为什么连接会被掐"（客户端 / CPU / 节点）
```
