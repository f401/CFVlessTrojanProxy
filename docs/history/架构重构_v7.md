# 架构重构 v7：三层决策 + 证据/判定/执行分离

> 历史文档：记录的是当时的方案与实测，**不要照此改代码**；当前设计见 `docs/v8.md` 与 `docs/ARCHITECTURE.md`。

> 背景：6.35→6.53 这十几轮里，我们靠实测推翻了好几个先验（x.com 按出口 IP 族封、CF→CF 透传客户端 IP、
> 优选 IP 只能提高概率不能改判）。代码里因此长出 9 个并行的判定机制，`session.ts` 贴着 560 行上限。
> 本文把架构重新组织成「**三层决策 + 一条证据链**」，并把旧机制的去留写清楚。

## 1. 已被实测确认的事实（架构必须服从它们）

| # | 事实 | 证据 |
|---|---|---|
| F1 | x.com 托管在 CF，Worker 直连会被自家边缘丢弃或偶发 403 | 直连 `?px=0` 200 @ VIE/ARN/MXP/TLL，403 @ SOF/MRS/CPH |
| F2 | 403 的响应体恒为 4 字节纯文本 `IPv6` | 多次抓包，`content-type: text/plain` |
| F3 | 走 CF 边缘中继时 X 看到的是**客户端 IP** | 换中继不改判；直连/中继失败面完全重合 |
| F4 | 只有**非 CF 主机**重新发起连接才改判 | 旧 seed 的 25 个非 CF 中继；实测 `45.136.117.194` 通、两条 CF 中继 403 |
| F5 | 封禁粒度是**机房**，不是单个 IP | 同一 IP 多次解析落到不同 colo，结论跟着变 |
| F6 | 客户端 IPv6 + CF 托管目标 = 必 403 | 钉 IPv4 入口 4/6，默认双栈 0/6 |
| F7 | 隧道里的 HTTP 状态码**可以看见**，但要自己实现 TLS 1.3 | subtls（纯 JS + SubtleCrypto）：microsoft/github/apple 全 200 |
| F8 | 每个探测 = 1 个 `connect()` = 1 子请求；免费计划 50/请求 | API 文档 + 实测 503 |
| F9 | 老 `nodes` 清单（9 条入口）随删脚本丢失，订阅只剩域名 | 订阅实测 `server: nanlianqing.ccwu.cc` × 20 |

## 2. 三层决策（这是新架构的骨架）

一次请求要回答三个**互相独立**的问题，旧代码把它们混在 `session.handleUpgrade` 里：

```
L1 入口决策（客户端 → CF 边缘）：走哪个边缘 IP？
   └─ 只在订阅里生效（客户端选），服务端只负责「测量 + 排序 + 下发」
L2 通道决策（CF → 目标）：直连 / 哪条中继？
   └─ 服务端每请求决策，依赖「目标 IP × 通道 IP」的判定表
L3 目标决策（哪一个 A 记录）：x.com 有多个 IP，某些 IP 本身被封
   └─ 直连可钉死（connect(ip) + SNI=域名）；中继不可钉（中继自己解析）
```

三层各自的输入、输出、存储、失败模式都不同 —— 这是必须分开的根本原因：

| 层 | 输入 | 输出 | 存储 | 失败模式 |
|---|---|---|---|---|
| L1 入口 | 客户端 → edge 的 TLS 时延/成败 | 有序 IP 列表（进订阅） | KV `edge:pref` | 下发坏 IP → 全部超时 |
| L2 通道 | 目标 IP + 通道类别 + 判定 | `direct` / `relay(ip)` / 放弃 | 判定表 + 池子 | 选到被封通道 → 403 |
| L3 目标 | DoH A 记录 | 具体 IP（或 `*`） | DoH 缓存 | 选到被封 IP → 403 |

## 3. 证据 / 判定 / 执行分离

```
① 证据层（只记录）
   traffic  : flush 里的 via/chan/ttfb/down/failed
   probe    : subtls TLS+GET 的真状态码（唯一能看见 403 的手段）
   client   : 订阅 expected-status 的回流（端到端，最可信）
        ↓ 统一入口 recordProbe()/recordTraffic()，幂等、去重
② 判定层（只表态）
   verdict 表：target|chan → {state, code, ms, n, at, src}
   supply  表：ip → {admit, ms, pFail, capBps, ...}（池子现有统计）
        ↓ 只回答「能不能过 / 有多快 / 有多可信」，不做选择
③ 执行层（只决策一次）
   policy.decide(host, family, mode) → {chan, reason}
   session 只负责：调用 decide → dial → 连接收尾写证据
```

三条硬规则：

1. **只有 probe / client 能产生 blocked/dead**；traffic 最多 `suspect`（避免小响应误判）
2. **判定不写池子黑名单**（「这机器连不上」≠「这机器对这个站点不行」）
3. **执行层只有一个决策点**：`policy.decide()`；其它任何地方不许再「顺手判断一下」

## 6. 请求生命周期（新）

```
1. 解析首包 → 得到 host, port, cmd
2. family = clientIpFamily(cf-connecting-ip)        // v4 / v6
3. d = policy.decide(host, family, mode, sz)        // 唯一决策点
     ├─ 解析目标 IP（DoH 缓存 10 分钟，最多 4 条）
     ├─ 候选 = direct + relay(活节点) + 按 family/类别过滤
     ├─ 过滤 blocked/dead（全灭 → leastBad）
     ├─ 打分 = base(ms 当量) + 风险(suspect) + 排队 + 抖动；unknown 走乐观面
     └─ 返回 {chan, reason}
4. d.chan === direct → dial(host) 三级降级；否则 connect(chan.ip) → 写首包
5. 数据面 pipeBack（不变，512KB tick）
6. 收尾 flush → observe.recordTraffic(...) → 写 suspect/ok
7. 若在 cron 窗口 → budget.pick() → probe → observe.recordProbe(...)
```

`reason` 会进计数（`why:*`），面板能直接回答「为什么这次没走中继」：

```
why:verdict-ok / verdict-blocked / no-candidate / v6-cf-target / direct-first
    / unknown-explore / all-blocked-fallback / manual-px / forced-px
```

## 7. 预算（每轮 48 子请求 / 10ms CPU）

| 用途 | 保底 | 上限 | CPU |
|---|---|---|---|
| 池子准入（裸 TLS 握手，无 HTTP） | 8 | 32 | ≈0 |
| 判定探测（subtls + GET） | 4 | 12 | ≈1ms/次 |
| 入口偏好（探自家 `/health`） | 0 | 2 | ≈1ms/次 |
| 流量触发的即时确认 | 0 | 剩余 | 同上 |

分配公式：`价值 = 流量占比(站点) × 代价(通道) × 陈旧度`，先保底再按价值。

## 9. 不变量（写进 code review 清单）

1. `probeTls` 永不抛错，内部接住 socket pump 的 reject（否则 1101）
2. 判定表只存证据；写入路径不做决策
3. blocked/dead 不得导致「无候选」，必须有 `leastBad()` 兜底
4. 一次请求内 `probe` ≤3，一轮 cron ≤12（见 §7）
5. `?vt=` / `?why=` 只读，不改池子
6. 只有 `policy.decide()` 能决定通道；`session` 里不许再出现 `if (isCfHost(...))` 这类判断

## 10. 与「采样算法」的关系（不推翻，只上移）

`score.ts` 的毫秒当量评分、`pickThom` 的单层抽样、S 参数化目标流量，全部保留 —— 它们是 **L2 的 base 代价与探索机制**。
变化只有一处：抽样池的**成员**从「节点」变成「通道」（`direct` 也算一个通道），
`σ` 里多一项「判定不确定性」（`blocked` 概率未知时 σ 大）。

## 11. 待定问题（需要决策）

1. **L3 是否值得做**：直连能钉目标 IP，中继不能。若线上直连本就少见（F1/F6），L3 只在 `direct` 分支有意义，可能只保留「解析 + 跳过被封 IP」两行。
2. **`capBps` 是否降级**：中继多为转发机，带宽采样价值低；降级可省一半池子 CPU，但「批量 16MB」场景精度会降（仿真 1.30x）。
3. **判定持久化**：现在只在 isolate 内存里。是否值得写 KV/DO？我倾向只把「入口偏好」落 KV（订阅要用），通道判定留在内存（30 分钟 TTL，重建成本低）。
