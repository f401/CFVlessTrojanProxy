# v8 设计

> 本文是 v8 的**重写版**：只留结论、规则与证据，删掉了过程日志（那些在 git 历史和 `docs/archive/` 里）。
> 实现时配着看 [`v8实现清单.md`](v8实现清单.md)——那是一页可勾选的硬规则。

---

## 0. 用一句话说清 v8

**v8 把「哪条出口能过这个站点」变成一条可验证、可共享、会过期的事实，然后拿这条事实去挑节点。**

现在的版本（线上 7.86）里，每个 isolate 各自记各自的经验，冷启动时什么都不知道，只能盲选；而且「成功」的判据是 2xx，导致业务 403 和真封锁分不开。v8 改三件事：

1. **事实层**：把「这条中继出口是 v4 还是 v6」「这个站点在这条出口上大概多能过」「这条出口被这个站点拒过」写成带证据等级的记录，放 Durable Object 里全队共用。
2. **判定闸门**：只有「同一时间窗、有对照通道拿到整页」这种有对比的观测才算证据；没有对照就弃权，宁可什么都不写。
3. **选路**：先按硬事实排除（被封锁的、坏掉的），再按代价排序（首字节 + 目标流量的传输时间），族与通过率只做**偏置**，绝不做硬过滤。

**收益（都带条件，见 §8）**：x 这类「会按 IP 族拒绝请求」的站点，首请求成功率从 **40% → 92–96%**（前提是池里至少有一条可用的非 CF 出口），冷启动从 37.7% → 84–90%。
**代价**：冷启动第一条连接最多多等 200ms 读一次事实；每天约 85 次 KV 写（额度 1000）；DO 请求约等于连接数/3（额度 10 万）。

## 1. 要解决的问题

| # | 现象 | 根因 | 证据 |
|---|---|---|---|
| P1 | 同一个站点，一会儿 200 一会儿 403 | 出口地址族按连接抽签；v6 出口被目标概率性拒绝 | 8 条中继里 3 条 v4；v4 出口 6/6 与 21/21 过，v6 出口 2/16 |
| P2 | 冷启动前几条几乎必坏 | 事实只在 isolate 内存，新 isolate 从零开始 | 每条 isolate 平均只跑 3 条连接；20% 请求落在冷 isolate |
| P3 | 业务 403 被当成封锁，好节点被踢 | 「成功 = 2xx」；没有对照就下结论 | 7.57：通配封锁把池子标死后成功率 97% → 2/20 |
| P4 | 吞吐最快的节点常常不能过这个站点 | 吞吐与「能过」是两个维度，按一个维度排序必然把坏机器排前面 | 1642 KB/s 的出口对 x.com **0/8**；469 KB/s 的出口 **4/4** |
| P5 | 「最优节点」学不出来 | 每个 isolate 只看到 3 个样本，后验停在先验 | 仿真：本地 `ps` 36.9% ≈ 盲选 40.2% |
| P6 | 额度看着快满了 | 事实若按每请求逐条写，直接把 DO 请求打满 | 2100 请求 = 2100 次写；上限 ≈ 连接数/3 |

## 2. 设计总览

```
用户连接
  │
  ├─① 读事实（冷 isolate：≤200ms，Cache API 优先，DO 兜底；single-flight）
  │
  ├─② 硬过滤：只有 dead[relay]（连接层失败，绝不由业务响应产生）—— blk ≠ 排除
  │
  ├─③ 排序：score = transport(mode) / max(0.25, p)
  │        transport(tput) = ttfb + 512KB / max(32KB/s, cap×64KB/s)
  │        transport(lat)  = ttfb
  │        p = (ok + 4·prior) / (ok + bad + 4)，prior 由 eg 族给出（v4 0.95 / v6 0.5）
  │
  ├─④ 拨号：2.5s 超时、失败最多换一条、CF 托管站点优先非 CF 出口
  │
  ├─⑤ 记账：本条连接的 ttfb / 下行 / 是否 tiny / 是否整页
  │
  └─⑥ 写事实：isolate 结束即冲写（≤3 行），经 commitFact 的闸门
```

**四条不变量**（任何改动都不能破坏）：

1. **永不返回空候选**：全部被排掉时走 `leastBad()`（分最低但历史上出过整页的那条），最差也是直连。
2. **事实只影响排序，不影响协议**：读事实失败就当作没有事实继续选，绝不因为事实层异常而失败请求。
3. **封锁只降权、不排除**：`blk` 必须「同窗口另一通道拿到 ≥20KB 整页 + 三批 ≥60s」，写入后只把该 (host,relay) 代价放大 ×6；**唯一的硬排除是 `dead`**，而它只能由连接层失败产生。
5. **业务响应永不导致候选消失**：任何 HTTP 响应（含业务 403/401/415）都无法写 `dead`，因此任何业务 403 观测都不能让候选集合变小（§15）。
4. **共享的只能是事实，不能是统计**：`eg`/`blk`/`dead`/`dns`/`cap` 可共享；`ttfb`、绝对 KB/s、每 isolate 的路径统计不共享（换 isolate 就换路径）。

## 3. 事实层

### 3.1 五类事实

| 事实 | 键 | 来源（证据等级） | TTL | 共享 |
|---|---|---|---|---|
| `dns` | host | DoH 查 A/AAAA（**A 客观**） | 24h | ✅ |
| `eg` | relay IP | 经中继打回显服务拿到 IP 字面量（**A 客观**） | 6h（在用 1h） | ✅ |
| `ps` | `host\|relayIP` | 真实连接的成败（**B 统计**，EWMA） | 45min | ✅ |
| `blk` | `host\|relayIP` | 同窗口差分 + 三批确认（**A 差分**） | 90min | ✅ |
| `dead` | relay IP | 连不上 / 证书不对（**A 客观**） | 30min | ✅ |

两条容易搞错的：
- **`ps` 是成功率，不是封锁标记**。它只进分母折价（`/max(0.25, p)`），永远不排除任何候选。
- **`dead` 是唯一的硬排除**（连不上 / 证书错 / RST，与业务语义无关）；`blk` 只做 ×6 代价放大，**永不从候选里移除**。

### 3.2 写入闸门（`commitFact` 的顺序就是规则）

自上而下，命中即返回：

| 序 | 条件 | 结果 |
|---|---|---|
| 0 | 同键 60s 内已写过 | 丢弃 `R_THROTTLED` |
| 1 | 回显能解析出 IP 字面量 | 写 `eg` |
| 2 | 连接错误（x509/tls/reset/timeout）且中继腿 | 写 `dead` |
| 3 | `429` | 丢弃（只退避） |
| 4 | 4xx 且同窗口无任何通道拿到 ≥20KB | 丢弃（站点级，分不清是谁的问题） |
| 5 | `tiny` + 有 ≥20KB 对照 + **三批 ≥60s 且每批 ≥3 次** + 中继腿 | 写 `blk`（软：只降权 ×6） |
| 6 | `down > 0` 且非 `tiny` | 写 `ps(ok)` |
| 7 | 零字节且非连接错误 | 丢弃 `R_NO_BYTES` |

三个判据的定义（**只用结构量，不读内容**）：

```
tiny     = down > 0 && down <= 2048 && down < 0.2 × bigTypical[host]
hasBigPeer = 同 120s 窗口内，另一条通道拿到 >= 20KB
confirmed  = 与上一批相隔 >= 60s，且结论一致
```

> 为什么不用「≤64 字节」：封锁页曾经是 4 字节 `IPv6`，现在是 **737B HTML**。绝对值判据一定会被对手改形态废掉，相对自身典型尺寸才稳。
> 为什么业务 4xx 不会被误判：`api.github.com` 的 415 带 1277B 正文，`bigTypical` 也是 1277B，比值 ≈ 1，不满足 `tiny`。

### 3.3 存储：DO 的一张表

```sql
CREATE TABLE facts (
  kind TEXT NOT NULL,   -- dns | eg | ps | blk | dead | cap
  k    TEXT NOT NULL,   -- dns: host   eg/dead/cap: relayIP   ps/blk: host|relayIP
  at   INTEGER NOT NULL,
  j    TEXT NOT NULL,   -- 短键 JSON（ps 单行 < 40B）
  PRIMARY KEY (kind, k)
) WITHOUT ROWID;
CREATE INDEX idx_facts_at ON facts (kind, at);

-- 唯一写入口：旧证据永不覆盖新证据（严格 >，相同 at 也丢弃，防两个 isolate 乒乓）
INSERT INTO facts (kind, k, at, j) VALUES (?, ?, ?, ?)
ON CONFLICT (kind, k) DO UPDATE SET at = excluded.at, j = excluded.j
WHERE excluded.at > facts.at;
```

容量：`dns 512 / eg 512 / ps 512 / blk 1024 / dead 256 / cap 256` 行。读必须**按 kind 分片**（`?s=eg&since=`）——实测 1000 行 = 82KB，整库最坏 ~250KB，一次全量读会吃掉免费计划几十毫秒的 CPU 预算。

### 3.4 额度账

| 项 | 用量 | 额度 | 说明 |
|---|---|---|---|
| KV 写 | ~85/天 | 1000/天 | `px:seed`、`px:pool:<gen>`、`snap`、`usage:snap`、`users` |
| KV 读 | ~500/天 | 10 万/天 | 冷启动 + 订阅 |
| DO 请求 | 连接数/3 | 10 万/天 | 上限 ≈ 30 万连接/天；超了按 `k` 抽样写 |
| connect 并发 | 6 | 6 | 真正的瓶颈，见 §5 |
| 子请求 | ≤48/轮 | 50 | 探活走 `connect()`，**不占**这一项 |

> 事实层不是额度瓶颈：**先撞顶的永远是「请求/天」本身**。真正的约束是 `connect()` 的 6 个并发名额。

## 4. 判定：什么算封锁，什么不算

四类现象必须分开，混在一起就是 7.57 那次事故的原因：

| 现象 | 长相 | 怎么判 | 动作 |
|---|---|---|---|
| 业务 4xx | 带站点自己的页面（1277B 的 GitHub JSON、932B 的 example 页） | 相对自身典型尺寸**不算小** | 原样透传，永不封锁 |
| 族级拒绝 | 737B HTML，正文提 `IPv6` | 同窗口有另一族出口拿到整页 | 只降权（`ps`），不写 `blk` |
| 单 IP 封锁 | 与族无关，某条出口稳定失败 | 三批差分确认 | 写 `blk[host\|relay]`：×6 降权 90 分钟，**不排除** |
| 中继自身坏 | 证书错 / RST / 超时 / 回自己的页面 | 连接层错误 | 写 `dead`，30 分钟 |

判定协议（A/B/C 三级）：

- **A 级**（可写 `blk`，软降权）：同窗口两条腿——腿 A「新鲜 `eg=4` 且拿到 ≥20KB」，腿 B「新鲜 `eg=6` 且只拿到 `tiny`」；**三个独立批次（间隔 ≥60s、每批 ≥3 次）结论一致**。
- **B 级**（只进内存，±10 分钟）：单批 `tiny` + 同窗口整页对照。用于把「弱」压下去，但不能硬排除。
- **C 级**（只计数）：单次观测、429、直连腿的 4xx、>1KB 的非站点页。

三条禁令：
1. **直连腿的 403 永不进共享事实**——那是 CF 边缘的出站身份，归属不到稳定对象。
2. **全通道 4xx 永不写封锁**——那时我们分不清「站点拒绝所有人」和「这批出口被封」。
3. **`blk` 永不外发到其他站点**，也永不外发通配键（`*|relay`）。7.57 用通配封锁把整池标死：97% → 2/20。

## 5. 选路

### 5.1 代价函数

```
p        = (ok + 4·prior) / (ok + bad + 4)        prior: eg=4 → 0.95, eg=6 → 0.5, 未知 → 0.5
score    = transport / max(0.25, p)
tput     = ttfb + 512KB / max(32KB/s, cap × 64KB/s)   // cap 是相对池内中位数、已过噪声门
lat      = ttfb
```

三条设计理由：
- **`p` 进分母而不是加常数**：`p=0.125` 的通道代价被放大约 8 倍，足以让它排到后面，但**永远排不完**（仍能被选中，池子不会枯竭）。
- **`cap` 是比值不是绝对值**：绝对 KB/s 换 isolate 就不可比（同一中继跨轮摆动 0.82–1.74x）。
- **噪声门**：同一中继两次测得的极差 ≤1.5x、且与池内中位数差 <2x 时，视为没有可学差异，不记 `cap`；此时 `/health` 标 `thr:"link-bound"`，按 `ttfb` 排即可——**不假装在优化吞吐**。

### 5.2 排序链

```
硬过滤（只有 dead）
  → 负记忆（负面证据，10 分钟）
  → 正记忆（最近出过整页，10 分钟）
  → score 升序
  → ip 字典序（保证确定性，测试可断言具体哪条）
```

**候选为空的兜底顺序**（`leastBad()`）：① 直连；② 最近出过整页的中继（按 `at` 降序）；③ 最后一个变成 `dead` 的中继。理由：8 条全 `dead` 时拿「刚死掉的那条」顶替等于换了个坏通道，直连至少语义正确（§15.7 S5 实测触发 140 次）。

`eg` 只出现在 `prior` 里（+0.25 量级的偏置），**不单独决定**：仿真里「只按出口族确定性选择」只有 **14.3%**，比盲选 40.2% 还差——因为一旦钉住「族对但站点拒」的那条就永久钉死。

### 5.3 冷启动三条路

| 情形 | 动作 | 代价 |
|---|---|---|
| warm（`alive` 非空、事实有） | 正常排序 | 0 |
| cold + 有缓存 | **最多阻塞 200ms** 读事实（Cache API 优先） | 首字节 +≤200ms，收益 40%→90% |
| cold + 无缓存 | 不阻塞，后台补 1 条回显探测（受波次限流） | 0，但这一条请求仍盲选 |

预算算术：`命中率 ≈ 1 − exp(−λ · TTL/60)`。个人自用（λ<0.5/分）命中率天然只有 ~33%，所以 200ms 这条预算必须保留——它在高流量下代价为 0，低流量下值 9 个点。

### 5.4 康复与探索

- **康复通道**：每 20 条请求放 1 条走「分数最低、但历史上有过整页」的中继。没有它，被误判的节点永远拿不到样本、永远恢复不了（D12）。
- **同质化检测**：候选 `p` 的 `max/min < 1.5` 时视为同质，改走轮换——弱池会被 `ps` 坍缩成个位数成功率并锁死。
- **探索**：8% 的请求不看分数（无记忆的候选优先），用于发现新出口。

## 6. 预算与并发

免费计划的三个额度，按约束强度排序：

| 约束 | 数值 | 后果 |
|---|---|---|
| 并发 `connect()` | **6** | 最硬。40 并发时 14 次探测 × 250ms ÷ 6 ≈ 583ms，p95 从 250 → 675ms |
| DO CPU | 几十毫秒 | 单发 TLS 握手装不下（这条已放弃，见 §11 #19） |
| 子请求 | 50/轮 | 探活走 `connect()`，不占；`refill + tfb` 只占个位数 |
| DO 请求 | 10 万/天 | 连接数/3，超了抽样 |

因此：
- **探测按波次限流**：一波用户连接最多 2 次探测，超出的直接用事实里最稳的那条；`/health` 暴露 `probeWaveUsed` 与 `connectWaitMs`。
- **`readFacts` 必须 single-flight**：同一 isolate 内并发读共享一个 Promise，否则等于「每条连接各读一次」。
- **写入批量**：3 连 isolate 攒不到 16 条，所以**结束即冲写**（≤3 行）；超过 20 万连接/天按 `k = ceil(连接数/30万)` 抽样，丢弃计入 `psDrop`。

## 7. 冷启动与客户端订阅

冷启动的残差不在服务端能修的那一半，所以订阅也要参与。结构（每个模式各一套竞速组，共用会让吞吐组混进取速条目）：

```
🅰 模式 (select)
 ├─ 🚀 吞吐优先 (fallback)
 │   ├─ 📡 目标实测（仅 ?tu= 时发）
 │   ├─ 🌐 入口竞速（url-test，server 是 CF 边缘 IPv4 字面量）
 │   ├─ 🔁 中继竞速（url-test，条目带 px=1&rx=<ip>）
 │   └─ 📛 域名入口（回退，v6 网络下必 403，只作最后手段）
 └─ ⚡ 速率优先 (fallback) 同上
```

- **入口竞速组只证明「能到 CF」**：实测它与「不挂组」逐位相同（52.6% / 54.6% / 47.8%），看不到出口族。真正有用的是 `?tu=` 目标实测组。
- **`?tu=` 必须「连测 2 次通过才健康」**：坏中继单次测试有 12.5% 概率蒙对。6 成员+连测 2 = 92.6%，10 成员+连测 2 = 97.4%，10 成员+连测 3 = 98.7%。mihomo 没有「连续 N 次」原语，需服务端 `/health?probe=2` 配合。
- 预算：默认 ≤36 条、`?full=1` ≤60 条；开关 `?e=0` 关入口块、`?r=0` 关中继块、`?ei=4..16` 入口数、`?p=vless|tj|both`（默认 vless）、`?tu=<url>` 开目标实测。
- 健康检查节奏：入口 180s / 中继 300s / 目标实测 300s 且成员 ≤4，合计约 8000 次/天（Worker 免费额度的 8%）。
- 已知局限：`?tu=` 会被**假 200**（nginx 假页）骗过——这一条没有通用解法，不假装能修。

## 8. 承诺与边界

| 条件 | 首请求成功率 | 冷启动 |
|---|---|---|
| 池里有 ≥2 条可用非 CF 出口（`eg=4`） | **92–96%** | 84–90% |
| 只有 1 条可用非 CF 出口 | 93.8% 但不冗余（降级态） | 同上 |
| 只有 v6 出口 / 全部被拒 | **≤14%** | ≤14% |
| 业务 4xx 站点（`api.github.com` 类） | ≥97%（原样透传） | — |

- 弹性实测：好出口 0 → 1 条值 **82 个点**，1 → 2 条只值 0.9 个点，3 条以上不加分 ⇒ 目标是 2 条，不是越多越好。
- 天花板 97.9%：25% 中继「族对但站点拒」+ 8% 探索 + 2% 连不上。
- **不承诺**：每次都挑到最优（2k~3k 池子做不到）、并发下 100%、吞吐一定比直连快（客户端腿是瓶颈时谁都慢）。
- **软化的代价写在明处**：同一场景（3/8 中继被封）软降权 firstPage **92.8%** vs 硬排除 **97.5%**，即「业务 403 零误伤」买了 **4.7 个点**（§15.7 A11）。这笔钱认为值得：误伤是无法自愈的，少 4.7 点只是排序慢一拍。
- 体感口径用 `good3s`（成功且 ≤3s）：盲选 32.4% → v8 68.2%。

## 9. 迁移六步

| 步 | 内容 | 成功率 | 验收 |
|---|---|---|---|
| S1 | 只加事实层（`eg`/`dns` 采集与落库），**选路不变** | 44.6 → 45.5% | 指标必须**不变**（变了说明你顺手用了 `eg`） |
| S2 | `eg` 偏置 + 共享 `ps` | **95.9%**（+50.4） | 两小时内见 +30 点 |
| S3 | `blk` 软降权（×6） | 代价未测（硬排除时 +1.9，软化后只会更小；403 安全见 §15.7） | 空候选率恒 0（不排除） |
| S4 | 冷启动读事实 + 200ms 预算 | 97.8%（+0） | `p95ok` 不涨过 60ms |
| S5 | 订阅新结构 + 竞速组 | 97.8%（+0） | 组内不涨就关 |
| S6 | 清理旧表（`verdict`/`judge`/`relperf`/`relay-health` 四合一） | — | 行为逐位等于 S5 |

每步回滚线：S1 掉 >6 点、S2 两小时不见 +30 点、S3 空候选 >0.1%、S4 `p95ok` 涨 >60ms、S5 组内不涨 —— 关掉后必须**逐位等于上一步**。

## 14. 残余缺陷与「业务 403 会不会被误判」

上一轮的 13 条证伪解决的是「说错了」，这一节列的是**还没解决**的（写完就承认，不装作没有）。

### 14.1 业务 403 的四条路径，逐条走判定链

| 情形 | 长相 | 走到的规则 | 结果 | 判定 |
|---|---|---|---|---|
| A 业务 4xx 带完整页面（GitHub 415/1277B、登录墙 2KB） | 相对自身典型尺寸不小 | R4 不算 `tiny` → 不写 `blk`；`down>0` → 记 `ps(ok)` | 原样透传，不降权、不封锁 | **安全** |
| B 站点级全通道 4xx | 所有通道都一样 | `R_SITE_LEVEL`（无 ≥20KB 对照） | 弃权，什么都不写 | **安全** |
| C 直连腿 4xx | CF 边缘身份 | `R_DIRECT_NEVER` | 弃权 | **安全** |
| D **端点级小 403**（未认证 API、WAF 拦截页，几十~几百字节） | `tiny` 成立，而同站点另一请求（首页）拿到 45KB | R5 三批成立 → 写 `blk[host\|relay]`（软） | 该中继对该站点降权 ×6，90 分钟；仍在候选里 | **不会误伤**（最多排序变差） |

即：**上一版只有 D 这一条会真的把业务 403 变成封锁；本轮已把 `blk` 全面软化（§15），四条路径都不移除候选**。旧文接着说，其余三条都安全。它的伤害面是「该站点在该 isolate 少一条候选」，不是「站点不可用」——因为 `blk` 是 per-relay 的，且 `leastBad()` 保证永不返回空候选。但如果用户大量访问同一个「小 403」端点，几个批次的 90 分钟累积下来可能让某站点只剩 1–2 条候选。

### 14.2 建议的两条收敛（等你拍板，未改进正文）

1. **已采纳（§15）**：`blk` 全面软化为 ×6 代价折算，永不移除候选；硬排除只留给 `dead`。
2. 小 403 若带 `content-type: text/html` 且正文含站点自身标记，降为 C 级（只计数）。但这会引入「读内容」，与 §3.2「只看结构量」冲突，所以列为可选项，默认关。

### 14.3 其它未解决缺陷

| # | 缺陷 | 后果 | 建议 |
|---|---|---|---|
| **D15（已修，§15.2）** | 新站点没有 `bigTypical` 时，`tiny` 恒为假（`down < 0.2×0` 不成立），737B 封锁页会被记 `ps(ok)` | 该站点 `p` 虚高 | `bigTypical` 缺失时：`down ≥ 20KB` 才视为「大」，其余**不写 `ps`**（宁可弃权） |
| D16 | `firstPage >= 4096` 与 `tiny <= 2048` 之间留了 **2048–4096 灰带** | 2–4KB 的正常小页面算「没拿到页」，3KB 的封锁页算「拿到页」 | 已加 `ftGray` 计数，先观察分布再定阈值 |
| **D17（已并入软化）** | `blk` 90 分钟对「概率性拒绝」偏重（v6 出口 2/16 是概率，不是稳定封锁） | v6 中继被整段排除，池子变薄 | 概率性拒绝只走 `ps` 降权；只有「连续三批、每批 ≥3 次全 `tiny`」才写 `blk` |
| D18 | 康复通道与同质化检测会互相干扰：`max/min < 1.5` 触发轮换时，会额外把请求分给已知的弱通道 | 弱池上成功率小幅下降 | 同质化时按 `ps` 轮换，不按字典序 |
| D19 | 事实表与用量账本共用同一个 DO 实例 | 请求数、1 GB 存储、1000 req/s 软上限互相挤占；`SQLITE_FULL` 会影响计量 | 写满时只降级事实层（捕获 `SQLITE_FULL`，不抛错），计量表单独建表并优先保障 |
| D20 | `ps` 的 EWMA 会在「站点临时抖动」时把好通道压低（一次坏样本 p: 0.95 → 0.84，十次 → ~0.1） | 抖动期排序失真，但 45 分钟 TTL 会自愈 | 不改；把「一次坏样本的步长」记进 §5 备注，避免有人后续调大 |

### 14.4 结论

- **业务 403 的误判面是可控的**：三条路径完全安全，唯一会出问题的是「端点级小 403 + 同站首页大响应」这种组合，且伤害是「少一条候选」而不是「站点不可用」。
- **本轮结论**：`blk` 已全面软化 + `p` 下限 0.25 + `dead` 是唯一硬排除 ⇒ 业务 403 的观测**不可能**让任何候选消失（证明见 §15）。

## 15. 业务 403 绝不被误伤：由构造保证，不靠判得准

§14.2 的两条建议已采纳。这一节的结论不是「误判概率很小」，而是**业务 403 在结构上做不到移除候选**。

### 15.1 三条不变量（可机械检查，不依赖阈值）

| 不变量 | 内容 | 为什么业务 403 触发不了 |
|---|---|---|
| **I1 候选只由 `dead` 缩小** | 写 `dead` 的唯一入口要求「**没有 HTTP 响应**」（x509 / RST / timeout / 响应头解析失败） | 业务 403 一定有状态行 ⇒ 永不满足 I1 |
| **I2 业务响应只影响顺序** | `ps` 写 ok 还是写 bad，差别只是 `p` 高低；`p` 只进分母 | 403 带完整页面 → ok（不降权）；403 极小 → bad，但只降序 |
| **I3 `p` 有下限 0.25** | `score = transport / max(0.25, p)` | 最坏代价放大约 4 倍，仍与「从没量过」的候选同量级 |

> 换句话说：`blk`（×6）与 `ps`（≥0.25）都只能让一条中继**排队靠后**，不能让它**消失**。而 `dead` 是唯一能移除了路径的东西，它的证据形态（连接层失败）与业务 403 正交。

### 15.2 本轮补齐的两处

- **D15 已修**：`bigTypical` 缺失时只有 `down ≥ 20KB` 才视为「大」，其余**不写 `ps`**（宁可弃权）——避免把 737B 封锁页记成成功、也避免把「首个观测就是小 403」的站点误读。
- **D17 已并入软化**：概率性拒绝（v6 出口 2/16）只走 `ps` 降权；写 `blk` 额外要求「三批、且每批 ≥3 次全 `tiny`」，单次抖动不可能触发。

### 15.3 最坏情形推演

8 条候选，用户反复访问一个「未认证 API」返回 300B 403、同站首页 45KB：

1. 每条候选被派到一次，各记一个 bad → `p` 从 0.95 降到 0.84 → 排序变化，但全部仍在候选里。
2. 若同一通道连吃三批 ≥3 次 `tiny` → 写 `blk`，代价 ×6 → 该通道排到末位，**仍在候选里**。
3. 全部 8 条都被写 `blk` → 排序退化、`leastBad()` 仍返回一条；请求照常发出，站点照常返回它自己的 403（透传，不改变语义）。
4. 45–90 分钟后 TTL 到期，叠加康复通道与 8% 探索，顺序自动恢复。

**用户看到的结果**：请求成功与否只由站点决定；最坏只是「这次选的中继不是最快的」。

### 15.4 验收清单（已由 §15.7 的原型逐条跑过）

`tools/exp-403safe.mjs` 枚举对抗性流量（小 403 / 带体 403 / 401 / 415 / 429 / 737B 封锁页 / 200 大页 / 200 小页 / 连接失败），断言：

| # | 断言 |
|---|---|
| A1 | 任何序列下候选数 ≥ 1（`leastBad` 兜底） |
| A2 | 业务 4xx 序列**从不**产生 `dead` |
| A3 | 业务 4xx 序列导致候选被移除的次数 **= 0** |
| A4 | `p` 永不低于 0.25 |
| A5 | 纯业务 403 站点：请求吞吐（透传）100%，排序位移中位数 ≤ 1 位 |
| A6 | 737B 封锁页站点：`firstPage` 仍 ≥ 90%（软化后不补偿过多） |

### 15.5 仍然不保证的

- `firstPage` 会把业务 403 算作「没拿到页」——**只影响报表口径**，不参与决策（决策只看 `ps`/`dead`/`cap`）。
- `?tu=` 目标实测组会被假 200 骗过，这是客户端侧判据，与本节无关（§12 未验证清单）。
### 15.6 全池被写 = 站点级：自愈规则

`blk` 写完后立刻检查：若该 host 的**活跃 `blk` 行 ≥ max(3, 75% 候选数)**，判为「更像端点级业务 403」而不是出口封锁 → 清空该 host 的全部 `blk` 行、计数 `bizSweeps++`、并对该 host **静默 30 分钟**（期间不再写 `blk`）。

- 依据：真正的 IP 级封锁只会命中**少数**出口（3/8 那种）；如果「几乎所有候选都被封」，更可能的解释是那个端点对所有人都返回小 4xx。
- 效果（§15.7 的「自愈」列）：S1（纯业务 403）与 S3（全池封锁）各触发 1 次，残留 0 行；S4（真的 3/8 被封）**不触发**，2 行保留并持续降权。
- 代价：真的「全池被封」时会被误判成站点级 → 少一次降权，行为退化为随机选（成功率等同于池子自然状态），**不会 worse than 盲选**。
- 静默必须是「暂时」的：到期后第一条合格证据立刻恢复写入（原型 A12 用「期内 0 行 / 到期 >0 行」两边都断言，防住「永久静默」这种静默失效）。

### 15.7 原型实测（`node tools/exp-403safe.mjs`，A1–A12 全部通过）

| 场景 | 响应 | firstPage | dead | 业务写 dead | 最低 p | 候选数 | 残活 blk | 自愈 | leastBad | 最长连选 |
|---|---|---|---|---|---|---|---|---|---|
| S1 纯业务 403（300B + 每 5 条一次 45KB） | 400/400 | 20.0% | 0 | 0 | 0.250 | 8 | 0 | **1 次** | 0 | 6 |
| S2 业务 4xx 带完整页面（1277B） | 400/400 | 0.0%（口径） | 0 | 0 | 0.950 | 8 | 0 | 0 | 19 |
| S3 全池 737B 封锁页 | 400/400 | 0.3% | 0 | 0 | 0.250 | 8 | 0 | **1 次** | 0 | 19 |
| S4 3/8 中继被 737B 封锁 | 400/400 | **92.8%** | 0 | 0 | 0.250 | 8 | 2 | 0 | 0 | 19 |
| S4h 同场景·**旧设计（blk 硬排除，仅对照）** | 400/400 | **97.5%** | 0 | 0 | 0.688 | 8→5（被排除 3） | 3 | 0 | 0 | 19 |
| S5 连接失败 + 业务 403 混合 | 389/400 | 0.0% | 8 | 0 | 0.950 | 1 | 0 | 0 | 140 | 37 |

三条从表里读出来的结论：

1. **S1 里 8 条中继全被写了 `blk`（随后被自愈清空，见 §15.6），行为没有变坏**——因为惩罚是**均匀**的（×6 对所有候选一致），排序自洽、自行抵消。这正好说明「软化」的性质：软封锁只会让「局部坏」的通道靠后，对「整体被误判」免疫。
2. **S5 里 `leastBad` 被触发 140 次**：8 条中继全部 `dead` 时会走兜底。这暴露一条实现要求——**`leastBad` 的第一顺位必须是直连**，不能是「最后一个死掉的中继」，否则等于用一个坏通道顶替。
3. **软化的价格是 4.7 个点**（S4 92.8% vs S4h 97.5%），换来的是业务 403 永远不会把候选写没——A11 已把「代价 ≤6 点」固化成断言。
4. S2 的 firstPage 是 0% 属于口径（1277B < 4096 阈值），**不改判据**：业务 4xx 记 `ps(ok)`、不降权、不封锁，收益体现在排序不变而不是报表变好看。

| R2 | x 这类站点成功率要高 | `eg` 先验 + 共享 `ps` + 冷启动读事实（§5、§8） | 满足：40% → 92–96%（条件式） |
| R3 | 按站点（地区差异导致的表现不同）筛中继，吞吐/速率都能路由到最优 | 每 `(host,relay)` 的 `ps` 与相对 `cap`（§5.1）；地区不设独立维度——它通过「同一条中继对不同站点的表现」被隐式学到；显式地区分组只保留在订阅侧 `🌍 地区` | 满足（吞吐仅在「中继间 ≥2x 差异」时可学，见 §5.1 噪声门与 §8 边界） |

| R5 | 普适性、不特化站点 | 判据全部是结构量（`tiny` 相对尺寸、`hasBigPeer`、`cf-connecting-ip` 是否含 `:`）；代码无站点域名分支（§11 第 1–2 行即此教训） | 满足（历史 7.41 已删 `X_RULES`） |
| R6 | IP 级封锁探测 | `blk`（A 级三批）+ `dead`（连接层）+ `eg` 回显（§3.2、§4） | **部分满足**：探测照做，但结论**只用于排序**（×6），不再「排除」。见下方权衡 |
| R7 | 业务 403 绝不被误伤 | §15 的不变量 I1–I3 + 自愈（§15.6）+ A1–A11 原型 | 满足（构造性保证，代价 4.7 点，§8） |

**R6 的权衡必须说清**：软化之后，一条「被确认封锁」的中继仍会以较低优先级参与排序，并在 8% 探索里被抽中。这正是那 4.7 个点（§15.7 A11）的去向。为什么不干脆排除它：
- 排除 = 不可自愈的错误（7.57 实测：97% → 2/20，人工才能救回来）。
- 排序 = 一次请求的选择代价，且 TTL 到期／康复通道会把它拉回来。
- 业务 403 与 IP 封锁在「一次小响应」这个观测上不可区分（§15.1 I1 之外的唯一模糊点），所以宁可少 4.7 点，也不换不可逆的删除。

如果将来要恢复「硬排除」，前提是**新增一个与业务响应正交的证据源**（例如两张不同 ASN 的探测同时失败），并且默认关闭、带独立开关与回滚线——这条写在这里，防止后人只看到「97.5% > 92.8%」就把软化改回去。
