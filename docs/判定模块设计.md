# 判定模块设计（v7.0 草案）

> 目标：把「这个客户端、走这条通道、连这个目标」的可用性判断收敛成**一个模块、一张表、一条决策链**。
> 现状是 9 个各自长出来的机制，互相覆盖、无法解释线上行为；本文用「以 IP 为单位」重画。
>
> **注意**：本文描述的是**线上 7.x 的判定层**（v8 之前）。v8 把 `blk` 全面软化（只降权、不排除）并由构造保证业务 403 不被误伤，见 [v8.md](v8.md) §15。

## 1. 现状：9 个重叠机制

| 机制 | 位置 | 粒度 | 谁写 | 谁读 | 问题 |
|---|---|---|---|---|---|
| `S.needPx` | `src/core/state.ts` | 域名 | 直连 0 字节关闭 | `session` 判 wantPx | 6 小时硬记忆，403 学不到 |
| `S.cfHost` | `src/core/state.ts` | 域名 | DoH 查 CF 网段 | `session` | 只回答「是不是 CF 托管」 |
| `pxHosts` / `isPxHost` | `src/core/hosts.ts` | 域名 | 环境变量 | `session` | 手写名单，与自动识别重复 |
| `S.cfHttp` | `src/proxy/cfverdict.ts` | 域名 | `httpProbe`（走 CF 边缘直连） | `session` | 3 分钟，只对「我方直连」有意义 |
| `S.cfBlock` | `src/core/state.ts` | 域名×节点 | 流量字节数猜 | `selector.current` | 阈值判不出小响应，等于噪声 |
| `S.relayOff` | `src/core/state.ts` | 节点 | `probeSni` 判是否 CF IP | `selector.current` | 判的是「出口是不是 CF」，不是「能不能过」 |
| `S.relaySite` | `src/core/state.ts` | 站点×节点 | cron 里 `probeSni` 握手成功 | `selector.current` | 握手成功 ≠ HTTP 200 |
| `S.viaRelay/viaDirect` | `src/core/state.ts` | 域名 | 连接成功 | `session` | 只记「上次谁成过」，无失败语义 |
| `S.edge` | `src/proxy/edge.ts` | 入口 IP | `probeTls` 探自己 `/health` | `sub` | 入口偏好，与通道判定无关（应保留但分表） |

共同病根：**判定粒度是域名，证据来源是「有没有字节」，结论是布尔**。而真实世界是
`(目标 IP) × (通道 IP) × (客户端 IP 族)` 的笛卡尔积，结论是状态码。

## 2. 新模型：三层 + 一张表

```
观测层  ── 流量弱证据（flush 里的 via/node/ttfb/down/failed/status?）
        ── 探测强证据（probeTls：TLS + GET，拿真状态码）
        ── 客户端证据（订阅里的 expected-status，端到端）
   ↓ 只写「证据」，不做判定
判定层  ── 一张表：Verdict{ target, chan, state, code, ms, n, at, src }
        ── 状态机：unknown → suspect → ok / blocked / dead
   ↓ 只回答「这条通道对这个目标能不能过、有多快、多可信」
选路层  ── 候选通道 → 打分 → 探索 → 兜底
        ── 决策输出：direct / relay(ip) / edge(ip) / 放弃
```

### 2.1 键与维度

- `target`：目标站的 **A 记录 IP**（DoH 解析，缓存 10 分钟）；中继路径无法钉死目标 IP 时用 `*`
- `chan`：`d`（直连，即本 Worker 出口）、`r:<ip>`（中继 IP）、`e:<ip>`（客户端入口 IP，仅入口表使用）
- 键：`target|chan`，两段都是 IP 或 `*` —— 这就是「以 IP 为单位」

### 2.2 表项

```ts
interface Verdict {
  t: string;      // 目标 IP 或 "*"
  c: string;      // "d" | "r:1.2.3.4" | "e:5.6.7.8"
  state: 0 | 1 | 2 | 3; // 0 unknown 1 ok 2 blocked 3 dead
  code: number;   // 最近一次 HTTP 状态码（0 = 没握手）
  ms: number;     // 握手 EWMA
  n: number;      // 样本数（用于置信度）
  at: number;     // 最近一次证据时间
  src: 0 | 1 | 2; // 0 traffic 1 probe 2 client
}
```

### 2.3 状态机与 TTL

| 证据 | 迁移 | TTL |
|---|---|---|
| traffic：连接建立但下行 < 站点画像下界 | → suspect | 10 分钟 |
| traffic：下行 ≥ 画像中位 | → ok（弱） | 30 分钟 |
| probe：TLS 失败/超时 | → dead（强） | 20 分钟 |
| probe：403 | → blocked（强） | 30 分钟 |
| probe：2xx | → ok（强） | 30 分钟 |
| client：`expected-status` 失败 | → suspect | 10 分钟 |
| 任意 `client` 成功 | → ok（强） | 60 分钟 |

规则：**只有 probe / client 能把状态推到 dead/blocked**；traffic 永远只到 suspect。
`suspect` 不硬拦，只加罚分并保留采样。

### 2.4 客户端 IP 族

`cf-connecting-ip` 解析出 IPv4/IPv6（现在 `src/proxy/session.ts` 没读这个头）。确定性规则：

> 目标在 CF 网段 **且** 客户端是 IPv6 → 跳过 `d` 与所有 `e:`/`r:<CF IP>` 通道，只走非 CF 中继。

理由（已实测）：CF→CF 会透传客户端 IP，X 对 IPv6 出口一律 403（body 恒为 4 字节 `IPv6`）。

## 3. 选路

```
候选 = { d } ∪ { r:<ip> : ip ∈ 活节点 } ∪ { e:<ip> : ip ∈ 入口偏好 }
过滤 = 状态为 blocked/dead 的去掉（全被过滤 → leastBad 兜底）
分数 = base(t,chan) + 风险 + 排队 + 抖动
       base   = 模式代价（lat 用 latency+传输，tput 用 E10）+ 5000·pFail（已有实现）
       风险   = suspect ? 0.3×failMs : 0；unknown 用乐观面 −β·σ
       排队   = inflight(chan) × 本请求传输时间
       抖动   = 0.5×MAD
探索   = 状态 unknown 的通道抽 2–5%（pxShadow），保证「变好」能被发现
```

**决策顺序**（替代现在的 6 步链）：

1. 解析目标 IP（含缓存）；拿不到 → 走域名直连（旧行为）
2. 取候选通道 → 过滤 → 打分
3. 若最高分是 `r:` 但 `(*|r:ip)` 为 blocked 且存在 `ok` 的 `r:` → 用 ok 的
4. 全 blocked → `leastBad()`（保留现状）并 `cnt("dead")`
5. 结果写回 `st.chan`，连接结束后按 §2.3 写证据

## 4. 证据来源与预算

| 来源 | 成本 | 何时 | 上限 |
|---|---|---|---|
| traffic | 0 | 每次连接收尾 | — |
| probe | 1 子请求 + ~1ms CPU | cron 每轮 + `?vt=` 手动 | 每轮 ≤6（`SCAN_SUB` 内）、每次调用 ≤3 |
| client | 0 | 订阅健康检查 | — |

`probeTls` 用 vendored `subtls`（48.5KB，3 张根证书 4.2KB）：TLS 1.3 + `GET`，拿状态行。
只能 TLS 1.3 —— 对只支持 1.2 的站点（如百度）返回 `Expected 771, got 769`，此时记为 `unknown` 而非 blocked。

## 5. 入口偏好（保留，但分表）

入口偏好量的是「用户 → CF 边缘」，与「CF → 目标」正交，必须分开存：

- 键：`*|e:<ip>`，用同样的 Verdict 结构
- 探测：`probeTls(自家域名, "/health", "<edge ip>:443")`
- 排序：`ms + 400×fail/(n+2)`，只出「6 小时内测过、成功率过半」的
- 用途：订阅里 `server: <ip>` + `servername/host` = 域名（缺 servername 就是上次全超时的根因）
- 持久化：KV `edge:pref`（≤16 条，90 分钟节流）

## 8. 不变量

1. `probeTls` 永不抛错（内部兜底），必须 `.then(ok, err)` 接住 socket pump
2. 判定表只存**证据**，不在写入路径做决策
3. 任何状态为 blocked/dead 的通道**不得硬拦到「无候选」**，必须有 `leastBad()` 兜底
4. 子请求：一次请求内 `probe` ≤3，一轮 cron ≤6
5. `?vt=` 是只读诊断，不得改动 `S.alive` / 池子

## 9. 与既有 proxyip 池的关系（不替换，降级为「候选供给 + 基础质量」）

proxyip 池（`src/px/pool.ts`、`src/px/seed.ts`、`src/nodes/*`）继续存在，但职责从「决定走谁」收缩成两件事：

| 池子现在做的 | 新设计里 | 说明 |
|---|---|---|
| 抓取候选（`refillPool`、`px:pool:N`、`px:seed` 名字） | **保留** | 候选供给，与判定无关；seed 仍只存 `{k,h,p,cc}` |
| 准入探活（`probeProxy`：SNI=www.cloudflare.com 的 TLS 握手） | **保留** | 便宜（1 子请求、不发 HTTP），回答「这个 IP 是不是 CF 边缘」 |
| 延迟/失败率统计（`nstat`、`scoreParts`） | **保留，但只作 base 代价** | 与「对这个站点能不能过」正交 |
| 选路（`SEL.current` 选谁） | **上移给 `policy.ts`** | 池子只出候选，不再做最终决定 |
| `S.relayOff`（出口是不是 CF） | **删除** | 改为打分时用 `isCfIp(ip)` 现算，不落状态 |
| `S.relaySite` / `S.cfBlock` / `S.needPx` | **删除** | 由判定表取代 |

分工一句话：**池子回答「有哪些中继、它们的基础质量如何」，判定表回答「这条中继对这个站点、这个目标 IP 行不行」**。

子请求预算（免费计划 50/请求，cron 一轮）：

| 用途 | 每轮上限 | 成本 |
|---|---|---|
| 准入探活（`probeProxy`，池子） | ≤32 | 1 子请求，无 HTTP |
| 判定探测（`probeTls`，本模块） | ≤6 | 1 子请求 + ~1ms CPU |
| 入口偏好（`probeTls` 自家 `/health`） | ≤2 | 1 子请求 + ~1ms CPU |

`SCAN_SUB=48` 作为总闸，`SCAN_MAX=400` 只约束 `?scan=` 手动刷新。`ALIVE_MAX=800` 仍是内存上限（判定表按需裁剪，最多 600 条）。

## 10. 两个模块怎么平衡

池子（候选 + 基础质量）与判定表（逐目标可用性）共享两样稀缺资源：**每轮 48 个子请求**、**单请求 10ms CPU**。平衡的做法是四件事：一次探测两处消费、固定保底 + 按价值分配、双向回馈、单点去重。

### 10.1 一次探测，两处消费

任何一次探测都产出一个 `Probe{ ip, host, tlsOk, status, ms, at }`，由**同一个写入函数**分发给两个模块：

```
recordProbe(probe) →
  pool:    tlsOk ? nsProbe(ip, ms) / nsOk(ip) : nsProbeFail(ip)     // 基础质量
  verdict: vSet(targetIp|chan, code, ms, src=1)                     // 逐目标可用性
```

同一条结果不许写两次、也不许两个模块各自再探一次 —— 这是现在「`probeSni` 在 cron 里探一轮、`cfBlock` 又靠流量猜一轮」重复劳动的根因。

### 10.2 固定保底 + 按价值分配（每轮 48）

| 用途 | 保底 | 上限 | 说明 |
|---|---|---|---|
| 池子准入（`probeProxy`，无 HTTP、CPU≈0） | 8 | 32 | 保证 `alive` 不饿死 |
| 判定探测（`probeTls`，TLS+GET，CPU≈1ms） | 4 | 12 | 只探热站点 × 候选通道 |
| 入口偏好（`probeTls` 自家 `/health`） | 0 | 2 | 无候选时让路 |
| 流量触发的即时确认 | 0 | 剩余 | 见 §10.4 |

先各给保底（合计 12），剩余 36 按价值分配：

```
价值(条目) = 流量占比(站点) × 代价(通道) × 陈旧度
陈旧度 = min(1, (now - at) / TTL)
代价 = base 分数（该通道在该模式下的毫秒当量），差通道优先被证伪
```

流量占比取 `S.hostNode` 里该站点的连接计数（已有的站点画像），不新增加权表。

### 10.3 双向回馈

| 方向 | 信号 | 动作 |
|---|---|---|
| 判定 → 池子 | 同一中继在 **≥3 个不同目标** 上都是 `blocked/dead` | `nsSiteFail` 累加，让它自然掉出候选带（不直接拉黑，可能是站点侧问题） |
| 判定 → 池子 | 某中继在热站点上 `ok` 且 `ms` 低 | `nsOk` + 参与 `edge`/订阅偏好排序 |
| 池子 → 判定 | `isCfIp(ip)` | 决定通道类别：CF 边缘中继对 CF 托管目标**只作兜底**，不作首选 |
| 池子 → 判定 | `capBps`、`pFail` | 作 `policy` 的 base 代价；判定只叠加「能不能过」的风险项 |

关键克制：**判定状态不回写池子的黑名单**。池子的黑名单表示「这台机器本身连不上」，判定的 blocked 表示「这台机器对这个站点不行」—— 两者混用会让一次站点侧风控污染整池。

### 10.4 流量触发的即时确认（不进 cron 预算）

`flush` 收尾时若发现「该站点此前 `ok`、这次下行 < 画像下界」→ 只记 `suspect`（§2.3），同时把 `(targetIp, chan)` 塞进即时队列；下一次请求如果有余量（`ctx` 允许）就探一次确认。这样把「确认」放在有真实需求时，而不是每 30 分钟盲扫。

### 10.5 单点去重与幂等

- 判定表键是 `target|chan`，同一 (target, chan) 在 TTL 内只探一次；`sweep` 与 cron 共用同一张「待探队列」
- 池子准入探活结果写 `nstat`；判定探测结果也写 `nstat`（`tlsOk` 部分），避免同一 IP 一周内被两条链路各探一遍
- `?vt=` / `?edge=` 都是只读诊断，不改 `S.alive`、不改池子

### 10.6 效果预期

| 指标 | 现在 | 平衡后 |
|---|---|---|
| 每轮子请求 | 最多 48 全给池子准入，判定的信息全靠猜 | 12 保底 + 36 按价值，判定有真状态码 |
| CPU（cron 一轮） | 48 次裸握手 ≈ 可忽略 | 8 次 subtls ≈ 8ms（上限 12 次 ≈ 12ms，仍在 10ms/请求的余量内靠并发摊薄） |
| 判定覆盖率 | 0（看不见状态码） | 热站点 × 前 5 通道 30 分钟内必有结论 |

## 11. 测试清单

- 状态机：traffic 只到 suspect；probe 403 到 blocked；2xx 回到 ok；TTL 过期回 unknown
- 键：`t|d`、`*|r:ip`、`*|e:ip` 三类的写入与读取优先级（精确 > 通配）

- 选路：全 blocked 时返回 `leastBad()`；未知通道被抽中（探索）
- probe：TLS 1.2-only 站点 → `unknown`（不是 blocked）

## 11. 差分判据（v6.98）：怎么区分「IP 级封锁」和「正常的业务 403」

用户追问（m06785/m07190）：「有一些正常的业务逻辑也会返回 403，会不会误判」。

### 11.1 尺寸救不了这个问题（实测）

| 场景 | 连接总下行 `down` | 说明 |
| --- | --- | --- |
| CF 边缘按 IP 族拒（x.com 403） | 3–12 KB（计数桶 `sz4`） | 其中 3–5 KB 是 TLS 握手证书，错误页只有几字节 |
| 中继把自家 nginx 页当响应 | ≈4 KB | 同样是「握手 + 小正文」 |
| 正常业务 403（`api.x.com` 无凭证） | 3–5 KB | 与封锁页**完全同带** |

所以任何「小于 X 字节就判封锁」的阈值都会误伤业务 403。计数器 `sz1..sz4/szBig` 就是为量这件事加的。

### 11.2 最终判据：同一站点「另一条通道刚拿到过整页」

```
大响应 down >= 20KB        → 记基线 bigByHost[host]=now，bigChan[host]=通道
小响应 0 < down < 12KB     → 只有 bigChan[host] 存在、30 分钟内、且不是当前通道时，才判「这条通道被封」
没有任何基线               → 只排队复核 + 记 needPx（下次优先中转），**不写判定**
中继小响应累计 >= 3 次      → 判该中继对这个站点不可用（假 200）
```

业务 403 的特征是「在所有通道上都一样小」，永远凑不出差分；封锁的特征是「换一条通道就变大」，差分立刻成立。

### 11.3 线上对照（6.98/6.99）

- `api.x.com`（合法业务 403/404）连打 3 次 → 判定表里 **0 行**（`?vt=api.x.com&do=1`）。
- `x.com` 连打 5 次 → 5/5 200；已知被封的 6 条中继仍在判定表里（state=2），选路绕开它们。
- 6.96 时（差分前的单次判据）曾用 1 次 403 就在 DO 里落下 `x.com|r:185.253.117.147 state=2`，跨 isolate 立刻生效。
